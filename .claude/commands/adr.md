# /adr — ADR作成コマンド

新しいArchitecture Decision Record（ADR）を作成します。

## 手順

1. `docs/adr/` 内の既存ADRを確認して次の番号を特定する
2. `docs/adr/ADR-XXXX-[title].md` として新規ファイルを作成する
3. 以下のテンプレートで記入する

## テンプレート

```markdown
# ADR-XXXX: [意思決定のタイトル]

## Status
Proposed
<!-- 他に使える値: Accepted / Deprecated / Superseded by ADR-XXXX / Trial（「まとめてTrial導入し項目ごとにロールバックする」パターンは `meta/adr/ADR-0014-third-party-skill-adoption-trial.md` 参照） -->

## Date
[YYYY-MM-DD]

## Context
[なぜこの判断が必要になったか。背景・問題・制約を記載]

## Decision
[何を決めたか。具体的に記載]

## Rationale
[なぜそう決めたか。採用しなかった代替案も記載]

### 採用しなかった代替案
- **[代替案1]**: [採用しなかった理由]
- **[代替案2]**: [採用しなかった理由]

## Consequences
[この決定による影響・トレードオフ]

### メリット
-

### デメリット・リスク
-

## Related
- [関連ADR・ドキュメントへのリンク]
```

## 見送り（不採用）を記録する場合のバリエーション

「検討したが今は採用しない」という結論も、通常のADRと同じ形式で記録する。ADRを書かず口頭・チャットの議論だけに残すと、後で同じ検討を繰り返すことになる。

- **タイトル**: 末尾に `— 見送り` または `— Not Adopted` を付け、一覧からファイルを開かなくても結論が分かるようにする
- **Status**: `Accepted` のままでよい（承認されているのは「不採用という決定」自体であり、ツール導入そのものではない）
- **Decision**: 「今は採用しない」ことと、再検討する条件・タイミングを明記する（例:「〇〇が実運用で問題化したら再検討する」）
- **Rationale**: 「時期尚早（premature）」など見送りの理由を明記する。将来採用する場合の設定方針（除外パス等）を先に書いておくと、再検討・導入がスムーズになる
- 参考実装: `meta/adr/ADR-0007-tdd-enforcement-probity.md`（本リポジトリにおける「オプション導入」パターンの例。`meta/adr/README.md` の「Harness-design ADR patterns」も参照）

## ADRを書くべきタイミング

- 新しいライブラリ・フレームワークの採用
- アーキテクチャパターンの変更
- セキュリティ方針の変更
- DBスキーマの大規模変更
- AI開発ポリシーの変更
- 検討した結果、あえて採用しないと決めたとき（見送り。上記バリエーション参照）
