# /commit — コミット提案コマンド

現在の変更をどのようにコミットに分割するかを提案し、人間の承認1回でコミットしてください。
最初に `docs/development/git-workflow.md` を読む（ルール。有効なプロファイルは `.claude/rules/70-git.md`
にある）。このファイルは手順のみを定める。

## 手順

1. **ブランチ確認** — `git status` と `git branch --show-current` を実行する。`main` 上にいて、
   変更がdocs/誤字修正のみを超える場合は、先にブランチに移る（§0 プロファイル、§1 ブランチ）:
   `lite` ではブランチ名を決めてその旨を伝える。`standard` ではブランチ名を提案し、承認されるまで
   止まる。その後 `git checkout -b <name>` を実行する（未コミットの変更はそのまま引き継がれる）。
2. **差分をすべて読む** — ステージ済み・未ステージ・未追跡のすべて（`git diff`, `git diff --cached`,
   `git ls-files --others --exclude-standard`）。
3. **コミット単位にまとめる** — §2 コミット単位に従う: 振る舞いの変更 / リファクタ / 整形を分ける。
   マイグレーションは単独。テストとdocsは対応するコードと一緒にする（`lite` では `/tdd` の1サイクルを
   1コミットにしてよい——§0 プロファイル）。すべてのコミットが
   Greenを保つ順にグループを並べる（例: マイグレーションはそれを使うコードより前）。
4. **グループごとにメッセージを起草する** — §3 コミットメッセージに従う。変更行数が約400行を
   超えるグループは分割候補として指摘する（§6 のスコア30に相当）。
5. **テスト** — このセッション中に、作業ツリー全体に対してテストが通っていること（例: `/tdd` の
   Green実行）。通っていなければ、ここで1回実行して結果を報告する。
6. **承認を1回だけ求める** — 1つの表で提示する。`lite` の一括実行（commit → merge → push を
   まとめて行う——§4 権限）では、ここでは承認を求めない。表を `prepare-merge` のステップ5に渡し、
   その計画への1回の承認でコミットもカバーする。承認後にステップ7へ進む。

   | # | Files | Lines | Message |
   |---|---|---|---|

   ユーザーはメッセージの編集、グループの統合・削除、ファイルの移動ができる。承認前には
   何もコミットしない。
7. **コミット** — グループごとに順番に: `git add <files>` の後、承認されたメッセージと
   `Co-Authored-By:` トレーラーを付けて `git commit` する。push・amend・rebaseは行わない（§4 権限）。
8. **報告** — 短縮SHAと件名を報告する。ブランチの作業が完了していそうなら `prepare-merge` を提案する。

## 制約

- コミットするのは現在の差分に含まれるファイルのみ。ユーザーが表で確認していないファイルまで
  `git add -A` で無差別に追加しない
- 自然文でのコミット依頼（「これをコミットして」）も同じ手順に従う
- 1つのファイル内に2種類の変更（例: 振る舞いの変更 + リファクタ、振る舞いの変更 + Pintの整形）が
  混在している場合は、その旨を伝えて1つのコミットとして提案するか、人間に `git add -p` で分割して
  もらう。部分パッチを手作りしない（`git apply --cached`）
