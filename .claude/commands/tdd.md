# /tdd — TDD（Red→Green→Refactor）実行コマンド

指定した機能・UC番号に対してTDDサイクルを進行してください。

## 実行前に読み込むファイル

- `docs/product/use-cases.md`
- `.claude/rules/30-testing.md`
- `docs/development/git-workflow.md`（ブランチ・コミット・マージの手順。プロファイルは `.claude/rules/70-git.md`）

## 手順

**Gate 4承認からステップ8の報告までは、ステップの間でユーザーを待たない**——順番に実行し、ステップに「止まる」と書かれている箇所か、フックが止まるよう求めるメッセージで呼び出しを拒否したときだけ止まる（ADR-0020）。各ステップの結果はその都度示す。ユーザーが答えるのはステップ8の報告の1回だけである。

0. **ブランチ確認**: 現在のブランチが `main` の場合は、ステップ1の前にブランチに移る——`lite` ではブランチを作成してその旨を伝え、`standard` ではブランチ名を提案して同意を待つ（`docs/development/git-workflow.md` §0 プロファイル、§1 ブランチ）
1. **Red**: `test-writer` サブエージェントに失敗するテストの作成を依頼する（実装コードには触れさせない）。`test-writer` は自分が触ったファイルだけを実行する（`.claude/rules/30-testing.md` のテスト実行バジェット）
2. **Gate 4（テストケース承認）**: 作成されたテストの内容と失敗ログをユーザーに提示し、意図通りの仕様になっているかレビューを求める。**承認を得るまで次のステップに進まない**（`.claude/rules/00-global.md` の品質ゲート）。承認の直後に承認スナップショットを保存し、その1行の結果を提示する: `bash .claude/hooks/tdd-snapshot.sh record`（`tests/` と `docs/product/` を `.git/` 内にコピーする。ADR-0017）
3. **Green**: Gate 4承認後、`tdd-implementer` サブエージェントにテストを通す最小実装を依頼する。`SPEC_CONFLICT` で止まった場合、または試行回数の上限（3回、または同じ失敗が2回）に達した場合は、その報告をユーザーに提示して待つ——自分の判断で再度呼び出さない。それ以外の理由（ターン数が尽きた等）でGreenにならずに戻った場合は、残りの作業を伝えてもう1回だけ起動してよい。`agent-guard.sh` は、Gate 4承認1回あたり実装者の起動を2回、実装者によるファイル書き込みとコマンドを60回まで許す。拒否されたら、終わったことを示して待つ。仕様の矛盾は人間が解決し、その後サイクルはステップ1からやり直す。新しいGate 4承認でスナップショットは置き換わる
4. **ゴールが動いていないことの確認**: `bash .claude/hooks/tdd-snapshot.sh verify` を実行する。exit 0 → 続ける。exit 2 → 承認後に `tests/` または `docs/product/` が変わった: 表示された差分を提示し、ユーザーが判断する（変更を破棄する、またはステップ1からやり直す）まで止まる。exit 3 → スナップショットがない: ユーザーに伝えて止まる。exit が 0 だったときは、続けて `bash .claude/hooks/fixture-literal-check.sh` も実行する: exit 0 → 続ける。exit 2 → 表示された `FIXTURE_LITERAL` の行をそのまま提示し（アプリケーションコードが、承認済みテストにしか含まれない値と比較している）、ユーザーが判断するまで止まる。exit 3 → ユーザーに伝えて止まる。ブロックされた試みの行（または「No blocked attempts」の行）と、出力された場合は `WARNING` の行を、表示されたままユーザーに提示する——これは `logs/audit.jsonl` から取っているので、実装者の報告に書かれていなくても提示する。両方のチェックが通ったら `bash .claude/hooks/tdd-snapshot.sh mark-green` を実行する（Green後のアプリケーションファイルを記録する。ステップ7で使う）。その後、Green確認（テスト結果）を示して続ける。`standard` では、Red + Greenのコミットを先に行う: `/commit` の手順で提案し、承認を待つ——これが `standard` で予定された唯一の停止である（Refactorは別コミットのまま）。`lite` では、ステップ8の報告からサイクル全体を1回でコミットする（`docs/development/git-workflow.md` §0 プロファイル）

   **テストの実行**（`.claude/rules/30-testing.md` のテスト実行バジェット、ADR-0021）: Gate 4の根拠（ステップ2）には、新規・変更したテストファイルを `php artisan test --compact <paths>` で1回実行する。Gate 4でテストが差し戻されたら、変わったファイルだけを再実行する。`tdd-implementer` は対象ファイルだけを実行する。Green確認（ステップ4）では、全件を `php artisan test --compact` で1回実行する——これがサイクルの正式な実行であり、そこに含まれる対象ファイルを別に再実行しない。対象テスト以外の失敗は `tdd-implementer` に戻し、その試行回数に数える。それ以降、全件を再実行するのはコードが変わったとき（サイクルレビューの修正、Refactor）だけである。

   **サイクルレビュー**（Green確認の直後。設定は不要で、ユーザーが起動するものもない——ADR-0020）:
   - `git diff HEAD --numstat` と `app bootstrap config database lang resources routes` 配下の未追跡ファイルを合わせた変更行が20行未満で、かつ `resources/`・`lang/`・`routes/`・`database/migrations/`・`app/Policies/`・`app/Http/`・`app/Livewire/` 配下のファイルが1つもない場合は、「サイクルレビューをスキップ: 小さな変更」と伝えて**スキップ**する
   - それ以外は `cycle-reviewer` サブエージェントに依頼する。渡すのは次のものだけ: このサイクルのテストで名前が挙がっているUC ID、それらのアプリケーションパスの `git diff HEAD` を `<untrusted_diff>` タグで囲んだもの、未追跡のアプリケーションファイル名。実装者の報告や自分の推論は決して渡さない
   - 返ってきた行を読む。引用された行がそのファイルの指摘行付近に存在しない `FINDING` は捨てる（捨てた件数を伝える）。`END` 行がない場合は「サイクルレビューを利用できません——マージ前に `/review` を実行してください」と伝えて続ける
   - 指摘に `SECURITY` か `SUSPECT_INSTRUCTION` がある、`SPEC_CONFLICT` か `USER_FACING_CHANGE` が `MEDIUM` 以上、または重大度が `HIGH` のものがある場合は**止まる**——指摘を書かれたまま示し、ユーザーを待つ
   - それ以外の場合は、`DEFECT` と `DOMAIN_BOUNDARY` の指摘を**1回だけ**修正し（`tests/` と `docs/product/` には決して触れない）、全件テストを再実行し、ステップ7と同様に `verify-green` を実行する。`LOW` の `SPEC_CONFLICT` / `USER_FACING_CHANGE`（例: ユースケースと文言が違うメッセージ）と `TEST_GAP`（テストはロックされている）は修正しない——修正しなかったものと合わせてステップ8に残す
5. **実挙動の確認**: ここでは止まらない。`run` スキルでアプリを試す推奨は、ステップ8の報告に入れる——バンドルされたスキルは人間が明示的に呼び出した場合にのみ実行されるため、AIが自動実行せず推奨する旨を伝える（`.claude/rules/30-testing.md`）
6. **E2E追加（該当する場合のみ）**: 対象がUCのクリティカルフロー（`docs/product/use-cases.md` 参照）かつUI変更を含む場合、`.claude/commands/generate-e2e-test.md` を読んでその手順に従い、Playwright E2Eテストを追加する（`/generate-e2e-test` 自体は起動しない——コマンドは人間が入力したときだけ実行する。ADR-0017）
7. **Refactor**: 必要に応じてリファクタを行う。リファクタ中は対象テストを再実行し、最後に全件を1回実行してGreenが維持されていることを確認する（何もリファクタしなかった場合はどちらも省く）。その後 `bash .claude/hooks/tdd-snapshot.sh verify-green` を実行する（レビュー指摘の修正など、Green後に行ったその他の変更の後にも実行する）: exit 2 → 表示された `STOP` の行をそのまま示し（Green後の変更が、権限・破壊的操作・セキュリティ・secrets・外部への影響・依存関係・整合性に触れている）、ユーザーが判断するまで止まる。exit 3 → ユーザーに伝えて止まる。exit 0 → `LISTED` の行をステップ8のために残す
8. **完了報告**——1通にまとめ、判断が必要なものを先頭に、短く書く。バグが見つかったかどうかに関係なく必ず出す。サイクルが途中で止まった場合も、そこまでの項目で出す:
   1. **要判断** — サイクルを止めたもの、修正しなかったサイクルレビューの指摘
   2. **変わった画面** — 下記のマージ計画に挙がる画面（`lite`）、または `LISTED` のページファイル（`standard`）。1行、または「なし」
   3. **チェック** — テスト結果と実行したテスト（回数とおおよその時間。`.claude/rules/30-testing.md` のテスト実行バジェット）、ステップ4のゴール確認とfixtureチェック（ブロックされた試みの行は表示されたまま）、`verify-green`
   4. **確認せずに修正したもの** — サイクルレビューの修正ごとに1行、またはレビューをスキップしたこと
   5. **あわせて確認** — ステップ7の `LISTED` の行（「Green後に変更」）と、`run` スキルでアプリを試す推奨
   6. **提案するコミットとマージ計画** — `lite` では、`.claude/skills/prepare-merge/SKILL.md` を読み、ユーザーが commit → merge → push の一括実行を依頼したものとしてステップ1〜5に従う（まだコミット・マージはしない）。1回の承認でそれらを実行する（§4）。このブランチで続けてサイクルを回す場合、ユーザーはコミットだけを承認してもよい。`standard` では、Refactorの変更について **`/commit`** を提案し、ブランチの作業が完了したら **`prepare-merge`** を提案する（`/review` の要否はこれが判定する——`docs/development/git-workflow.md` §6）

## 制約

- 上記の手順・順序を省略しない（特にステップ2のGate 4承認とスナップショット、ステップ4のスナップショットの確認）
- 各テスト実行のサマリー行と失敗を、`.claude/rules/30-testing.md` のテスト実行バジェットに従って示す——結果が分かっているツリーを再実行しない
- サイクルが途中で止まった場合（Gate 4の差し戻し、`SPEC_CONFLICT`、試行回数の上限、チェックやサイクルレビューによる停止）も、そこまでの項目でステップ8の完了報告を出す
