# トレーサビリティマトリクスの再生成

`docs/rcid/traceability-matrix.md` の**マトリクス**表を、現時点のリポジトリの状態から
UC → 要件ID → 実装 → テストを再導出して作り直す。コミット単位の手動更新は、こうした表を
陳腐化させる原因になりやすいため、代わりに定期的に（`/review` 実行時やリリース前など）
一括再生成する運用とする。

## 対象範囲 — 書き換えるもの・触れてはいけないもの

| セクション | 扱い |
|---|---|
| `## マトリクス` | **表の中身をまるごと置き換える**（`F-001` / `UC-001` 等のプレースホルダー行を含む）— 追記ではなく置換 |
| `最終再生成日:` | 今日の日付に更新する |
| `## 変更追跡` | **絶対に触らない。** コードから再導出できない、承認済み変更の手動管理台帳である — 上書きすると履歴が失われる |
| それ以外の全セクション | そのまま残す（`RCID命名規則`、`ステータス定義`、`使い方`、`Maintenance`） |

`docs/product/use-cases.md` もこのスキルからは編集しない — ここでは入力として扱うだけであり、
変更するのはGate 2の管轄である。

## 実行前に

`docs/product/use-cases.md` に実質的な内容があるか確認する。まだテンプレートのプレースホルダー
のままであれば、そこで止めてその旨を報告する — その状態で再生成すると空の表になり、前回の
実行結果を上書きしてしまう。

## 手順

1. `docs/product/use-cases.md` の `### UC-XXX` 見出しと、その直後の `**Related requirement**` 行から、
   UC ID → タイトル → 要件ID を抽出する。
2. 各UCについて、リソース名での検索により実装ファイル・テストファイルを特定する。実際にアプリコード・
   テストがどこにあるかは `docs/ai-context/module-map.md` を参照する。名前だけで一致が曖昧な場合のみ
   ファイル内容を確認する。
3. `docs/rcid/traceability-matrix.md` に既にある定義に従ってStatusを割り当てる:
   - **Complete** — 実装と、実際の挙動を検証するFeature/Unitテスト（Policy/認可のみのテストは含まない）
     の両方が確認できた
   - **Partial** — 実装は存在するが、テストが未整備・間接的、または認可チェックのみにとどまる
   - **Not Found** — 実装・テストのいずれも見つからなかった
4. 再生成したマトリクスと `最終再生成日:` を書き込む。
5. 下記の出力形式で報告する。

## ガードレール

- **推測で一致させない。** UCが複数のファイルに該当しうる場合、あるいは別名で存在していて
  一致が確認できない場合は、確実な内容だけを行に記録し、残りは未解決リストに挙げる —
  自信満々な誤りは、認められた欠落より悪い。次にこの表を読む人はそれを信用してしまうため。
- ある行のStatusは「見つかったもの」についての記述であり、「あるべきもの」についての記述ではない。
  UCに書いてあるからといってCompleteとマークしてはならない。
- ここで見つかったギャップを埋めるために、実装ファイルやテストファイルを新規作成しない。
  ギャップは報告して止める — 不足しているテストを書くのは、独自のGate 4を持つ `/tdd` サイクルの仕事である。
- `docs/product/requirements.md` にあって対応するUCがない要件IDは、マトリクスではなく報告書に載せる。

## 出力形式

1. **サマリ** — 処理したUCの件数、Statusごとの件数
2. **ステータスの後退** — 前回の表からStatusが下がった行（例: `Complete` → `Not Found`）。
   これを最初に列挙する — 通常の原因はファイルのリネーム・削除、または一致検出が
   静かに機能しなくなったことであり、いずれもリリース前に把握しておく価値がある
3. **未解決** — 手順2で曖昧だった一致について、何が曖昧だったかとともに列挙する
4. **対応するUCがない要件ID**

リストが空の場合は、見出し自体を省略せずその旨を明記する。
