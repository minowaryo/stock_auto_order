# 体系的なデバッグ

非自明なバグは、直す前に調査する価値がある。これはその調査のための規律であり、些細な
1行のtypo修正にまで適用すべきチェックリストではない——明白で局所的な修正はそのまま行えばよい。

## 実装コードに触る前に

1. **まず再現する。** 何かを変更する前に、失敗する最小の再現手段（失敗するテスト、または
   症状を引き起こす正確なコマンド・入力）を用意する。まず失敗するところを見られない修正は、
   修正ではなく推測にすぎない。
2. **エラーは全文読む。** 症状の1行だけでなく、スタックトレース・ログ出力全体を読む。
   症状だけから原因を推測することは、目の前に既にある情報を読み飛ばすことになる。
3. **まず `docs/ai-context/known-pitfalls.md` を確認する。** ライブラリ・フレームワーク固有の
   既知の詰まりどころであれば、修正方法はすでに記録されている——一から導出し直さない。
4. **直す前に原因を切り分ける。** 何かを編集する前に、失敗を再現する最小の単位（関数・クエリ・
   コンポーネント）まで絞り込む。

## 修正を試みてもうまくいかないとき

- **1回失敗したら**: もう一度エラーを読み直す——その修正はエラーが実際に言っていたことに
  対応していたか、それとも自分が思い込んだ内容に対応していただけか？
- **2回失敗したら**: 推測での修正をやめる。今分かった「原因ではないもの」を書き出し、
  最初の2回が共有していた前提を見直す。
- **3回失敗したら**: それをバグではなく設計上の問いとして扱う。失敗しているテスト、あるいは
  現在のアプローチ自体が誤った前提を含んでいる可能性がある——4回目のパッチを書くのではなく、
  アプローチ自体を再検討する。

## 症状を隠してはいけない

テストのassertionを緩める、エラーを握りつぶす `try`/`catch` を追加する、警告を抑制する——
これらは修正ではない。失敗を解決せずに見えなくするだけであり、本リポジトリが本番コードに
既に適用している「起こり得ないシナリオへのエラーハンドリング追加禁止」という原則と矛盾する。

## 原因が分かったら

`.claude/rules/30-testing.md` のTDDサイクルに従う: まず再発防止テストを書き、今診断した理由で
（別の理由ではなく）失敗することを確認してから、修正を実装する。
