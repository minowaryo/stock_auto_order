# ADR-0002: NISA区分を含む口座区分の内訳保存

## Status
Accepted

## Date
2026-08-16

## Context

`docs/architecture/data-model.md`（Gate 3承認済み、2026-08-15）および`docs/product/use-cases.md` UC-001業務ルールでは、「楽天証券CSVの口座区分（特定口座/一般口座/NISA成長投資枠等）の内訳は保持せず、銘柄コード単位で数量を合算・取得単価を加重平均した結果のみ保存する」方針で確定していた。UC-001のCSV取込はこの方針でTDD Green（実装）まで完了している。

その後、利用者から売買判断ロジックへの要望が出た:

- **売り/リバランス**: NISA区分（NISA成長投資枠/NISAつみたて投資枠）で保有している銘柄は非課税メリットを維持したいため、利確シグナル（UC-004）・リバランス提案（UC-005）の対象にしたくない
- **買い**: 非常に強い確信＋中長期（5〜10年）保有が推奨できる新規投資候補（UC-008）については、NISA枠での購入を推奨してほしい

この判断を行うには、保有銘柄がNISA区分かどうか（または一部NISA区分か）をシステムが把握できる必要があるが、現行の方針では口座区分の情報がCSV取込時点で失われるため実現できない。

`docs/original-docs/`の実際の楽天証券CSVサンプル（JP株/US株/投資信託）を確認したところ、同一銘柄が複数の口座区分（特定口座とNISA成長投資枠など）にまたがって保有されている実データが存在することを確認した。

## Decision

CSV取込時に、口座区分ごとの内訳（数量・取得単価）を新テーブル`holding_snapshot_accounts`に追記保存する。

- 既存の`holdings`/`holding_snapshots`テーブルのカラムは一切変更しない（後方互換を維持する）
- 既存の「銘柄コード単位で合算・加重平均した値」は引き続き`holding_snapshots`に保存し続け、既存の画面・ロジックへの影響はない
- 新テーブルは`holding_snapshots`の子テーブルとして追加し、口座区分（`specific`/`general`/`nisa_growth`/`nisa_tsumitate`）ごとに1行を保存する
- 詳細なテーブル定義は`docs/architecture/data-model.md`を参照

data-model.md（line 11）が元々想定していた拡張方針「将来的に口座別内訳の確認ニーズが出た場合は別テーブル追加で対応する（既存カラムの変更は伴わない想定）」に沿った変更である。

## Rationale

- 別テーブルへの追記保存であれば、UC-001の既存実装（合算・加重平均のロジック）を変更せずに拡張でき、影響範囲を最小化できる
- 複数口座にまたがる同一銘柄の実データが存在するため、銘柄1件につき口座区分を1つしか表現できない設計は採用できない

### 採用しなかった代替案

- **手動フラグ方式**（銘柄ごとに本人がNISA区分を手動で設定する）: CSVの実態（同一銘柄が複数口座にまたがる、取込のたびに変動しうる）を反映できず、取込のたびに手動更新が必要になり運用負荷が高い。利用者からも「CSVから自動判定したい」との明確な意向があったため不採用
- **`holding_snapshots`に`account_type`カラムを追加する方式**: 1銘柄1口座区分しか表現できず、実データにある「同一銘柄が特定口座とNISA成長投資枠の両方に存在する」ケースを扱えない。また既存の`(snapshot_id, holding_id)` unique制約にも反するため不採用

## Consequences

### メリット
- 既存テーブル・既存ロジック（UC-001の合算表示、UC-002〜UC-009の既存動作）に影響を与えずにNISA区分を追跡できる
- 複数口座にまたがる保有の実態を正確に表現できる
- 利確シグナル・リバランス提案の精度が向上し、非課税メリットのあるNISA区分を誤って売却提案してしまうリスクを避けられる

### デメリット・リスク
- CSVパーサ（`JpStockCsvParser`/`UsStockCsvParser`/`MutualFundCsvParser`）の変更が必要。JP/US株CSVはセクション見出し（`■特定口座`等）、投資信託CSVは`口座区分`列の値と、口座区分の検出方式が異なるため実装がやや複雑になる
- `ImportCsvAction`の集計ロジックに、既存の合算処理に加えて口座区分別の内訳生成処理を追加する必要がある
- Gate 3で一度承認された決定を覆すため、再度データモデルのレビューが必要になる
