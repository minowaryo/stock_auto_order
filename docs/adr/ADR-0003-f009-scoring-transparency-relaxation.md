# ADR-0003: F-009サマリーレポートの合成スコアリング方針の緩和（部分的透明化）

## Status
Accepted

## Date
2026-08-21

## Context

`docs/product/requirements.md` 6章「制約・前提」100行目は、売買判断ロジック全体の設計方針として次のように定めていた。

> 個人投資家（本人）が根拠を目視で理解できるシンプルさを優先する。複雑な自動スコアリング・機械学習的な合成指標は用いず、個別のテクニカル/ファンダメンタルズ指標・市場全体指標をそれぞれ独立した参考情報として並べて提示する構成とする

同101行目は、この方針の例外としてF-009（取込後サマリーレポート）に限り、複数の簡易指標（含み益率・RSI・セクター配分状態・注目テーマ合致状況等）を組み合わせた合成スコアリングを許容し、「合成ロジックの詳細な計算過程・重み付けはユーザーに開示しないブラックボックスとしてよい」としていた。`docs/product/use-cases.md` UC-009業務ルール（478行目）、`docs/architecture/data-model.md`（325-357行目、`import_summary_reports`/`import_summary_report_items`テーブルの`composite_score`）もこの「非開示」前提で設計されており、いずれもGate 2/Gate 3承認済みだった。

レビューの中で、以下の指摘があった。

- F-009はCSV取込直後に最初に表示される、最も目立つ画面である
- その画面のヘッドライン（`portfolio_headline`）・主要レコメンドの根拠だけが「算出根拠非開示のブラックボックス」であることは、6章が掲げる「根拠を目視で理解できるシンプルさ優先」という設計哲学と矛盾するのではないか
- `link_to`で裏付け画面に遷移できる設計にはなっているが、レポート単体（ヘッドライン・一覧表示の時点）では根拠が一切わからない

この指摘を受けてユーザーと協議した結果、以下の考え方で合意した。

1. レコメンドの元になる基礎指標（含み益率・RSIなど個別指標）は、UC-003等と同様に今まで通りシンプルなまま独立して提示する（この部分は変更しない）
2. その基礎指標を横断的に組み合わせて分析・順位付けするロジック自体は、投資判断に役立つのであれば複雑にしてよい。「単純さ」を求めるべき対象は個別指標の提示方法であり、指標を組み合わせる分析ロジックの複雑さそのものではない
3. ただし各レコメンド項目（`reason_summary`）と全体感サマリー（`portfolio_headline`）には、判定の主要因となった代表指標を一言添える。これにより「結果だけ表示されて何も分からない」状態は解消する
4. `composite_score`の生の数値・詳細な重み付け計算式そのものは、引き続きユーザーへの表示対象外としてよい（完全な計算式開示までは求めない＝部分的な緩和にとどめる）
5. この考え方（基礎指標はシンプルに個別提示／分析ロジックは有用なら複雑でよい／出力には主要因を開示する）は、F-009固有の例外ではなく、プロジェクト全体の設計方針として6章に一般化して記載する

対象のUC-009（F-009）はPhase 1で未着手（`docs/rcid/traceability-matrix.md`にF-009の行が存在しない）のため、既存コード・既存テストへの影響はない。

## Decision

以下のドキュメントを改訂する。

- `docs/product/requirements.md` 6章（100-101行目）: 「F-009に限る例外」という書き方をやめ、①基礎指標は個別にシンプル提示する、②その上の分析・合成ロジックは投資判断に資するなら複雑でよい、③ただし出力（ヘッドライン・各項目の理由）には主要因を開示する、という3点をプロジェクト全体の一般原則として記載する。あわせて2章IN scope（38-42行目）のF-009関連記述も整合させる
- `docs/product/use-cases.md` UC-009業務ルール（478行目）: 合成スコアリング自体は内部ロジックとして許容しつつ、`reason_summary`と`portfolio_headline`の生成ルールとして「判定の主要因となった代表指標（1〜2件程度）を一言含める」ことを必須化する。出力テーブル（470-476行目）の該当項目の説明も更新する。`composite_score`の詳細な計算式・重み付けは引き続き非開示のままとする
- `docs/architecture/data-model.md`（325-357行目）: `import_summary_report_items.reason_summary`のコメント、および357行目の注記を「詳細な重み付け計算式は非開示だが、主要因はreason_summary/portfolio_headlineに含める」という趣旨に修正する。テーブル構造・カラム追加は不要（`reason_summary`の文字列内で表現するため）
- `docs/rcid/traceability-matrix.md`にCHG-0002として本CRを記録する（ADR-0002/CHG-0001と同じパターン）

## Rationale

- 「投資判断の規律化」というプロジェクトの目的（requirements.md 1章）にとって重要なのは、個別指標の計算方法が単純であることそのものではなく、**最終的にユーザーが提示された結論を検証・納得できること**である。基礎指標を独立提示しつつ、その上位に位置する横断的な分析ロジック（利確・リバランス・新規投資候補を横断した優先順位付け）は、複数のシグナルを統合する性質上、単一指標の閾値判定より複雑になるのは自然であり、そこを無理に単純化するとF-009自体の価値（ポートフォリオ全体を一目で把握する）が損なわれる
- 一方で、計算過程が完全に不可視だと「なぜこの順位か」が全く検証できず、6章の設計哲学（目視で理解できるシンプルさ優先）と乖離する。主要因（代表指標）を一言添えるだけで、ユーザーは`link_to`先の詳細画面に行く前に「妥当そうか」の一次判断ができるようになり、両立できる
- 完全な計算式・重み付けまで開示する必要はない。個人利用ツールであり、weightingの詳細を追う負担よりも「何が根拠か」の要旨が分かれば実用上十分というのがユーザーの意向である

### 採用しなかった代替案

- **例外規定を完全撤廃し、F-009も合成スコアリングを廃止する**: 各レコメンド項目に根拠指標を単純列挙する方式。透明性は最大化できるが、複数シグナルを横断した優先順位付けというF-009の中核価値（利確・リバランス・新規投資候補を一つのランキングで比較する）を実現しづらくなる。ユーザーからも「分析ロジック自体は有用なら複雑でよい」との明確な意向があったため不採用
- **現状維持（非開示のまま）**: 6章の設計哲学との矛盾がドキュメント上に残り続ける。プロジェクトの中核機能と位置づけられているF-009の方針として指摘を放置するのは適切でないと判断し不採用

## Consequences

### メリット
- 6章の設計哲学（根拠を目視で理解できるシンプルさ優先）とF-009の実装方針の矛盾が解消される
- ユーザーはヘッドライン・各レコメンド項目を見た時点で大まかな根拠を把握でき、`link_to`先での詳細検証と合わせて二段階で納得感を得られる
- 分析ロジック自体の複雑さは制約しないため、F-009が将来的に精度を上げる余地（優先順位付けロジックの改善）を残せる
- UC-009は未実装のため、既存コード・テストへの影響なく方針変更できる

### デメリット・リスク
- `reason_summary`・`portfolio_headline`の生成ロジックに「主要因の抽出・言語化」という追加の実装コストが発生する（単純な合成スコア計算だけでなく、どの指標が支配的だったかを特定するロジックが必要）
- 「主要因1〜2件」という開示粒度の線引きが曖昧になりやすく、Phase 1実装時（`/tdd`サイクル）で具体的な抽出基準を確定させる必要がある
- Gate 1（requirements.md）・Gate 2（use-cases.md）・Gate 3（data-model.md）で一度承認された内容を覆すため、3ドキュメントすべてで再度レビューが必要になる
