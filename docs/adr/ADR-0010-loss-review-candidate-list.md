# ADR-0010: 整理検討（含み損）候補一覧の新設

## Status
Accepted

## Date
2026-09-05（Gate 1: requirements.md 2026-09-05 承認 / Gate 2: use-cases.md UC-011 2026-09-05 承認 / Gate 3: data-model.md 2026-09-05 承認）

## Context

`docs/product/requirements.md` 2章OUT（53行目）は次のように定めている。

> 既存保有銘柄に対する**損切り判断・機械的なナンピン推奨・含み損銘柄の売却判断支援**。ただし押し目買いシグナル＋ファンダメンタルズ健全性フィルタの範囲に限り、買い増しタイミングの提示はF-010として対象とする（2026-08-23、ADR-0007）。新規投資候補に関しては、F-008の軽量レコメンド（注目テーマ合致＋財務健全性フィルタ＋小口の購入額目安）の範囲に限り対象とする

F-010（買い増しタイミングレコメンド）のバックエンド・フロントエンドが完結し、`docs/product/accuracy-improvement-backlog.md` に「F-010開発完了後に着手判断」として持ち越されていた次の項目の着手タイミングとなった。

> **整理対象（損切り）候補一覧**: 含み損×長期保有×ファンダ不健全×回復兆候なしの銘柄を機械的に足切り提案する、UC-004（利確検討）の鏡像機能

### 現状の機能空白

`/signals` 画面は「買い増し候補（UC-010）」「利確検討（UC-004）」の2段構成。含み損の銘柄に対する判断支援は UC-010（押し目買い）のみで、UC-010 は Addendum（ADR-0007、2026-08-23）で「健全で好調だった銘柄が市場全体・セクター全体の調整で一時的に下げた場面」だけを拾うよう、7シグナル共通の前提条件（直近13週以内の `week52_high` -15%以内到達、`relative_strength_vs_market` -5pt以上）を課している。

その結果、**押し目シグナルもファンダ健全性も満たさない「深い含み損で長期低迷している銘柄」は、`/signals` のどのセクションにも現れない**。UC-004 は含み益+20%超のみ、UC-002 保有銘柄一覧は含み益率を出すだけで整理の判断材料を提示しない。本人からの要望は「一番判断に困っている（＝早く足切りしたい）銘柄が一番情報が少ない」この空白を埋めることにある。

### 本人が求めているのは「踏ん切り」

本人の言葉:「めちゃくちゃ損益が出ているやつを早く足切りしたい。足切りするための**踏ん切りをつけたい**。そのための情報が分かっている状況を作りたい」

したがって本機能の価値は「機械が損切りを指示する」ことではなく、「まだ戻るかも」という保有継続バイアスを断ち切るための客観的な数字（復帰に必要な上昇率・含み損の実額・塩漬け期間・投資根拠の毀損・下げ止まり兆候の不在）を一覧で見せることにある。`requirements.md` 1章「意思決定支援に徹する。最終判断は本人が行う」の方針をそのまま踏襲する。

### 既存資産の状況

- 必要な指標（`holding_snapshots.unrealized_gain_amount`／`ma75`／`technical_indicators.week52_low`／`relative_strength_vs_market`／`macd`／`macd_signal`）はいずれも算出・保存済みで、追加の外部データ取得は不要
- 判定チェックリスト表示（`SignalCriteriaEvaluator`、CHG-0007）・共有テーブルコンポーネント（`signal-table-colgroup`／`signal-table-head`／`signal-criteria-cells`／`signal-criteria-summary-badges`）・財務健全性評価（`FundamentalHealthEvaluator`）・ポートフォリオ評価総額（`PortfolioEvaluationCalculator`）が既に存在し流用できる
- 楽天証券CSVに取得日が含まれないため、正確な保有期間は取得できない。`snapshots`／`holding_snapshots` の連続出現週数からの推定で代替する

### 本人と合意したスコープ（2026-09-05）

| 論点 | 決定 |
|---|---|
| スコープ | **一覧＋判断材料の提示のみ**。分割売却の指値提案は行わない |
| UC-009 サマリーレポートへの統合 | **しない**。`/signals` 画面のみ・**DBスキーマ変更なし** |
| 推定保有期間 | **観測以来の連続保有週数のみ**（MVP）。`holdings` への取得日カラム追加・手動上書きは今回入れない |

## Decision

以下を決定する。

- **D1**: `requirements.md` 2章OUT（53行目）を分割改訂する。「損切り判断・機械的なナンピン推奨」および「自動売却」は引き続きOUTのまま維持し、「**含み損銘柄について、一覧表示による整理（売却検討）の判断材料を提示すること**」をINへ移し、新機能 **F-011** として追加する。指値提案・自動発注・ナンピン推奨は含めない
- **D2**: 判定・抽出は**表示レイヤー（Action層）で完結**させる。新テーブルは作らず、`FetchExternalMarketDataAction` のシグナル判定・永続化には一切手を入れない（CHG-0006「利確検討ラインの動的分岐」と同じ方式）。`signals`／`buy_signals` テーブルも不変。**DBマイグレーションなし**
- **D3**: 新設 `app/Actions/Signal/ShowLossReviewListAction` が対象抽出・行組み立て・ソートを担う。既存の `ShowSignalListAction`（UC-004）・`ShowBuySignalListAction`（UC-010）には手を加えない
- **D4**: 対象抽出は「直近スナップショットの個別株のうち `unrealized_gain_rate <= -20%`（**整理検討ライン**、叩き台）」。`FundamentalHealthEvaluator` が `failed` の銘柄も**除外せず表示する**（UC-010 とは逆。ファンダ毀損は整理の後押し材料であり、隠すと本機能の意味がなくなるため）
- **D5**: 判定チェックリストは `SignalCriteriaEvaluator::evaluateLossReview()` を新設して構築する。既存の `classify()`・`row()` は再利用し、`evaluateTakeProfit()`／`evaluateBuy()` は無改修。財務3項目は判定の向きを反転させるため `fundamentalRows()` に反転フラグ（`$forLossReview` 相当）を追加する（詳細は D6）。**新規閾値は3つのみ**（整理検討ライン -20%／52週高値からの下落率 -30%／押し目買いシグナル 0 件）で、いずれも `app/Services/Analysis/LossReviewThresholds` に `public const` として単一ソース化する（CHG-0005 型の二重管理を防ぐ既存方針）。残りの項目は既存の確定済み閾値をそのまま可視化する
- **D6**（2026-09-06 改訂）: **整理検討テーブルの判定チェックリストは「赤の単一極性」で表示する。** テクニカル7項目・財務3項目のいずれも「整理を後押しする事実が成立している」状態を `met`（赤チップ）とし、そうでない状態は `unmet`／`unavailable`（グレー）とする。**このテーブルに緑チップは出さない**（利確検討・買い増し候補テーブルの緑/琥珀チップとの視覚的混同を避け、「テーブルが赤いほど切る材料が揃っている／全部グレーなら切る理由がない」と一目で読めるようにする）。
  - このため財務健全性3項目（ROE／自己資本比率／成長率）は UC-004/UC-010 とは**判定の向きを反転**させ、「基準割れ（＝投資根拠の毀損）」を `met`（赤）とする。閾値の値そのもの（ROE 10%／自己資本比率 40%／成長率 0%）は `FundamentalHealthEvaluator` の既存定数を流用し新設しない。健全な財務は `unmet`（グレー）で表示し、実測値（例「ROE 15.2%」）はチップ内に見せる
  - 「まだ売らなくてよい（保留材料）」の情報は、(a) 赤チップが少ない＝切る理由が薄い、(b) `fundamental_status`（`passed`/`unavailable`/`failed`）列＋`fundamental_summary`、(c) `loss_review_reason_summary` の散文（「財務は健全なため一旦保留も可」まで言い切る）——の3経路で担保する
  - 当初案（2026-09-05、D6 初版）は「財務3項目は UC-004/UC-010 と同一で、達成＝健全＝まだ売らなくてよい、の保留材料。別グループの見出しで明示」だったが、1テーブル内でテクニカルの緑（＝売り後押し）と財務の緑（＝保留）が正反対の意味になり、サマリバッジ「技術◯/7・財務◯/3」が「合計◯/10＝売り確定」と誤読される懸念が実装レビューで判明したため反転案に変更した
  - サマリ（`x-signal-criteria-summary-badges` 相当）の文言も「◯/7 達成」→「整理シグナル ◯/7 点灯」、財務側は「投資根拠の毀損 ◯/3」とし、テクニカルと財務の分子を足し算で読ませない。集計はテクニカルと財務で分けたまま
  - 利確検討（UC-004）・買い増し候補（UC-010）テーブルのチップ配色・`fundamentalRows()` の既定挙動は不変（反転はフラグ指定時のみ）
- **D7**: 押し目買いシグナル（`buy_signals`）が発生している銘柄は**除外しない**。一覧に含めたうえで「押し目買いシグナル発生中・買い増し候補にも掲載」と明示し、ソートで最後尾に回す。「切れ」と「買え」を矛盾提示しないための順序制御であって、情報の抑制はしない
- **D8**: 並び順は透明なマルチキーソートとし、F-009 の非開示合成スコアは用いない（ADR-0007 D の踏襲）。キー順: ①押し目シグナルなし→あり ②財務状態 `failed`→`unavailable`→`passed` ③整理テクニカル該当数の多い順 ④含み損率の深い順
- **D9**: 推定保有期間は新設 `app/Services/Portfolio/ContinuousHoldingWeeksCalculator`（純粋計算）で、対象銘柄が直近スナップショットから連続して何週分の `holding_snapshots` に出現しているかを数える。最古スナップショットまで連続していた場合は `is_truncated` を立て「N週以上（観測開始まで遡及）」と表示する。`holdings` テーブルへのカラム追加はしない
- **D10**: 画面は `/signals` 最下部の第3セクション「整理検討（含み損）」とする。独立タブは設けない（`ui-guidelines.md` のタブ数方針を維持）。シグナル種別バッジは `variant="danger"`（赤）とし、既存の配色規約（買い=success緑／利確=warning琥珀）に整理=danger赤を追記する
- **D11**: UC-009 取込後サマリーレポートへの統合は今回のスコープ外。`ShowImportSummaryReportAction` の `composite_score` には手を入れない

## Rationale

- **表示レイヤー完結（D2）**: CHG-0006 が「利確検討ラインの動的分岐」を `signals` テーブルに触れず表示レイヤーだけで実現した先例がある。本機能も対象抽出条件（含み損率＋既存指標）が時点データではなく現在値から機械的に決まるため、永続化する必然性がない。テーブルを増やさなければ `FetchExternalMarketDataAction` の再判定サイクル・UC-004/UC-010 の抽出クエリ・UC-009 のスコアリングという既存の3系統に一切影響しない
- **ファンダ `failed` を隠さない（D4）**: UC-010 は「健全な銘柄だけ買い増し対象にする」ため `failed` を除外するのが正しいが、整理検討は逆に「投資根拠が崩れている」ことこそ足切りの最大の後押し材料。ここで `failed` を隠すと本機能の中心的価値が失われる
- **押し目シグナル併発銘柄を除外しない（D7）**: 深い含み損かつ押し目シグナルありは最も判断に迷う場面。UC-010 のように単純除外すると「買い増し候補には出るが整理候補には出ない」という非対称が生まれ、本人が全体像を掴めなくなる。一覧に残したうえで順序と注記で「切る前に買い増し検討側も見ろ」と誘導するほうが誠実
- **合成スコアを使わない（D8）**: ADR-0007 D と同じ理由。ADR-0003 の透明性3原則の適用対象を増やさず、単純キーのソートで判断軸を可視化する
- **保有期間は推定のみ（D9）**: 楽天CSVに取得日がない以上、正確な保有期間はどうやっても出せない。`holdings.acquired_on` を足して手動入力させる案は、134銘柄すべてに手入力が必要で運用負荷が高く、MVP では割に合わない。観測以来の連続保有週数でも「塩漬けの度合い」の相対比較には使える。運用が続けば自然に情報が厚くなる
- **新規閾値を3つに絞る（D5）**: CHG-0007 が「既存の確定済み閾値を可視化するだけで新設しない」方針を採ったのに倣う。整理検討に固有で既存閾値を流用できないのは「どのくらいの含み損から対象にするか」「どのくらい高値から落ちたら毀損とみなすか」「反発の兆しの有無」の3点のみ

- **赤の単一極性（D6、2026-09-06 改訂）**: 判定チェックリストは CHG-0007 で「達成＝緑」の意味づけが定着している。整理検討テーブルでテクニカルの緑（＝売り後押し）と財務の緑（＝保留）を同居させると、同じ色が正反対を意味し、特にサマリバッジが誤読される。財務3項目を反転して「毀損＝赤」に揃えれば、テーブル全体が「赤＝整理を後押し／グレー＝そうでない」の1軸になり、`unmet` をグレーに保つことで全セルが原色になる読みづらさも避けられる。UC-004/UC-010 の緑・琥珀チップは不変（反転は `fundamentalRows()` のフラグ指定時のみ）

### 採用しなかった代替案

- **`loss_signals` 新テーブルを作り `FetchExternalMarketDataAction` の再判定サイクルに乗せる**: UC-009 サマリーレポートに整理候補を載せるなら `composite_score` 組み込み＝永続化が自然だが、本人が UC-009 統合を今回スコープ外と決めたため、テーブルを作る便益がない。`signals`/`buy_signals` に続く3つ目の同型テーブルを増やすデメリットのほうが大きい
- **独立した「整理検討」タブを新設する**: `ui-guidelines.md` のタブ数上限方針（5〜6個程度、現在6個）に抵触する。UC-004 の鏡像機能である以上、同じ「売買シグナル」画面に並べるのが自然
- **`holdings.acquired_on` を追加して正確な保有期間・機会損失を出す**: D9 の Rationale の通り、MVP では運用負荷に見合わない。将来 `accuracy-improvement-backlog.md` の項目として再検討可能
- **損切りラインを機械的に「-20%で売れ」と指示する**: `requirements.md` 1章「固定ルールで売買を自動判定しない／意思決定支援に徹する」に反する。判断材料の提示に留める
- **含み損銘柄も UC-004 の対象に含めて1テーブルで扱う**: UC-004 は「利確」、本機能は「整理（損切り検討）」で判断の向きが逆。チェックリストの項目も逆向き。1テーブルに混ぜると `signal_reason_summary`・並び順・空状態メッセージが破綻する

- **財務3項目を「健全＝緑＝保留材料」のまま別グループ見出しで表示する（D6 初版）**: 1テーブル内で緑が「売り後押し」と「保留」の両方を意味することになり、見出しの注記だけでは弱い。実装レビューで誤読リスクが具体的に判明したため反転案（毀損＝赤）に変更した
- **全テーブル（利確／買い増し／整理）を緑・赤の両方を出す共通配色に統一する**: `unmet` も着色することになり全セルが原色化して読みづらい。「効いている状態だけ着色・残りはグレー」という CHG-0007 の設計が崩れる。テーブルごとに `met`/`near` の色相を変える（買い＝緑／利確＝現状維持／整理＝赤）+ 残りグレー、で十分に統一感が出る

## Consequences

### メリット

- DBスキーマ変更なし・外部データ取得追加なし。既存の指標・共有コンポーネント・評価クラスの流用で完結する
- 既にGreen・マージ済みの UC-004（`ShowSignalListAction`）・UC-010（`ShowBuySignalListAction`）・UC-009（`ShowImportSummaryReportAction`）への改修が一切発生しない（CHG-0006 と同じ性質）
- `/signals` が「買い増し候補／利確検討／整理検討」の3段構成になり、保有銘柄に対する売買判断支援が含み益・含み損の全域をカバーする

### デメリット・リスク

- Gate 1（requirements.md）・Gate 2（use-cases.md）・Gate 3（data-model.md）で一度承認された OUT スコープを覆すCRのため、3ドキュメントで再レビューが必要（ADR-0007 と同じ手続きコスト）
- 整理検討ライン -20%・52週高値-30% は**バックテストを経ていない叩き台**。実データで件数が多すぎ/少なすぎる場合は Gate 3 の数値を調整する（`accuracy-improvement-backlog.md`「シグナル閾値のキャリブレーション」と同じ扱い）
- 推定保有週数は現状の取込回数（3回）ではまだ情報量が薄い。画面の注記でその旨を明示する必要がある
- `SignalCriteriaEvaluator` に3つ目の `evaluate*()` メソッドが増え、クラスがやや大きくなる。ただし共通ヘルパ（`classify()`・`row()`）を共有できる利点のほうが大きい。`fundamentalRows()` は反転フラグ分岐が入るが、既定挙動（UC-004/UC-010）は不変
- 判定チェックリストのチップ配色が「全テーブル共通で達成＝緑」から「テーブルごとに `met`/`near` の色相が変わる（買い＝緑／整理＝赤）」に変わる。`criteria-chip` に `tone` 相当の prop 追加と `ui-guidelines.md` の配色規約改訂が必要（利確検討テーブルは現状維持）
