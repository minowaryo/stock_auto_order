# ADR-0014: ポートフォリオ分類ダッシュボード（減らす／保つ／増やす）

## Status

Proposed（Gate 1: requirements.md / Gate 2: use-cases.md UC-013 の承認をもって Accepted とする。第1段階は DB スキーマ変更を伴わないため Gate 3 は影響範囲確認のみ）

## Date

2026-09-08

## Context

### 本人の要望

これまで積み上げてきた売買判断支援機能（UC-004 利確検討 / UC-005 セクター配分 / UC-010 買い増し候補 / UC-011 整理検討 / UC-012 ウォッチリスト）は、いずれも「条件 X に合う銘柄はどれか」という**縦割りの一覧**である。本人の要望は、これらを**銘柄起点**に束ね直し、次を1画面で把握できるようにすること:

1. 保有銘柄それぞれが「利確・リバランス検討 / 整理検討 / 買い増し検討 / キープ / 新規購入検討」のどれに当たるか（本人の言葉。実質は「減らす / 保つ / 増やす」の3分類）
2. ポートフォリオ評価額の何%がどの分類に入っているか（全体感）
3. 「積立・長期保有（ガチホ）を核70〜80%、残り20%でアクティブに新規売買」という運用像を数値で確認できること
4. （将来）先週から今週で、ある銘柄がどの分類からどの分類へ動いたか（遷移＝シグナル）

### なぜ今できないのか

- 各 UC の抽出 Action（`ShowSignalListAction` / `ShowBuySignalListAction` / `ShowLossReviewListAction` / `SectorAllocationCalculator`）は独立に走り、**同じ銘柄が複数の一覧に載ってよい**設計。一覧内の並びはソートキーで解決しており、「1銘柄がちょうど1つの分類に属する」というモデルを必要とした画面が存在しない
- そのため「分類が複数該当したときどれを採るか」の優先順位ルールがコードにない（あるのは ADR-0007 の「利確シグナル成立時は買い増し対象外」というペア1本だけ）
- 「キープ」に相当するバケツはどの画面にもなく、`ListHoldingsAction`（UC-002 保有一覧）が全銘柄を等価に並べているだけ
- 遷移（先週→今週）を出すには先週の分類が必要だが、`technical_indicators` / `fundamental_indicators` は `holding_id` 1:1 キャッシュで履歴を持たない（`signals` / `buy_signals` はスナップショット紐付けで履歴あり）

### 段階を分ける理由

分類の定義・優先順位・「キープ」の線引きは、本人の投資スタイルに合わせて運用しながら調整するもの（`accuracy-improvement-backlog.md` の「シグナル閾値のキャリブレーション」と同種の性質）。永続化を先に作ると、定義を変えるたびに過去スナップショット分の再計算・整合が問題になる。まず**表示のみ**を数回の週次取込で回して分類が直感に合うことを確認し、そのうえで永続化層（遷移表示・トレードジャーナル）を設計する。

## Decision

### D1. requirements.md 4章に F-013 を新設する

- 4章に **F-013「ポートフォリオ分類ダッシュボード」**（Phase 2、優先度 中）を追加
- 2章 IN に「保有銘柄を『減らす / 保つ / 増やす』に分類し、評価額構成比とあわせて俯瞰表示する」を追加。**新しい抽出ロジック・新しい閾値は設けず、既存 UC の抽出条件を再投影する**旨を明記
- 7章のフェーズ計画に F-013 の位置づけ（F-012 完成後、表示レイヤー完結の第1段階）を追記

### D2. バケツは既存 UC の抽出条件の再投影であり、新しい判定ロジック・閾値を作らない

| バケツ（`bucket`） | 大分類 | 所属条件（既存の再利用） | 供給元 |
|---|---|---|---|
| `core_accumulation`（積立・インデックスコア） | 保つ | `instrument_type` が ETF / 投資信託、または保有が NISAつみたて投資枠のみ | `holdings` / `holding_snapshot_accounts` |
| `loss_review`（整理検討） | 減らす | UC-011 の対象抽出条件（含み益率 ≤ 整理検討ライン。叩き台 -20%） | `ShowLossReviewListAction` |
| `take_profit`（利確検討） | 減らす | UC-004 の対象抽出条件（含み益率 > 動的利確ライン、かつ シグナルあり or 高水準モード該当） | `ShowSignalListAction` + `TakeProfitThresholdEvaluator` |
| `add_on`（買い増し検討） | 増やす | UC-010 の対象抽出条件（押し目買いシグナルあり ＋ 財務 passed/unavailable ＋ 共通前提） | `ShowBuySignalListAction` |
| `hold`（キープ） | 保つ | 上記いずれにも該当しない個別株（JP/US） | 補集合 |
| `new_entry`（新規購入検討） | 増やす | UC-012 ウォッチリストの未保有銘柄（**評価額%の分母・分子に含めない**。参考リンクのみ） | `ShowWatchlistAction`（F-012） |

- 対象はJP株・US株の個別株と、保つ側の ETF・投資信託。CFD は対象外（`instrument_type` 対象外、UC-002 準拠）
- 新規に定義するのは `core_accumulation` と `hold` の線引きのみ（数行）。残りは「UC-X の抽出条件をそのまま使う」

### D3. 各保有銘柄はちょうど1つのバケツに入る。優先順位（開示された全順序）で排他解決する

叩き台の全順序（上が優先）:

1. `core_accumulation`（`instrument_type` / 口座区分で最初に確定。以降の判定対象外）
2. `loss_review`
3. `take_profit`
4. `add_on`
5. `hold`

競合の扱い:

| 競合 | 発生条件 | 叩き台の解決 |
|---|---|---|
| `loss_review` × `add_on` | 含み益率 ≤ -20% かつ 押し目買いシグナルあり（財務健全な急落銘柄） | `loss_review` を採用し、行に「押し目買いシグナル発生中・買い増し候補にも掲載」注記（UC-011 の既存挙動と同一）。**★本人判断ポイント**: コア/アクティブの銘柄タグ導入後は銘柄の役割で分岐させる余地 |
| `take_profit` × `add_on` | — | 発生しない。ADR-0007 で「利確シグナル成立時は買い増し対象外」として既に排他 |
| `take_profit` × `loss_review` | — | 発生しない。含み益と含み損は同時に成立しない |

- 「落ちなかったバケツ」は行内の注記バッジで見せ、情報自体は隠さない（UC-011 の「買い増し候補にも掲載」注記が先例）

### D4. リバランス（セクター偏り）は個別銘柄のバケツを動かさない。セクター単位の警告として別表示する

- UC-005 は元々セクター単位の設計で、個別銘柄に per-stock で「売る／売らない」を割り当てる仕組みを持たない（売却額目安もセクター単位）
- 偏り警告セクターの全銘柄を「減らす」に落とすと、例えば AI 関連8銘柄が偏り警告→8銘柄すべて「減らす」となり、直感とも UC-005 の売却額目安（セクター単位）とも整合しない
- 叩き台: 偏り警告セクターに属する `hold` / `take_profit` 銘柄の行に「偏り警告セクター」バッジを付す。ダッシュボード上部に UC-005 の `allocation_status` を要約したセクター偏りサマリを併置する
- **★本人判断ポイント**: 当初要望の「利確・リバランス検討を1つの塊で見たい」との折り合い。バッジ＋セクターサマリで足りるか、「減らす」の中に `rebalance` サブバケツを立てるか

### D5. 「キープ」は残余だが、簡易ヘルスラインを必ず表示する。「要観察」サブフラグは第2段階

- `hold` = 減らす／増やす／積立コアのいずれにも非該当。ただし空バケツ扱いにせず、各行に簡易ヘルスライン（含み益率・RSI 帯・財務 passed/failed・相対力〔対市場〕の符号）を表示する
- 第2段階で `hold_watch`（要観察）: 財務 failed／相対力が継続マイナス／含み益率が整理検討ライン手前まで悪化、等で `hold` から昇格。整理検討に落ちる前の早期警戒層
- **★本人判断ポイント**: 要観察を第1段階から出すか、第2段階に回すか

### D6. 3分類の構成比は評価額（`market_value`）ベースで算出する

- 各バケツの `Σ market_value ÷ 全保有 Σ market_value`。`market_value`（保有数量 × 現在値、US株は円換算済み、投信は評価額）は CHG-0011 で `ShowSignalListAction` / `ShowBuySignalListAction` に実装済みの算出を流用する
- 基本は全口座ビュー。課税口座のみビュー（減らす系アクションの実対象）は第2段階
- 「保つ」は内訳（`core_accumulation` / `hold`）を明示する。積立コア比率が直接見えることで requirements.md 1章の「積立・長期保有（ガチホ）」の可視化になる
- `new_entry`（未保有）は分母・分子どちらにも含めない

### D7. 20%アクティブ枠の予算トラッキングは第2段階（現金ポジション入力が必要）

- 「積立コア70〜80% / 残り20%でアクティブ売買」を数値で支えるには、アクティブ枠の目標額・投下済み額・余力の3値が要る
- 投下済み額は保有側の `market_value` から定義できるが、余力の分母（預り金・買付余力）は楽天証券の保有 CSV に含まれず別入力が必要（requirements.md 2章 OUT「預り金等の取込」に抵触するため、やるなら別CR）
- 第1段階は「保つ」の内訳表示（積立コア vs キープ）に留め、枠の残量計算は入れない
- **★本人判断ポイント**: アクティブ枠トラッキングを別CRで追うか

### D8. 段階リリース。第1段階は表示のみ（永続化なし）、第2段階で週次分類の永続化＋遷移表示

- **第1段階（本CR / F-013 / UC-013）**: `ClassifyHoldingsAction`（純ロジック、DB 書き込みなし）＋ サマリーレポートタブ上部の「分類俯瞰」セクション。直近スナップショットのみを分類する。CHG-0006 / CHG-0010 と同じ「表示レイヤー完結・DB スキーマ変更なし」
- **第2段階（別CR、F-013 の運用実績を見てから）**: `portfolio_classifications`（`holding_snapshot_id` FK、`bucket`、`reason`、`decided_at`）を取込時（UC-001 のフロー）に書き込み、「先週→今週の異動（どの銘柄がどのバケツへ動いたか）」の遷移表示と、シグナル→その後の値動きを突き合わせるトレードジャーナルを追加する
- 理由: Context「段階を分ける理由」の通り

### D9. 画面はサマリーレポートタブ（UC-009）に「分類俯瞰」セクションを追加する形で提供する。新タブは作らない

- `ui-guidelines.md` のタブ数上限（6個、現在6個）
- サマリーレポートタブは既に「最新取込に基づく・いつでも見られる・開くたび再計算」という性質を持ち、分類俯瞰と土台が同じ（CHG-0008）
- 配置: タブ最上部（既存の `portfolio_headline` の直上または直下）に「分類俯瞰」セクション。3分類の構成比バー／「保つ」の内訳／セクター偏りサマリ／各バケツの銘柄リストで構成する
- UC-009 の非開示合成スコアによる上位10〜20件リストは当面併存させる
- **★本人判断ポイント**: 第1段階から UC-009 の top-10/20 リストを分類俯瞰に置き換えるか、併存させるか

## Rationale

- **再投影に徹する（D2）**: 新しい抽出条件・閾値を作ると、UC-004/010/011 と分類ダッシュボードで「どちらが正か」の二重管理が発生する。既存 Action の出力を束ねるだけなら、閾値変更が自動で分類にも反映される
- **優先順位は開示された全順序（D3）**: F-009 の非開示合成スコアではなく、UC-010／UC-011 が採用した「透明マルチキーソート」と同じ思想。どの銘柄がなぜそのバケツにいるかを本人が追える
- **リバランスをバッジに留める（D4）**: セクター単位の指標を per-stock バケツに機械的に展開すると、UC-005 の設計（セクター単位の売却額目安）と齟齬が出る。per-stock へ落とすには「セクター内でどの銘柄を削るか」の選定ロジックが別途必要で、それは本CRのスコープを超える
- **表示のみを先行（D8）**: 永続化は不可逆度が高く、分類定義の調整コストを上げる。CHG-0006／CHG-0010 で確立した「表示レイヤー完結で試す」パターンに乗せ、価値検証を先にやる
- **サマリーレポートタブに相乗り（D9）**: 新タブは `ui-guidelines.md` の方針違反。UC-009 タブは常設・再計算という土台を既に持ち、分類俯瞰の置き場所として最も自然

### 採用しなかった代替案

- **新規タブ `/portfolio` を作る**: タブ数上限（6個）に抵触
- **一回きりの分析レポートとして出力**: 本人が「常設・俯瞰」を要望。UC-009 タブが既に常設なのでそこに乗せれば新規導線は不要
- **偏り警告セクターの全銘柄を「減らす」に分類する**: D4 の Rationale 参照
- **第1段階から `portfolio_classifications` を永続化する**: D8 の Rationale 参照。分類定義が固まる前の永続化は再計算・整合コストを生む
- **合成スコアで1銘柄を1バケツに寄せる**: ADR-0003 が F-009 に限って許容した合成スコアリングを分類全体に広げることになる。UC-010／UC-011 の透明マルチキー方針（ADR-0007／ADR-0010）と逆行する
- **UC-002 保有一覧に分類列を足す**: 保有一覧は「全体把握」、分類ダッシュボードは「アクション優先度の俯瞰」で目的が異なる（`ui-guidelines.md`「目的が異なる一覧は無理に統合しない」）。UC-004 と UC-002 を別画面にした判断と同じ

## Consequences

### メリット

- ポートフォリオ全体を1画面で俯瞰でき、「今どこに何%あるか」「今週動くべき銘柄はどれか」が銘柄起点で読める
- 既存の抽出 Action（`ShowSignalListAction` / `ShowBuySignalListAction` / `ShowLossReviewListAction` / `SectorAllocationCalculator`）をロジック新規実装ゼロで流用する
- 表示レイヤー完結（DB スキーマ変更なし）のため、既に Green・マージ済みの UC-001〜UC-012 のロジックへの改修が発生しない（`ClassifyHoldingsAction` と サマリーレポートタブの Blade/Livewire 追加のみ）
- 段階リリースにより、永続化という不可逆な工事の前に「分類ダッシュボードは実際に役立つか」を数回の週次取込で検証できる

### デメリット・リスク

- 優先順位（D3）・キープの線引き（D5）・リバランスの扱い（D4）・UC-009 top-10/20 との関係（D9）に、本人の投資哲学に依存する判断が複数残る。Gate 2（use-cases.md）レビューで確定する
- 第2段階の遷移表示は `portfolio_classifications` テーブル追加＋ UC-001 の取込フロー改修が必要（別CR、Gate 3 の実質承認が要る）
- リバランスをバッジに留めたことで、当初要望「利確・リバランス検討を1つの塊で見たい」とズレる可能性（Gate 2 で調整）
- UC-009 の非開示 top-10/20 リストと分類俯瞰が同じタブに併存し、情報が一部重複する。将来的に分類俯瞰が top リストを置き換える方向は ADR-0003 の透明化方針とも整合するが、本CRでは踏み込まない
- `ClassifyHoldingsAction` が4つの既存 Action を呼ぶため、サマリーレポートタブの1回のレンダリングで実行されるクエリ本数が増える（個人利用・週次運用のためパフォーマンス影響は許容範囲。UC-009 が既に同種の集計をしている）
