# ADR-0017: シグナル結果の前向き記録と週次価格履歴の永続化

## Status
Accepted（2026-09-27、Gate 1〜3 本人承認。D8の画面配置は新ルート＋リンクで確定）

## Date
2026-09-27

## Context

本システムの全シグナル閾値（RSI70・PEG2.0/1.0・PER15・ROE10%・営業利益率10%・52週高値-15%等）は、ADR-0004 以来「叩き台」のまま運用されている。`docs/product/accuracy-improvement-backlog.md` は全体優先順位の1位に「シグナル閾値のキャリブレーション（トライアルの実績データがあれば着手可能）」を挙げているが、**実績データを貯める仕組みが存在しない**。

外部調査ベースの改善提言（`docs/original-docs/stock-auto-order-recommendations-detail.md` 提言3）は、これを最重要課題に位置づけた。理由は以下の3点。

1. 保有はAI・半導体に集中し実効ベット数は2〜5。`IR ≈ IC × √(実効ベット数)` より、シグナルを磨いても取り出せるアルファは小さく、**「どのシグナルが実際に効いているか」を測らないまま閾値を足し引きすると、ノイズに合わせたルール変更（過学習）になる**
2. 未決の論点（前提B〔対市場相対力〕の日米同一適用、営業利益率10%フィルタ、低ボラの導入、PEG山側ガードの方式）が、すべて「測れば決着する」問題である
3. `BACKGROUND.md` の要求「判断基準は本人が根拠を目視で理解できる、信頼できるもの」に対し、信頼は指標の知名度ではなく実績から来る

### 現物確認（2026-09-27、実DB・コード）

| 項目 | 実態 |
|---|---|
| `signals` / `buy_signals` | `FetchExternalMarketDataAction` が `holding_snapshot_id` 単位で削除→再作成。**過去スナップショット分は残る**（週次6スナップショット 2026-08-28〜09-20、各 signals 55〜65件・buy_signals 12〜31件）。ただし発生時点の株価・根拠値は保存していない |
| `watchlist_buy_signals` | `holding_id` 単位で上書き。**履歴なし** |
| 価格履歴 | `YahooFinanceChartClient` で週足104週を毎回取得し、指標算出後に破棄。`technical_indicators` は `holding_id` 1:1 のキャッシュ |
| 指数 | `MarketIndexClient` が nikkei225（`^N225`）・sp500（`^GSPC`）の週足を毎回取得し13週リターン算出に使用。`market_indicator_snapshots` にはスナップショットごとの1点のみ保存 |
| 分割調整 | `YahooFinanceChartClient` は `indicators.quote[0].close` を使用。実測（NTT 9432、2023-06-25 に25:1分割）で、分割前の週足も約161円＝**分割遡及調整済み**であることを確認。一方 `indicators.adjclose` は配当込みの調整値で `close` と別物（NTT で約9%差）。ファーストリテイリング 9983 は提言書が例示した2024-03の期間に Yahoo が分割イベントを返さず、未確認 |

### スコープの前提（2026-09-27 本人判断）

`requirements.md` 2章は「バックテスト機能」を OUT としている。本ADRは**前向き記録のみ**を扱い、蓄積した価格で過去時点の判定を再計算すること（バックテスト）は引き続き OUT とする。

## Decision

### D1 前向き記録のみ

週次の判定で実際に出たシグナルを、発生時点の根拠値とともに記録し、その後に実際に付いた価格で結果を測る。過去データを使った判定の再計算はしない。判定ロジック（`SignalDeterminationService` / `BuySignalDeterminationService`）には一切手を入れない。

### D2 週次価格履歴 `weekly_prices` / `index_weekly_prices`

- `weekly_prices`: `holding_id` × `week_date` で UNIQUE。`close`・`volume` を保存
- `index_weekly_prices`: `index_name`（nikkei225 / sp500）× `week_date` で UNIQUE。`close` を保存
- `FetchExternalMarketDataAction`（保有銘柄）・`RefreshWatchlistMarketDataAction`（未保有ウォッチリスト銘柄）が**既に取得している**104週系列を UPSERT するだけ。新規の外部APIコールは発生しない
- 取得のたびに系列全体を UPSERT（既存行も上書き）する。Yahoo 側で遡及調整が入った場合も、直近104週の範囲は常に最新の調整に揃う

### D3 シグナル発生記録 `signal_occurrences`

- 列: `holding_id`、`source`（`take_profit` / `buy` / `watchlist_buy`）、`signal_type`、`observed_week`（判定に使った系列の最終確定週）、`snapshot_id`（ウォッチリストは null）、`metrics`（JSON、発生時点の判定根拠値）、`created_at`
- UNIQUE(`holding_id`, `source`, `signal_type`, `observed_week`)。同じ週に再実行しても重複しない（`firstOrCreate` 相当）
- 既存の `signals` / `buy_signals` / `watchlist_buy_signals` の削除→再作成ロジックには**触らず**、各書き込み箇所の直後に追記するだけにする。既存画面（UC-004/010/011/012/013）の挙動は変わらない
- `metrics` に残す値: 終値、RSI、52週高値比、相対力（対市場・対セクター）、ma75_trend_rising、PER、PBR、PEG、ROE、自己資本比率、営業利益率、成長率（単年・3期平均）、配当利回り、財務健全性の判定結果。「なぜ出たか」を後から再現するため

### D4 結果は保存せず読み取り時に算出

- 評価期間は **+4週 / +13週 / +26週**（≒20 / 60 / 120営業日。価格データが週足のため週単位で持つ）。保有期間3か月〜1年に対し4週だけでは短すぎるため3本持つ
- 超過リターン = 銘柄リターン − 同期間の指数リターン（JP株は nikkei225、US株は sp500。`FetchExternalMarketDataAction` の13週相対力と同じ対応）
- 両端とも `weekly_prices` / `index_weekly_prices` の同一系列から取る。CSV由来の `holding_snapshots.current_price`（未調整の実株価）とは混ぜない
- 保存しないため後埋めバッチは不要。評価期間に達していない発生は「未到来」として集計から除く

### D5 分割調整の前提をテストで固定

- 前提: Yahoo `quote.close` は分割遡及調整済み・配当は未調整（上記実測）。指数（価格指数）も配当を含まないため、超過リターンは「配当を除いた価格ベース同士」の比較として一貫する
- `YahooFinanceChartClient` の回帰テストに「分割前後の系列が連続していること（NTT 9432 相当のフィクスチャ）」を追加し、前提が崩れたら検知できるようにする
- リターン計算は調整済み系列、株価水準の判定（単元金額等）は未調整価格、という使い分けを data-model.md に明記する

### D6 既存スナップショット分の移送（一度だけ）

- 既存スナップショットの `signals` / `buy_signals`、および現在の `watchlist_buy_signals` を `signal_occurrences` へ移送する Artisan コマンド `signal-outcomes:backfill` を用意する。`observed_week` は作成日時（ウォッチリストは `determined_at`）を**マニラ時間（Asia/Manila）に換算した日付を含むISO週の月曜**、`metrics` は null＝根拠値不明。INSERT IGNORE のため再実行しても重複せず、分析処理がリアルタイムに記録した行（根拠値あり）を上書きしない
- 日付判定の基準をマニラ時間とするのは、本人の生活圏の時刻に表示・日付判定を統一する方針（2026-09-27 本人指示。DBの保存はUTCのまま）による。JP株の週足は月曜0時JST（＝日曜23時マニラ）に切り替わるため、日曜23時台マニラ時間の取込だけはリアルタイム記録の週（翌週）と移送時の週（当週）が1週ずれうるが、移送は一度きりの処理であり許容する
- 価格は次回の取得（104週系列の UPSERT）で埋まるため、移送直後から +4週 の結果は計算できる

### D7 評価指標と判定基準を事前に固定する

データを見てから基準を決めると、都合のよい解釈を選ぶ余地が生まれるため、先に固定する。

| 区分 | 指標 |
|---|---|
| 主 | シグナル種別ごとの平均超過リターンと t値 |
| 副 | 的中率（超過リターンの符号が期待通りだった割合）、中央値、年次の符号の安定性 |
| 使わない | RMSE・決定係数（ノイズが支配的な対象で誤差指標を見ると判断を誤る） |

期待される符号: 買い系（`buy` / `watchlist_buy`）はプラス、利確系（`take_profit`）はマイナス（利確シグナル後に市場を下回るなら「売って正解」）。

| 判定 | 基準 |
|---|---|
| 機能している | 符号が期待通り、t値 > 2.0、かつ3年中2年以上で符号が一致 |
| 判断保留 | 発生30件未満、または有意でない |
| 機能していない | 符号が期待と逆、または年によって符号が反転 |
| 異常を疑う | 効果量が過大（平均超過リターンの絶対値が +4週で10%超／+13週で20%超／+26週で30%超）。成功ではなくバグ・リークを疑う。他の区分より優先して表示 |

「3年中2年以上」は蓄積が3年に達するまで判定できないため、それまでは最良でも「判断保留」または「機能している（暫定）」と表示する。

#### D7 改訂: 判定の標本は発生週（2026-10-03、CHG-0020 Cycle5）

- **発覚の経緯**: Cycle4 の実データ確認で、利確検討 `week52_high_pullback` の +4週が、8/24週に出た30件だけで「機能していない」（平均+4.22%、t=2.38）と判定された。同じ週に出たシグナルは同じ相場の動き（その4週間の市場全体の上げ下げ）に一緒に左右され、互いに独立しない。発生1件を1標本としてt値を計算すると、相場1回分が30回分に数えられ、t値が過大になる
- **対策A**: 平均超過リターン・t値・判定区分は、発生週ごとに超過リターンを平均した値を1標本として求める。中央値・的中率は「何件中何件当たったか」の実感に合わせ、個々の発生の値のまま表示する
- **対策B**: 判断保留を抜ける条件に「結果が出た発生週が評価期間の3倍以上（+4週は13週〔最低13週〕、+13週は39週、+26週は78週）」を加える（従来の「結果到来30件以上」と併用）。当初は一律13週を提案したが、+13週・+26週では連続する週の評価期間がほぼ重なり、13週分そろっても相場局面としては1〜2回分にしかならないため、どの期間でも重なりのない局面を約3回分見てから判定する形にした（2026-10-03 本人選択）。代償として +26週の判定は早くても約2年後になる
- **残る限界**: +13週・+26週では連続する発生週の評価期間が重なるため、週平均どうしも完全には独立しない。重なりを補正する手法（Newey-West 等）は、個人が判定理由を目視で理解できることを優先して採用しない。判定は控えめに読む前提とし、閾値変更の判断は本人が個別発生の展開表示も見て行う（UC-014 の業務ルールどおり、自動では変えない）

### D8 表示

シグナル種別 × 評価期間の集計表（発生件数・結果到来件数・平均超過リターン・t値・的中率・中央値・判定区分）を1画面に出す。**配置は新ルート `/signal-outcomes` とし、売買シグナル画面（`/signals`）の上部からリンクする**（2026-09-27 Gate2で本人確定）。グローバルナビのタブ数6（`docs/product/ui-guidelines.md`）は維持し、既存の横に広いテーブル画面をさらに長くしない。2026-10-03（CHG-0020 Cycle5）、行き来しやすくするため上部のリンクを「売買シグナル｜シグナル検証」の切替タブに置き換えた（ADR-0021 D5 のセクター配分｜集中度と同じ形）。

## Rationale

- **前向き記録のみにした理由**: バックテストは「当時取得できたデータだけで判定を再現する」ことが難しい（財務データの開示日基準、12週遅延、`financial_statements` の保存期間など）。前向き記録なら判定時点の実データがそのまま残るため、先読みのバイアスが構造的に入らない。代償は結果が出るまで時間がかかることで、そのため D6 で既存6週分を移送し早く始める
- **結果を保存しない理由**: 保存すると後埋めバッチ・再計算・整合性管理が必要になる。数百銘柄×週次の規模なら読み取り時の計算で足りる
- **既存シグナルテーブルを変えない理由**: 削除→再作成をやめて履歴化する案もあるが、UC-004/010/011/012/013 の抽出クエリすべてに「最新週のみ」の条件を足す必要が生じ、回帰リスクが大きい。追記専用の別テーブルなら既存画面に影響しない
- **採らなかった案**: `signal_outcomes` に結果を保存する案（上記の理由）、日足の取得（新規APIコール増・週次運用に不要）、TOPIX をベンチマークにする案（現状取得していないため。日経225で開始し、必要なら後で追加）

## Consequences

- 新テーブル3つ。既存テーブルの変更なし（追加のみの低リスクなマイグレーション）
- 結果が統計的に意味を持つまで時間がかかる（+26週の結果は最短でも2027年3月以降、30件以上の蓄積も種別によっては数か月〜1年）。それまで集計表は大半が「判断保留」と表示される。これは想定どおりで、単年・少数での閾値変更を抑止する働きも持つ
- ウォッチリスト銘柄（未保有）も `watchlist_buy` として同じ仕組みで測れる
- 後続（`accuracy-improvement-backlog.md` 候補O 集中度ダッシュボード、候補N エクスポージャー管理、CHG-0021 PEG山側ガードの効果測定、候補A ファンダ週次スナップショット）は `weekly_prices` を前提にできる
- `weekly_prices` の行数は概算で 約220銘柄（2026-09-27時点の`holdings`の個別株、保有＋ウォッチリスト）× 104週 ≒ 2.3万行から開始し、週あたり約220行ずつ増える。個人利用の規模では問題にならない
