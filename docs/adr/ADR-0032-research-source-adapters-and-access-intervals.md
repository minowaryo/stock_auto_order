# ADR-0032: 情報源の形式別解析と源固有のアクセス間隔

## Status
Accepted（2026-10-11、本人。「承認してFDAのGreen実装へ進む」により本設計補足と追加Red31件を承認）

## Date
2026-10-11

## Context

[ADR-0031](ADR-0031-research-source-startup-check.md)はRSS/HTML/fileを設計したが、稼働中はRSS/Atomだけを解析する。FDAの公式CSVとNEDOの実HTMLを確認したので、未対応の形式を追加する。新規企業の発見への実用性からFDA→NEDO→YouTubeの順で着手する（[計画](../product/megatrend-source-implementation-plan.md)）。

FDAの[robots.txt](https://www.fda.gov/robots.txt)は一般UAにCrawl-Delay 30を指定する。ADR-0031の源間1.5秒と週1回だけでは、forceによる短時間の再アクセスを制限できない。FDAのCSVの決定日は公開日と異なり、公開日への流用も避ける。

## Decision

1. 既存取得層のストリーム/サイズ/接続・応答15秒/専用DBロック/全体120秒を共用し、応答をsource_keyとmethodに対応する解析器へ渡す。Cycle 1はS10/fileのFDA CSVだけを追加する。RSS/Atomの既存パーサは継続し、未知の形式を成功0件と扱わない。
2. S10の設定URLは公式のCSV直URL。既存の紹介ページURLをCSVとして読み込まない。1源1リクエストで個別資料・PDF・動画は追取得しない。Acceptは取得方式に合わせる。DB・画面構造の変更なし。
3. FDAの6列を解釈し、企業/製品/申請番号と「決定 YYYY-MM-DD」が分かる表示用題名（既存フォームに合わせ255文字以内）、型別の公式FDAデータベースURL、4KB以内のmetadataへ保存する。長い企業/製品名は題名だけで省略できるが、申請番号と決定日は残す。metadataのキーは`company`, `device_name`, `submission_number`, `date_of_final_decision`, `review_panel`, `product_code`。決定日はYYYY-MM-DDとし、`published_at`はNULL。決定日を発見経路の投稿日や元発表日に代入しない。元フィールドを省略すると4KB以内に収まる場合も、FDAの必須metadataを黙って切らず、源全体の失敗とする。既存RSSの任意metadataの扱いは変更しない。
4. 初回は全行を基準線、新着0として扱う。URLhashで重複排除し、後続の新番号だけを新着にする。番号/必須列/行の破損は源の失敗とし、一部だけを成功扱いで保存しない。正規ヘッダーだけの空CSVは0件として許可する。上場主体・企業の役割は本人が確認する。
5. 源設定に任意の`min_request_interval_seconds`（既定0、FDAは30）を追加する。直前の試行の開始/完了時刻の遅い方を基準に、秒精度の最大1秒分の余裕を付け、足りない分を専用ロックを保持して**取得前**に待機する（FDAは基準時刻+31秒）。完了時刻不明なら開始時刻を使う。履歴の開始時刻は待機後の取得試行開始時に記録する。通常の最低168時間は開始時刻を基準に継続し、forceは168時間だけを飛ばし、この秒単位間隔を無視しない。0秒設定には余裕/待機を追加しない。
6. 秒間隔の待機と通常の源間1.5秒をどちらも満たす。源間待機が既に消化した秒数を二重に足さず、残時間を再計算する。待機に全体120秒の残りを使い切るなら取得せず省略し、取得したような履歴を作らない。期間内の通常起動は待機/アクセスせず既存どおり省略する。
7. YouTubeのAPI鍵/データ更新期限への対応は本ADRで決めず、第3段階の設計差分とする。NEDOのHTML解析は既存の取得枠を使うが、列/結果リンク/日付の対応を次のRedで固定してから実装する。
8. FDA内では決定日の新しい項目から既存一覧で確認できる登録順にする。既存画面全体の作成時刻/ID降順の規則を変えず、決定日を保存の作成時刻へ代入しない。この順序は規制決定の時系列であり、銘柄の推奨順位ではない。

## Rationale

- CSVの企業/製品/規制情報は一次資料への入口として直接使えるが、上場親会社や売上への結び付けは自動化しない。
- 同じ2テーブルに保存すれば、基準線・取得欠測・本人選択の振る舞いを共用できる。スキーマ変更が不要。
- 秒単位の間隔を任意設定にすることで、FDAの取得条件を守り、既存RSSの挙動を保てる。

### 採用しなかった代替案

- FDAページ+CSVの2リクエスト: 1源1リクエストに反するので、公式ページで確認したCSV直URLを設定する。
- 決定日を公開日として保存: 週次の発見や投稿日を誤認する。
- force時の秒間隔無視: 短時間の同一ホストへのアクセスが増える。
- 配布データからティッカーを推定して自動候補化: 上場主体の誤同定を招く。

## Consequences

- 取得方式の解析を追加し、S10を有効化できる前提を整える。Green・実データの専用DB確認・レビュー後に有効化/導入を判断する。
- forceがFDAの直近試行後なら最大31秒ほど待つ。画面の既存loading表示を使い、基準線/新着以外の自動評価は追加しない。
- CSVの列/形式/URLは将来変わりうる。失敗を記録して確認できることを継続する。
- 認可、候補の手動確認、保有/ウォッチリスト/シグナルへの非自動登録を維持する。マイグレーションなし。

## 秒精度への追加補足（2026-10-11・本人承認済み）

独立Greenレビューで、既存`started_at`の秒精度により、実アクセス00.900→保存00.000→次回30.000となると実間隔が29.1秒になり得ることを確認した。通常168時間の起動は影響を受けないが、forceの最低アクセス間隔を満たさない。

開始時刻の保存から実HTTPまでにもDB書込み時間があるので、完了済み試行は`started_at`と`finished_at`の遅い方に、秒精度の最大1秒の余裕を付ける。FDAではこの時刻+31秒を次のアクセス可能時刻にする。`finished_at`不明の異常終了試行は開始時刻を使う（生存中の並行実行は既存600秒の専用ロックが防ぐ）。スキーマや別の時刻保存経路を増やさず、設定値の最低30秒、通常168時間、全体予算/源間待機の制約は維持する。

追加Red4件（成功/失敗の小数秒2ケース、31秒境界、試行記録のDB書込み遅延）と既存3ケースの待機期待の補正は、6件の意図した失敗/55件の成功・エラー0を独立レビュー後、本人の「承認して精度補足を修正する」で別途Gate 4承認を得た。Decision 5へ統合しGreenに着手。元の設計/31ケースの承認を遡及流用しない。
