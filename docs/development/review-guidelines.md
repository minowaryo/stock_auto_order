# review-guidelines.md — レビュー観点（全文）

> `/review` がレビュー前に読む。毎セッション読み込まれるファイルではない。常時読み込まれるコアは `.claude/rules/50-review.md`。

## レビュー強度の自動判定（review-score）

> 関連ADR: `meta/adr/ADR-0009-review-escalation-mechanism.md`

`/review` コマンド実行時、最初のステップ（Step 0）として `review-score` スクリプトが自動実行され、**現在のブランチが `main` から分岐して以降に変更されたすべて——ブランチのコミットに加え、作業ツリー上のステージ済み・未ステージ・未追跡の変更を含む**をスコアリングする。状態ファイルは持たない。AIは呼び出さないローカル処理のため、`/review` 実行のたびに計算しても実質コストゼロ・待ち時間もごくわずかである。

- スコアは「変更ファイル数」「変更行数」「機密パス（DBマイグレーション・Policy・認証関連ディレクトリ等）へのマッチ」の重み付き合計で算出する
- 閾値以上の場合は強化レベル（`.claude/commands/review.md` のStep 0で定義）でレビューを実行し、閾値未満の場合は通常レベルで実行する
- 設定（環境変数）: `REVIEW_SCORE_BASE_BRANCH` / `DOMAIN_BOUNDARY_BASE_BRANCH` でベースブランチを指定する（デフォルト `main`。ローカルにブランチがない場合は `origin/<base>` を使用）。`REVIEW_SCORE_THRESHOLD` で閾値を指定する（デフォルト30。`REVIEW_SCORE_LIGHT_THRESHOLD`（デフォルト10）でマージ前チェックの light 区分を指定する）。`master` / `develop` をベースにするプロジェクトはベースブランチ変数の設定が必須
- ブランチごとにスコアのスコープが自動的に分離されるため、複数ブランチを行き来しても他ブランチの差分に影響されない（`main` 分岐後の自分のブランチの差分だけを見る）
- Phase単位のまとまった開発か、Phase外のアドホックな小修正かは区別しない。`main` から分岐して以降の差分であれば、どちらも自動的に拾われるため、開発者側で分類する必要はない
- 同一ブランチで複数回 `/review` を実行すると、既にレビュー済みの部分を含めてブランチ全体の差分を毎回再評価する（差分はレビューのたびにリセットされない）。無駄な再チェックが発生し得るが許容する
- 本仕組みは「レビュー実行時にどの強度で行うか」を自動判定するものであり、「`/review` の実行自体を促す」ものではない（実行自体を自動化しない設計をA案として採用。詳細は `meta/adr/ADR-0009-review-escalation-mechanism.md` 参照）。実行タイミングは引き続き `.claude/rules/30-testing.md` の運用ルール（Refactor完了後・マージ前）に従う
- マージ時には、`prepare-merge` が同じスコアをマージ前チェックの区分として読む（`docs/development/git-workflow.md` §6 マージ前チェック）。これにより `standard` ではマージ前の `/review` が必須になることはあるが、`/review` 自体を起動することはない

## レビュー前確認（作成者）

マージ前に自分で確認する:

- [ ] `docs/product/use-cases.md` の要件に紐づいているか
- [ ] Feature Testがあるか
- [ ] TDD（Red→Green→Refactor）で進めたか（テストが実装より先に存在していたか）
- [ ] `php artisan test` が通るか
- [ ] クリティカルフローに変更がある場合、Playwright E2Eテストを追加し `npx playwright test` が通るか
- [ ] `./vendor/bin/pint` でコードスタイルを整えたか
- [ ] マイグレーションに危険な操作がないか
- [ ] secrets・PII がコードに含まれていないか
- [ ] 関係ないファイルを編集していないか
- [ ] Vue コンポーネントが `<script setup>` + Composition API になっているか（Vue+Inertia選定時かつフロントエンド変更がある場合。他スタック選定時は該当ルールファイルの規約に従っているか）
- [ ] `npm run lint` / `npm run build` が通るか（フロントエンド変更がある場合）

## レビュアー観点

### 機能・設計
- [ ] 要件（use-cases.md）と実装が一致しているか
- [ ] 既存の設計パターンに沿っているか
- [ ] 各Controllerが `.claude/rules/10-laravel.md` のDomain Boundary契約を満たしているか（`DB::` を呼んでいない、Eloquentの書き込みをしていない、ロールのインラインチェックをしていない、複数エンティティにまたがる判断をしていない）？ `/review` のStep 0で実行される `.claude/hooks/domain-boundary-check.sh` が機械的に検出可能な部分を検知する——クリーンな実行結果は証拠にはならない。プレーンなPHPで書かれたクロスエンティティな判断はこのチェックには見えないため
- [ ] Policy / Gate を通しているか

### DB・パフォーマンス
- [ ] マイグレーションが後方互換か
- [ ] N+1クエリがないか
- [ ] 必要なインデックスがあるか

### セキュリティ
- [ ] バリデーションが適切か
- [ ] 認可チェックがあるか
- [ ] secrets が含まれていないか
- [ ] ログに PII が出ていないか
- [ ] 特権操作・破壊的操作が固定最小スキーマで `audit` チャンネルに記録されているか（`.claude/rules/40-security.md`）

### テスト
- [ ] テストが正常系・異常系をカバーしているか
- [ ] テスト名が日本語で分かりやすいか
- [ ] E2Eテストが「クリティカルフローのみ」の範囲に収まっているか（網羅目的の乱用がないか）
- [ ] 新規データモデル（migration）が追加された場合、use-cases.md上で提供が定義されている作成・編集・削除の操作がFeature Testで網羅されているか（未定義の操作を理由に追加実装・追加テストを求めていないか。`.claude/rules/30-testing.md` のCRUD網羅ルール参照）

### フロントエンド（`meta/adr/ADR-0005-frontend-stack.md` の選定に応じて適用）

以下は Vue 3 + Inertia.js + Pinia を選定した場合の観点。他スタックを選定した場合は、そのスタックの実装ルールファイルの観点に置き換える。

- [ ] Page コンポーネントが `Pages/` に、共通コンポーネントが `Components/` にあるか
- [ ] Props・Emits の宣言方式がプロジェクト言語設定に沿っているか（TS: 型パラメータ形式 / JS: runtime 宣言形式）
- [ ] ロジックが Composable / Store に分離されているか（Fat コンポーネント禁止）
- [ ] DOM 直接操作がないか
- [ ] Inertia `useForm()` でバリデーションエラーを処理しているか

### ドキュメント
- [ ] 設計変更が docs に反映されているか
- [ ] 新しいADRが必要な判断をしていないか
