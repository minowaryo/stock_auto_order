# tdd-guard.md — `/tdd` の間に何がロックされるか、それをどう変えるか

> 書き込みがブロックされたとき、`/tdd` がスナップショットとの差分を報告したとき、またはガードが何を
> しているか知りたいときに読む。決定の記録: `meta/adr/ADR-0017-loop-engineering-stage1.md`。

## ルールは1つ

**実装者は、自分が到達を求められているゴールを動かせない。** `/tdd` のサイクルでは、ゴールとは Gate 4 で
人間が承認したテストと仕様である。`tdd-implementer` サブエージェント（Green）は、そのゴールを満たすために
アプリケーションコードを変更してよいが、ゴールそのものは変更できない。

## 誰が何を変更できるか

| 誰 | `tests/` | 仕様（`docs/product/`） | アプリケーションコード |
|---|---|---|---|
| あなた | いつでも | いつでも（通常どおり変更要求で） | いつでも |
| メインセッション（あなたが対話しているAI） | あなたの指示で | あなたの承認を得てドラフト・修正 | 可 |
| `test-writer`（Red） | 書く | 読むだけ | 不可 |
| **`tdd-implementer`（Green）** | **ブロック** | **ブロック** | 書く |

サイクルの記録 — `logs/audit.jsonl` と `.git/claude-tdd/` の承認スナップショット — も `tdd-implementer`
に対してブロックされる: 確認される側が、自分についての証拠を編集できてはならない。

あなたとメインセッションに対しては何もロックされない。オン・オフを切り替えるロックもない。

## 何が実行され、何が見えるか

| いつ | 何が起きるか | 何が見えるか |
|---|---|---|
| すべてのツール呼び出し | `.claude/hooks/agent-guard.sh` が `tdd-implementer` の呼び出しを確認し、`tests/`、`docs/product/`、`logs/audit.jsonl`、スナップショットへの書き込みと、ステージ・コミット・切り替え・設定を行う git コマンドをブロックする | その時点では何も見えない。ブロックした試みは1件ずつ `logs/audit.jsonl` に書かれる |
| Gate 4 で承認した直後 | `/tdd` が `tests/` と `docs/product/` を `.git/claude-tdd/approved/` にコピーし、`logs/audit.jsonl` のサイズを記録する | 1行: 「Saved the approved snapshot …」 |
| Green の直後 | `/tdd` がファイルをそのコピーと比較し、承認後に書かれたログの行を読む | 通常は「unchanged」と「No blocked attempts」。何か変わっていれば差分が表示され、`/tdd` はあなたの判断を待って止まる。ブロックした試みはログの行そのままで表示される — 実装者の報告ではなくログから取る。報告には書かれないことがあるため |
| テストと仕様が矛盾している | 実装者が止まり、`SPEC_CONFLICT`（テスト名 + ユースケースからの引用）を報告する | 無理に Green にする代わりの報告。どちらが間違っているかはあなたが判断する |
| 実装者が行き詰まった | 3回の試行の後、または同じ失敗が2回出たときに止まる | 何を試したかの報告 |

## テストや仕様を正当に変える方法

1. 何が間違っているかを判断する（テスト、仕様、またはその両方）。自分で編集するか、メインセッションに
   依頼する。
2. サイクルを Red からやり直す（同じユースケースでもう一度 `/tdd`）。
3. Gate 4 で承認する — 新しいスナップショットが保存され、以後は新しい版がゴールになる。

これだけである。ロック解除や再ロックの手順は別にない。

## `/tdd` がスナップショットとの差分を表示したとき

差分は、承認後に `tests/` や `docs/product/` で何が変わったかを正確に示す。`verify` がログが承認時より
短いと言った場合は、サイクル中に誰かが `logs/audit.jsonl` を書き換えている。サイクルの記録は信頼できない
ものとして扱い、`app/` の差分を自分で確認すること。

- **意図しない変更** → 破棄して（例: 差分からファイルを元に戻す）続ける。
- **望む変更** → Red からやり直して、もう一度承認する（上記）。

チェックはいつでも自分で実行できる:

```bash
bash .claude/hooks/tdd-snapshot.sh verify   # 承認スナップショットと比較する
bash .claude/hooks/tdd-snapshot.sh record   # 新しいスナップショットを保存する（Gate 4 の承認が行うこと）
```

## ログ

`logs/audit.jsonl`（git の管理外）はAIエージェントの活動を記録する。1イベント1行の JSON で、このガード
の場合は `"event":"agent_guard_denial"` に、セッション、ツール、ブロックしたパスまたはコマンドが入る。
ファイルの内容は決して入れない。ブロックした試みは、それ自体がシグナルである: テストを編集しようとした
実装者は、できなかったとしても、ゴールを動かそうとしていた。
これはアプリケーションの監査ログ（`storage/logs/audit.log`、`.claude/rules/40-security.md`）**ではない**。
そちらはアプリケーションの利用者が何をしたかを記録する。

## 限界

- フックはガードレールであり、壁ではない: ネイティブWindowsには OS サンドボックスがないので、
  サブプロセスは書き込める。Green 後のスナップショットのチェックが `tests/` と `docs/product/` への
  そうした書き込みと、短くなったログを捕まえる。テストとそのスナップショットのコピーの両方を書き換える、
  または最新のログの行だけを消すサブプロセスは捕まえられない。それを塞げるのは、エージェントを自分の
  作業領域の届かない場所で動かすことだけである（ADR-0017、段階5）。
- クラッシュまたはタイムアウトしたフックは呼び出しを通してしまう。そのためフックは速く保たれ（bash の
  組み込み機能のみ）、スナップショットのチェックが最後の砦になる。
- Codex の利用者はスナップショットのチェック（AGENTS.md のワークフローで `/tdd` の手順が実行する）は
  使えるが、フックはまだ使えない — Codex のフックは書き込んでいるエージェントを区別できない（ADR-0017、
  段階4）。
