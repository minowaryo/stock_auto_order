# tdd-guard.md — `/tdd` の間に何がロックされるか、それをどう変えるか

> 書き込みがブロックされたとき、`/tdd` がスナップショットとの差分を報告したとき、またはガードが何を
> しているか知りたいときに読む。決定の記録: `meta/adr/ADR-0017-loop-engineering-stage1.md`。

## ルールは1つ

**実装者は、自分が到達を求められているゴールを動かせない。** `/tdd` のサイクルでは、ゴールとは Gate 4 で
人間が承認したテストと仕様である。`tdd-implementer` サブエージェント（Green）は、そのゴールを満たすために
アプリケーションコードを変更してよいが、ゴールそのものは変更できない。

## 誰が何を変更できるか

| 誰 | `tests/` | 仕様（`docs/product/`） | アプリケーションコード |
|---|---|---|---|
| あなた | いつでも | いつでも（通常どおり変更要求で） | いつでも |
| メインセッション（あなたが対話しているAI） | あなたの指示で | あなたの承認を得てドラフト・修正 | 可 |
| `test-writer`（Red） | 書く | 読むだけ | 不可 |
| **`tdd-implementer`（Green）** | **ブロック** | **ブロック** | 書く |
| `cycle-reviewer`（Green後） | 読むだけ | 読むだけ | 読むだけ——指摘を報告し、判断は `/tdd` が行う |

サイクルの記録 — `logs/audit.jsonl` と `.git/claude-tdd/` の承認スナップショット — も `tdd-implementer`
に対してブロックされる: 確認される側が、自分についての証拠を編集できてはならない。

あなたとメインセッションに対しては何もロックされない。オン・オフを切り替えるロックもない。

## 何が実行され、何が見えるか

| いつ | 何が起きるか | 何が見えるか |
|---|---|---|
| すべてのツール呼び出し | `.claude/hooks/agent-guard.sh` が `tdd-implementer` の呼び出しを確認し、`tests/`、`docs/product/`、`logs/audit.jsonl`、スナップショットへの書き込みと、ステージ・コミット・切り替え・設定を行う git コマンドをブロックする | その時点では何も見えない。ブロックした試みは1件ずつ `logs/audit.jsonl` に書かれる |
| Gate 4 で承認した直後 | `/tdd` が `tests/` と `docs/product/` を `.git/claude-tdd/approved/` にコピーし、`logs/audit.jsonl` のサイズを記録する | 1行: 「Saved the approved snapshot …」 |
| Green の直後 | `/tdd` がファイルをそのコピーと比較し、承認後に書かれたログの行を読む | 通常は「unchanged」と「No blocked attempts」。何か変わっていれば差分が表示され、`/tdd` はあなたの判断を待って止まる。ブロックした試みはログの行そのままで表示される — 実装者の報告ではなくログから取る。報告には書かれないことがあるため |
| Green の直後、その比較の後 | `/tdd` が `.claude/hooks/fixture-literal-check.sh` を実行する: アプリケーションコードが、承認済みテストにしか含まれない値と比較していないか（例: `if ($product->sku === 'SKU-A')`） | 問題なければ何も出ない。見つかれば `FIXTURE_LITERAL file:line 'value'` の形で表示され、`/tdd` はあなたの判断を待って止まる |
| 両方のチェックが通ったとき | `/tdd` がアプリケーションファイルを `.git/claude-tdd/green/` にコピーする（`tdd-snapshot.sh mark-green`） | 1行: 「Saved the application files after Green …」 |
| Green確認の後 | `/tdd` が `cycle-reviewer` サブエージェントに変更のレビューを依頼する（小さな変更ではスキップ。ADR-0020） | 判断が必要な指摘（仕様の矛盾、セキュリティ、ユーザー向けの変更、不審な指示、HIGH）があれば `/tdd` はあなたの判断を待って止まる。小さな DEFECT / Domain Boundary の指摘は1回だけ修正して報告する。テストの不足は報告する |
| Refactorの後、またはGreen後に行った修正（例: レビュー指摘）の後 | `/tdd` がそのコピーと比較する（`verify-green`）。権限（Policy、ルート、ミドルウェア、`authorize`、`Gate::`、ロールチェック）、破壊的操作（マイグレーション、`delete(`、`truncate(`）、セキュリティ（`v-html`・`{!! !!}`、生SQL、一括代入、hidden属性、認証・セッション設定）、secrets（`.env`、キーの代入）、外部への影響（メール、HTTP、通知、スケジュール、ジョブ）、依存関係（`composer` / `npm` のファイル）、整合性（トランザクションやロックの削除）に触れる変更 | `STOP …` の行が出て、`/tdd` はあなたの判断を待って止まる。それ以外の変わった画面・文言・バリデーション・コントローラは、最後のまとめに `LISTED` として載り、あなたが見る。それ以外に聞かれることはない |
| テストと仕様が矛盾している | 実装者が止まり、`SPEC_CONFLICT`（テスト名 + ユースケースからの引用）を報告する | 無理に Green にする代わりの報告。どちらが間違っているかはあなたが判断する |
| 実装者が行き詰まった | 3回の試行の後、または同じ失敗が2回出たときに止まる | 何を試したかの報告 |
| 実装者が止まらない | `agent-guard.sh` が Gate 4 の承認ごとに、実装者の起動回数（3回目の起動を拒否）と、実装者の書き込み・コマンドの回数（60回を超えたら拒否）を数える。新しい承認で両方とも数え直しになり、`/tdd` のサイクル外では何も数えない（ADR-0020） | `/tdd` は済んだことと残っていることを報告して止まる。拒否はブロックされた試みの行に出る |

## テストや仕様を正当に変える方法

1. 何が間違っているかを判断する（テスト、仕様、またはその両方）。自分で編集するか、メインセッションに
   依頼する。
2. サイクルを Red からやり直す（同じユースケースでもう一度 `/tdd`）。
3. Gate 4 で承認する — 新しいスナップショットが保存され、以後は新しい版がゴールになる。

これだけである。ロック解除や再ロックの手順は別にない。

## `/tdd` がスナップショットとの差分を表示したとき

差分は、承認後に `tests/` や `docs/product/` で何が変わったかを正確に示す。`verify` がログが承認時より
短いと言った場合は、サイクル中に誰かが `logs/audit.jsonl` を書き換えている。サイクルの記録は信頼できない
ものとして扱い、`app/` の差分を自分で確認すること。

- **意図しない変更** → 破棄して（例: 差分からファイルを元に戻す）続ける。
- **望む変更** → Red からやり直して、もう一度承認する（上記）。

チェックはいつでも自分で実行できる:

```bash
bash .claude/hooks/tdd-snapshot.sh verify   # 承認スナップショットと比較する
bash .claude/hooks/tdd-snapshot.sh record   # 新しいスナップショットを保存する（Gate 4 の承認が行うこと）
bash .claude/hooks/tdd-snapshot.sh mark-green    # Green後のアプリケーションファイルを記録する
bash .claude/hooks/tdd-snapshot.sh verify-green  # Green後に何が変わったか、どれで止まるべきか
```

## ログ

`logs/audit.jsonl`（git の管理外）はAIエージェントの活動を記録する。1イベント1行の JSON で、このガード
の場合は `"event":"agent_guard_denial"` に、セッション、ツール、ブロックしたパスまたはコマンドが入る。
ファイルの内容は決して入れない。ブロックした試みは、それ自体がシグナルである: テストを編集しようとした
実装者は、できなかったとしても、ゴールを動かそうとしていた。
これはアプリケーションの監査ログ（`storage/logs/audit.log`、`.claude/rules/40-security.md`）**ではない**。
そちらはアプリケーションの利用者が何をしたかを記録する。

## 限界

- フックはガードレールであり、壁ではない: ネイティブWindowsには OS サンドボックスがないので、
  サブプロセスは書き込める。Green 後のスナップショットのチェックが `tests/` と `docs/product/` への
  そうした書き込みと、短くなったログを捕まえる。テストとそのスナップショットのコピーの両方を書き換える、
  または最新のログの行だけを消すサブプロセスは捕まえられない。それを塞げるのは、エージェントを自分の
  作業領域の届かない場所で動かすことだけである（ADR-0017、段階5）。
- ロックされたパスに言及し、かつ書き込みに見えるコマンドは、コマンドの文面を読んで拒否される。そのため誤って拒否されることがある——たとえばアプリのファイルを書き換え、同じコマンドの中でテストファイルを実行するスクリプトなど。PHP の `$obj->prop` と `=>` はリダイレクトとして数えない。それでも誤って拒否される場合は、2つのコマンドに分ける（書き込み、次にテスト実行）。逆の抜け道——`$v->tests/x` のように見せかけた書き込み——は、スナップショットのチェックに任せている。
- fixture-literal チェックが読むのは引用符付きの文字列だけで、比較している追加行（`===`、`==`、`!=`、`case`、`match`、`in_array(`、`where(`）が対象である。数値、連結で分割された値、定数の陰に隠れた値は見えない——それらはレビュアー、または差分を読む人が補う（EN版の `meta/design/fixture-literal-check.md`）。
- Green後のチェックが読むのはパスと追加・削除された行なので、それらの語を使わずに書かれた権限や破壊的操作の変更（別名で手書きしたロール比較、一括更新）は `LISTED` になるだけか、見えない——レビュアーとあなたの最後の確認で補う（EN版の `meta/design/s7-user-facing-stop.md`）。ロールチェックは一般的な名前（`isAdmin`、`hasRole` など）と、本体がロールに触れているプロジェクト独自の `is…()` / `has…()` メソッドで認識する——自動で見つけるので設定は要らない。git が無視するファイルは対象外。Livewireコンポーネント（`app/Livewire/`）は `LISTED` の対象パスに入っていないが、`STOP` の判定は行の内容で行うので同じく効く
- 起動回数と呼び出し回数の上限（2回と60回。実際のサイクルで使われた回数のおよそ2倍）は、フックからは見えない
  時間とトークンの代わりである。サイクルレビュアーには回数の上限がない（EN版の `meta/design/stretch-chaining-limits.md`）。
- フックは、Claude Code が各呼び出しについて伝える内容に依存する。アップデートでそれが変わると、フックは何の兆候もなくすべてを通してしまう。そのため `verify` は、承認後に実装者の呼び出しを1件も数えなかったときに警告する（「WARNING: agent-guard.sh counted no …」）: 実装者が動かなかったか、フックがもう呼び出しを見えていないかのどちらかである——テンプレートのメンテナーに伝えれば、そのバージョンでフックを確認し直せる（EN版の `meta/design/guardrail-regression-suite.md`）。
- クラッシュまたはタイムアウトしたフックは呼び出しを通してしまう。そのためフックは速く保たれ（bash の
  組み込み機能のみ）、スナップショットのチェックが最後の砦になる。
- Codex の利用者はスナップショットのチェック（AGENTS.md のワークフローで `/tdd` の手順が実行する）は
  使えるが、フックはまだ使えない — Codex のフックは書き込んでいるエージェントを区別できない（ADR-0017、
  段階4）。
