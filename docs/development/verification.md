# 共通検証手順

Codexの `$verify` とClaude側の検証手順が参照する共通方針。検証依頼は機能変更やGate承認を意味しない。失敗を発見した場合は原因と影響を報告し、実装修正は通常のTDD・承認手順に従う。

1. `AGENTS.md`、`docs/ai-context/common-commands.md` と対象変更に対応するルールを読む。
2. `git status --short`、作業ツリー・ステージ済み差分、対象の未追跡ファイルを確認し、検証範囲を特定する。
3. `composer.json` / `package.json`、コンテナ手順と導入済みツールを確認し、変更に必要なチェックを実行する。

| 対象 | 検証例 |
|---|---|
| Laravelの機能・修正 | 対象Feature/Unitテスト、必要に応じて関連回帰テスト |
| PHPのスタイル・型 | 導入済みのPint `--test`、PHPStan |
| フロントエンド | 定義済みのlint・型検査・build |
| UIを含むクリティカルフロー | 対象UCのPlaywright E2Eとローカル画面操作 |
| 文書・ハーネスのみ | 参照先、SKILL.md frontmatter、設定構文、`git diff --check` |

4. UI変更の実挙動確認では既存の起動手順とローカルのテストデータを使う。実ブラウザ確認ができなければ未実施と理由を記録する。
5. 実行したコマンド、終了結果、対象UC、未実施項目と理由を報告する。設定ファイルの存在や単体テスト成功を、MCP接続・画面動作の成功と言い換えない。

本番URL・実データ・実認証情報を使わない。検証のためにDBをリセットしたり依存パッケージを勝手に追加したりしない。Gate 4のRed確認は、依存不足・接続失敗と仕様どおりの失敗を区別する。
