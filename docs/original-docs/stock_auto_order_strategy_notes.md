## 1. システムの基本運用サイクル

- 楽天証券のWeb（マイページ）から取引履歴CSVをダウンロード
- 週末にCSVをアップロード → スコアリング・分析 → レポート出力
- 月曜寄り付き前に、分析結果をもとに指値を判断

## 2. データ取得経路の整理

| 経路 | 用途 | 特徴・制約 |

## 3. 多層スコアリングモデル（分析フローの核）

### ① テクニカル指標層（過熱度判定）
- RSI、MACDシグナル、MA20乖離率、52週高値/安値からの距離、ボリンジャーバンド乖離、PEGレシオ
- 既存ポジション向けの失速検知タグ：`week52_high_pullback`（52週高値からの下落）、`relative_strength_weakening`（対市場相対力の劣後）、`peg_overvalued`

### ② ファンダメンタルズ層（質のスコアリング）
- PER・PBR・ROE・自己資本比率・売上/営業利益成長率・営業利益率・配当利回り
- 同業種内での相対評価（例：低PER/PBRで同等以上のROEを実現できているか）

### ③ マクロ・セクター文脈層
- SOX指数・日経平均の52週高値からの下落率で「セクター全体の底打ちシグナルの有無」を判定
- セクター集中度の可視化（半導体/AI関連への偏りをチェックし、非関連セクターへの分散方針と接続）

### ④ 意思決定支援層（グループ分類）
- **グループA**：新規エントリー候補（PEG割安・MA20乖離が小さく未加熱）
- **グループB**：含み益大だが失速シグナル出現（52週高値からの下落・相対力劣後）
- **グループC**：決算急騰などで直近過熱（RSI高水準・MA20乖離大）

### ⑤ ダイナミック・ファクター・ローテーション（拡張案）
- マクロレジーム（SOXドローダウン幅、米金利動向など）に応じて①〜④の重み付けを動的に変更する発想
- 例：AI減速懸念が強い局面ではモメンタム系の重みを下げ、クオリティ・バリュー系の重みを上げる

### ⑥ 上場年数・IPOイベントリスク層（拡張案）
「上場5年以内」は危険信号にも成長シグナルにもなり得る両面的な指標——単純なフラグではなく「追加精査トリガー」として扱う。
- プラス面：IPO5年以内＆四半期2ケタ増収は"高成長サイン"として実際にスクリーニング条件に使われる組み合わせ
- マイナス面（イベントリスクとして個別管理）：
  - ロックアップ解除日（上場90日後・180日後が一般的）— 解除前後は需給悪化・株価急落リスクが高まるため、保有銘柄はこの日付をカレンダー管理する
  - 財務トラックレコードが短く、業績の景気サイクル耐性が未検証
  - 上場基準厳格化に伴う市場区分ダウングレードのリスク（再上場時の格下げ事例あり）
- 運用案：上場5年以内の銘柄は自動的に除外・警戒するのではなく、①②の通常スコアリングに加えて「ロックアップ解除日が直近60日以内か」を個別にチェックするフラグを立てる

### ⑦ 信用取引需給層（拡張案）
週次で公表される信用取引残高データを、既存の「週末バッチ分析」サイクルにそのまま組み込める追加レイヤー。
- **信用倍率**（信用買い残÷信用売り残）：1倍超で買い優勢、1倍未満で売り優勢
  - 5倍以上＝過熱（グループCの追加判定材料。返済期到来による将来の売り圧力リスク）
  - 0.5倍以下＝空売りの買い戻しによる反発の逆張りチャンス（グループAの後押し材料）
- **逆日歩（品貸料）**：信用売り残が買い残を上回る「売り長」銘柄で発生するコスト。信用倍率1倍未満・貸借倍率が低い銘柄、権利付最終日や株主優待銘柄は特に注意
- **回転日数**：`(融資残+貸株残)×2 ÷ (融資新規+返済+貸株新規+返済)`（5日移動平均）。短いほど資金循環が速く、相場が活発
- **公表タイミング**：毎週金曜（最終営業日）時点のデータが翌週第3営業日朝に更新——既存の週末バッチサイクルと自然に噛み合う
- 実践的な週次チェック項目：①信用倍率の絶対値 ②買い残の前週比増減率 ③売り残の前週比増減率 ④株価との乖離状況の4点セット
- 注意点：信用残高単体では判断材料として弱く、出来高・テクニカル指標と併用が前提

## 4. 出口戦略（利確・損切りルール）の強化

### 現行方針
- 含み益が一定水準（例：+20%）を超えた銘柄に絞った「ラストワンマイル」利確判断支援
- 買い側・含み益が薄い銘柄の判断は引き続き人力

### 強化案：固定閾値 → ATRベースの動的トレーリングストップ（チャンデリアエグジット）
- 計算式：**ストップライン ＝ 直近高値 − ATR × 乗数**
- 乗数の目安：短期1.5倍／標準2.0倍／スイング・長期3.0倍
- 銘柄ごとのボラティリティに応じてストップ幅が自動調整されるため、値動きの荒い中小型株と穏やかな大型株を同一ルールで扱う矛盾を解消
- 確定足（日足終値）ベースでATRを計算し、ノイズへの過剰反応を避ける
- 補助策：目標到達時に半分だけ利確し、残りをトレーリングストップで伸ばす「分割売却」

## 5. インフラ・アーキテクチャ面の改善点

1. **Claude Codeサブエージェント構成**：リポジトリの`.claude/agents/`に、データ収集担当・テクニカルスコアリング担当・ファンダメンタルズスコアリング担当・レポート生成担当のような専門サブエージェントを追加する設計
2. **障害耐性設計**：1つのデータソース取得失敗でパイプライン全体を止めない。取得失敗はエラーフィールドに格納して処理継続
3. **通知基盤の見直し**：LINE Notifyは2025年3月末でサービス終了済み。後継のLINE Messaging API（LINE公式アカウント経由）への置き換えが必須
4. **通知履歴のDB記録**：Laravelのデータベース通知機能を使い、「いつ・どの銘柄で・どんな条件でシグナルが発動したか」を`notifications`テーブル等に記録し、後から精度検証できるようにする
5. **バックテスト基盤**：Pythonの`backtesting`ライブラリ等で過去データ検証を行うだけでなく、**モンテカルロシミュレーション（バックテスト結果のブートストラップ再抽出）**で戦略の頑健性を評価。目安として「最悪ケースの最大ドローダウンはバックテスト観測値の2倍程度を想定」

## 8. 確認事項・判断事項（実装前に整理が必要）

### 確認事項（事実ベースで調べれば決まるもの）
- [ ] 楽天証券の取引履歴CSVには「信用取引残高（市場全体の需給データ）」は含まれない（あくまで自分の保有ポジション明細）。信用倍率・信用残高は**別データソース**が必要——東証の日々公表データ、日証金の貸借取引データ、または証券会社サイトのどれを使うか要確認
- [ ] ATR計算に必要な日足OHLC（始値・高値・安値・終値）データが、楽天証券CSVの取引履歴に含まれているか、それとも別途株価データ取得（無料API・スクレイピング等）が必要か
- [ ] ロックアップ解除日は有価証券届出書に記載——個別に確認するか、IPO情報サイト（トレーダーズ・ウェブ等）のロックアップ解除一覧を毎回参照するかの運用方法
- [ ] マーケットスピードII RSSの利用に、追加契約や取引ツールのインストールが必要かどうか（将来の自動発注機能を見据える場合のみ確認すればよい）

### 判断事項（方針として決める必要があるもの）
- [ ] 信用倍率の閾値（5倍以上を過熱、0.5倍以下を逆張り機会とする案）をそのまま採用するか、自分の投資スタイルに合わせて調整するか
- [ ] ロックアップ解除日が近い銘柄を「自動的に警戒表示」するか、「単に情報として提示するだけ」に留めるか
- [ ] ATRの乗数（1.5/2.0/3.0倍）を全銘柄一律で始めるか、業種・時価総額規模で最初から差をつけるか
- [ ] 信用取引データ・ロックアップ日程などの外部データ取得を、どこまで自動化（スクレイピング/API連携）するか、どこまで手動確認で許容するか——実装コストとのバランス
- [ ] MVP（Gate 2で着手する最小実装）の範囲：①②③④のコアスコアリングのみで最初にリリースし、⑤⑥⑦（ファクターローテーション・IPOイベント・信用取引需給）は第2フェーズに回すかどうか
