# Web情報から企業候補を自動抽出する計画（CHG-0031 / F-016 / UC-016）

作成: 2026-10-16、状態更新: 2026-10-20。**[追加仕様・3画面モック](megatrend-candidate-automation-spec.md)のGate 2、ADR-0033のGate 3、FDA79件/JPX補足3件のGate 4は2026-10-19本人承認済み。[マージ前レビューの4指摘と追加Red10件](../development/chg0031-automation-merge-review.md)も10/20にGate 4本人承認しGreen修正済み。関連314件/画面E2E1件が成功、具体的commit/merge計画の承認待ち。** 関連UC: UC-012。関連ADR: ADR-0022・ADR-0025・ADR-0031・ADR-0032・ADR-0033。

## 1. 完成時の利用体験

**アプリがWeb情報を取得し、企業を抽出・絞り込み、出典付きの候補を表示する。本人は候補を確認・選択し、必要な確認後にウォッチリストへ追加する。** 企業名・資料名・URL・テーマとの関係を一から手入力しないことを通常の経路とする。

流れ: `アプリ起動 → 情報源の更新確認 → 企業ごとの候補下書きを自動生成 → 候補一覧を確認 → 調査記録へ取り込み・根拠確認 → 監視に追加 → UC-012の指標更新`。

ここでのスクリーニングは、テーマとの関係、企業の役割、日米の上場主体との対応、既存登録・保有状況で候補を整理すること。財務健全性・押し目買いシグナルは、監視登録後のUC-012で既存処理を使う。候補段階での財務条件による足切り・有望度ランキングを追加するなら別の仕様差分として扱う。

## 3. 仕様として先に確定する差分

| 項目 | 提案 |
|---|---|
| 主経路 | 自動抽出された企業候補の確認を主経路にする。手動記録は補助操作として折りたたむ |
| 自動化の境界 | 情報源の取得から、未確認の企業候補下書きの生成・表示までを自動化する。本人が確認して初めて調査記録・監視登録へ進む |
| 情報の由来 | 元資料の企業名・製品名・申請番号等と、システムの分類・要点を区別して表示する。システム生成の説明を「自分の要約」、取得日を「本人の確認日」として保存しない |

| 初回取得 | 過去の基準線も候補抽出の対象にし、「初回取得・過去資料」として確認できる。今週の新着発見には数えない |
| 未登録判定 | 最新の保有・CSV・ウォッチリストと照合する。照合元がない/同定できない場合は「照合未実施/上場主体要確認」で残す |
| 取得のきっかけ | 既承認の起動時確認を使う。「今すぐ確認」も使える。PC停止中の定期巡回を約束せず、前回確認時刻と取りこぼしを示す |
| 品質評価 | 4週試行・導入後3週の観察は品質評価として続ける。mainで既承認の前倒し導入を前提に、今回の追加差分の着手条件を最新UCへ整理する。日付経過や取得成功を品質合格とみなさない |

ADR-0031 D7とADR-0032は「自動で候補を作らず、本人がフォームで記録」を承認している。候補下書きの自動生成、入力項目の由来、画面の主経路は**新しいGate 2差分**としてレビューする。既承認の取得処理のGate承認を、この差分の承認へ流用しない。

P2は途中成果として利用可能にするが、CHG-0031全体はP3/P4まで未完了として残す。各実装サイクルはRed → Gate 4本人承認 → Green → Refactorで進める。保存設計の追加はGate 3承認後に実装する。

### P3で情報源ごとに確認すること

- **FDA**: 既存の構造化metadataを優先する。製品が一覧に載ることと、売上・上場主体の確認を区別する。初回全件をそのまま企業数として数えず、法人候補ごとに束ねる。
- **NEDO**: 進行中計画の「結果リンク一覧」だけでは企業抽出が終わらない。採択先名がある正規の配布データ、結果本文、添付資料までの取得条件と解析可能性を調べる。必要な本文/PDFの追加取得は、現行の1源1リクエスト・本文/PDF非取得を変える差分としてGate 2/ADRで別途承認する。取得数・サイズ・時間に上限を設け、画像PDF等の解析不能は明示する。
- **AI基盤**: NEDOの該当事業や、企業名が取れる公式データを候補として比較する。OCPが手動対象である現状を、自動対応済みへ読み替えない。取得できない源は代替を選び、AI基盤の企業抽出まで検証する。
- **公開note**: 既に取得できるRSSのフィールドから何が抽出できるか測る。題名だけで企業を特定できない項目は「資料のみ・企業未抽出」として区別する。
- **YouTube等**: 既存計画の取得経路・鍵・保存更新条件を先に解決する。タイトル/動画URLの取得だけでは企業抽出の完了条件にしない。

各源は採用前に公式の取得経路・利用条件・最新のサンプル・更新頻度を再確認する。本計画は既存の調査とコードを再利用する提案であり、外部サイトの現在の取得可否を新たに確認した結果ではない。採用できない源は理由と代替源を残し、手動入力への置き換えだけでP3を完了扱いにしない。

## 5. 抽出・照合・保存の方針案

最初は構造化フィールドと根拠を追える分類ルールを使う。FDAのCompany/Device等、企業名の出所を特定できるデータから始める。テーマの分類理由には一致した分類・製品・根拠箇所を持たせ、企業の役割は資料に書かれた範囲で示す。固定語だけで扱えないものは未分類として再確認できるよう残す。

同定は、確認済みの法人・別名対応と公式の上場銘柄情報を使う。既存のholdingsだけでは未知の上場企業を照合できないため、日米それぞれの公式銘柄情報の取得経路・更新方法もP1で確定する。名称の類似だけで親会社やコードを埋めない。未同定企業も自動候補一覧には出す。

初期版の必須依存に新しいLLM・有料サービスを加えない。資料の要点は取得フィールドから構成できる説明とし、自由文の自動要約が必要になれば費用・評価・requirementsのOUT・CHG-0049との関係を別途レビューする。

保存設計はP1のGate 2後にADR/data-modelで具体化する。候補下書きは、元の取得項目・元発表・言及法人・分類結果・同定状態・根拠・処理状態を関連付ける単位とする。1資料に複数企業がある場合と、1企業に複数資料がある場合を扱う。既存の`research_source_items`は取得資料、`research_candidates`は本人確認後の調査記録として再利用し、下書きと人の確認記録を混ぜない。

同一の元発表×法人候補の再抽出で下書きを増殖させない。元の資料・分類ルールの変更は追跡できるようにし、本人が訂正・見送り・確認済みにした内容を再取得で上書きしない。転載は根拠として加算せず、同じ企業の別発表は保持する。手動記録と後から同一と判明した場合も関連付け、履歴を失わない。

既存レコードは保持し、追加テーブル/列による移行を基本とする。新処理は設定で停止でき、停止しても既存の調査記録・監視登録を閲覧できる設計にする。具体的な移行・戻し方はGate 3で確認する。

## 6. 画面と本人の操作

「調査候補」の上部を、最終取得状況 → 自動抽出候補一覧 → 選択した候補の確認、の順にする。手動記録フォームは補助操作へ移す。新しいグローバルタブは作らない。

一覧に企業名、テーマと抽出理由、製品/事業・企業の役割、元資料URL、発表/決定日、初回検出日、日米上場の対応状態、登録/保有状態、未確認事項を表示する。テーマ・市場・未登録・要確認・新着/初回取得で絞り込めるようにする。資料の件数と企業数を分け、上場主体未確定を確定企業数へ加算しない。

本人は候補を選び、根拠と上場主体を確認し、監視するか判断する。取得済みの企業名・URL・資料名・資料由来の説明を再入力させない。根拠不足の訂正や保留理由は入力できる。本人の確認・反証確認が済んでいないものを監視へ自動登録しない。

取得失敗・企業未抽出・候補なし・照合未実施を別の状態として出す。既存の「今週の新規発見」は記録・検出・元発表のどの週かを明記し、初回の過去資料を混ぜない。

P1で情報源ごとの正解サンプルと誤抽出/未抽出の許容基準を先に固定する。既存試行の「未登録3社・2テーマ・2元発行主体」は情報源の実用性指標として継続するが、A9の3テーマ対応の代わりにしない。新着がない日も再現できるよう過去の固定資料を使い、過去資料であることを明記する。

追加Feature/UnitはUC-016のタイトル・フローから命名し、Pestの外部HTTPを固定応答にして専用MySQL DBで実行する。実際の外部取得は別の確認として記録する。UIにはPlaywrightのクリティカルフローを追加し、UC-012・起動時情報源確認・FDA解析の既存テストを回帰実行する。通常の必要チェックとレビューを行い、テストと実環境の確認を混同しない。
