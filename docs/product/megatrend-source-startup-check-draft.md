# 情報源の起動時確認（CHG-0031 追加案・Gate 2/3 未承認）

> 状態: 2026-10-10 叩き台。Gate 2はUC-016「情報源の起動時確認」節、Gate 3は[ADR-0031](../adr/ADR-0031-research-source-startup-check.md)とdata-modelの`research_source_*`節に起こした（2026-10-10 本人承認済み）。本人が「データ取得のきっかけはアプリ起動時」と決定した。既存の起動時処理と競合せず、負荷が問題にならない作りにすることが条件。UC-016 の「情報源固有の自動取得は別のGate 2差分」に当たるため、本書の承認前に実装しない。

## なぜ必要か

- アプリは常時起動していない。現状の UC-016 は手動記録のみで、情報源を「確認して新着なし」だったのか「確認していない」のかを区別できない。4週試行の欠測をアプリで把握できない。
- 試行中の5源のうち、RSS・一覧ページで新着URLを取れる源は、起動時に「前回からの新着URL・タイトル・日付」を記録すれば、確認漏れと新着なしを分けられる。

## 方針

1. **きっかけ**: `scripts/start-app.bat` が応答確認後に起動するバックグラウンド処理（CHG-0033 の `price:track` と同じ経路）。cron は使わない。
2. **起動時処理を1本にまとめる**: `start-app.bat` から個別のコマンドを並べて呼ばず、起動時タスクの実行役（例: `php artisan app:on-start`）を1つ呼ぶ。実行役が `price:track` → 情報源確認の順に**直列**で実行する。並列にしないことで、PHPコンテナ・MySQLへの同時負荷を増やさない。タスクを足すときは実行役に登録するだけにする。
3. **起動ごとに毎回は取りに行かない**: 源ごとに「前回の成功確認から最低間隔（既定24時間）」を持ち、間隔内なら外部アクセス0件で終える。同じ日の再起動は何もしない。
4. **二重起動の防止**: 情報源確認は専用ロック（`research-source-check`、DBのcache_locks、最長10分）を持つ。`price-fetch` ロックとは別にし、価格取得の失敗・中断で情報源確認が止まらないようにする。
5. **負荷の上限**: 1源あたり一覧・RSS 1リクエスト（ページ送りなし）、源の間隔1.5秒、タイムアウト15秒、全体で最大2分。記事本文・PDFは取得しない（UC-016 の「公開本文を保存しない」を維持）。応答サイズの上限を超えたら失敗として記録する。
6. **失敗してもアプリを止めない**: 取得は起動後の裏で行い、画面表示を待たせない。失敗は源ごとに記録し、次回起動で再試行する。3回連続失敗で画面に「取得停止中」を表示する（自動では止めない）。
7. **候補は自動で作らない**: 取得するのは新着URL・題名・公開日だけ。本人が一覧から選んで UC-016 の候補記録へ進む。一次資料・上場主体の確認は従来どおり本人が行う。

## 記録するもの（Gate 3 で確定）

- 確認ログ（案 `research_source_checks`）: 源ID（S03/S09/S10/H01/H02）、開始・終了時刻、結果（新着あり／新着なし／失敗／間隔内のため省略）、新着件数、失敗理由。
- 新着項目（案 `research_source_items`）: 源ID、URL（ハッシュで一意）、題名、公開日、初回検出日時、本人の処理状態（未確認／候補化／対象外）。
- 画面: 調査候補の上部に源ごとの最終確認時刻・結果・未処理の新着件数を出す。前回確認から源の配信範囲（RSSの保持件数等）を超える間隔が空いた場合は「取りこぼしの可能性」を表示する。

## 本人の追加判断（2026-10-10）

- 起動時確認は試行期間にかかわらず入れる（確認記録は源の採否と無関係に欠測把握に役立つため）。
- どの源・どのデータを取るかは後から判断できるようにする（源は設定で有効／無効、付帯情報はJSONで保存）。
- 導入後3週間ほど記録を見てから、源ごとの継続と使う項目を決める。
