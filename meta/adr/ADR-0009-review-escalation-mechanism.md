# ADR-0009: 差分スコアに基づくレビュー強度の自動判定

## Status
Accepted

## Date
2026-08-14

## Context

`.claude/rules/30-testing.md` および `.claude/rules/00-global.md` では「Refactor完了後・マージ前に `/review` を実行する」という運用ルールが定義されているが、これを検知して実行を促す仕組みが存在せず、実運用では実行を忘れられやすい。

一方で、変更のたびに毎回AIによる強化レビュー（複数観点・adversarial検証を伴うWorkflow）を走らせるとAIコストが過大になる。また、開発はPhase単位（複数UC/機能をまとめた計画）で進むことが多いが、Phase外のアドホックな小修正も混在するため、Phase境界に処理を紐付ける設計は「このコミットはどのPhaseに属するか」という分類コストが発生し、運用上の負担になる。

## Decision

以下のレビュー強度自動判定の仕組みを採用する。

### 概要

1. `/review` コマンド実行時、最初のステップ（Step 0）として `review-score` スクリプト（AIを使わない決定的なローカルスクリプト）を実行する
2. スクリプトは **現在のブランチが `main` から分岐した地点（`git merge-base main HEAD`）から現在の HEAD までの差分** を計測する（状態ファイルは持たない）
3. 以下の重み付けでスコアを算出する
   - 変更ファイル数
   - 変更行数（追加+削除）
   - 機密パス（DBマイグレーション、Policy、認証関連ディレクトリ等）へのマッチ
4. スコアが閾値を超える場合、「強化レベルでのレビューを推奨」する旨を表示し、そのまま `/review` は強化レベル（複数観点・adversarial検証を伴うWorkflow）で実行する。閾値以下の場合は通常レベルで実行する
5. スコア計算自体はAIを呼ばずローカルで完結するが、計算結果に応じたレビューレベルの選択・実行は `/review` 実行という人間の明示操作の中でのみ行われる。バックグラウンドや `git push` などのタイミングで自動的にレビューWorkflowが起動することはない（この「実行自体は常に人間の `/review` 呼び出しを起点とする」方針を以降 **A案（半自動）** と呼ぶ）

### 状態ファイルを持たない理由（merge-base方式）

当初は「最終レビュー済みコミットSHA」を `.claude/review-checkpoint` に記録するチェックポイント方式を検討したが、以下の問題があり不採用とした。

- チェックポイントがリポジトリ全体で1つの共有状態のため、複数ブランチを行き来する運用（例: 大きめのPhaseブランチ作業中に別の小さいhotfixブランチへ切り替える）で、無関係なブランチの履歴を基準にスコアが計算され、小さい変更が不当に大きいスコアとして扱われる、あるいはノイズの多い結果になる
- チェックポイントの更新を忘れると、以降のスコアが実態より大きく計算され続ける

`git merge-base main HEAD` を基準にする方式であればブランチごとにスコアのスコープが自動的に分離され、状態ファイルの管理・更新忘れの問題自体が発生しない。Phase単位のまとまった開発か、Phase外のアドホックな修正かを区別する必要がない点は従来どおり維持される（そのブランチが `main` から分岐して以降の差分であれば、どちらも自動的に拾われる）。

トレードオフとして、同一の長期ブランチ上で `/review` を複数回実行した場合、差分が「前回レビューからの増分」にリセットされず、常に「ブランチ全体の差分」を再計算する。そのため2回目以降の `/review` が、既にレビュー済みの部分を含めて再度強化レベルを推奨することがある。これは無駄な再チェックが発生する程度の非効率であり、ブランチをまたいでスコアが壊れる問題より軽微と判断し許容する。

## Rationale

- スコア計算（`git diff --stat` 相当の処理のみ）はAIを一切呼ばずローカルで完結するため、push の頻度に関わらずコストゼロで実行できる
- AIコストが発生する強化レビューは「実際にスコアが高い＝リスクが高い変更」の場合のみ、かつ人間の明示操作でのみ発生するため、無制御な自動実行やコストの浪費を避けられる
- 非ブロッキングにすることで、通知のために開発速度・push自体を阻害しない

### 採用しなかった代替案

- **毎コミット時にAIによる複雑度解析を実行**: AIコストが過大になるため不採用
- **Phase定義とコミット・ブランチを厳密に紐付けて管理**: 分類コストが高く、「アドホックな修正を気にしなくてよい」という要件に反するため不採用
- **pre-push hook + インストールスクリプトによる自動起動**: `.git/hooks/` はGit管理外のため、新しい開発環境ごとにインストール手順（スクリプト実行または手動コピー）が発生し、ファイル構成・運用が複雑になる。ファイル一式をシンプルに保つ方針のため不採用し、`review-score` の起動は `/review` コマンド自身のStep 0に統合した
- **スコア閾値超え時にレビューWorkflowをバックグラウンドで自動起動（B案: 完全自動）**: `(ブランチ, HEAD SHA)` をキーにした重複排除（dedup）マーカーを持たせれば、同一状態への繰り返し自動実行は理論上防げる。しかし、そのためには自動実行のトリガー経路（push検知等）と dedup用の状態ファイルが新たに必要になり、merge-base方式で一度排除した「状態ファイルの管理・複数ブランチでの整合性」の問題が別の形で戻ってくる。ファイル一式をシンプルに保つ方針を優先し、現時点ではA案（人間が `/review` を明示実行し、レベル選択のみ自動化する半自動方式）を採用する。B案は将来的に打ち忘れが実運用上の問題として顕在化した場合に再検討する

## Consequences

### メリット

- `/review` の実行忘れを通知によって防止できる
- AIコストは実際にレビューを実行した回数・規模に比例し、push頻度には比例しない
- Phase単位の開発か、Phase外のアドホックな修正かを区別する運用コストが発生しない

### デメリット・リスク

- スコアの重み付け・閾値はプロジェクトごとの調整が必要（初期値は経験則ベースであり、チューニング前提）
- 実行自体は人間の `/review` 呼び出しを起点とする（A案）ため、「`/review` をそもそも実行し忘れる」リスク自体は残る（`.claude/rules/30-testing.md` の運用ルール順守に依存する）。この点は既存の運用ルール（Refactor完了後・マージ前に実行する）から変わらない
- 同一の長期ブランチ上で複数回 `/review` を実行すると、ブランチ全体の差分を毎回再評価するため、既にレビュー済みの部分を含めて再度強化レベルが推奨されることがある（無駄な再チェックが発生する程度の非効率であり、機能上のブロッカーではない）
