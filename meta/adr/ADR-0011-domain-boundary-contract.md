# ADR-0011: Domain Boundary を列挙型の契約として明文化し、決定的な検知を導入する

## Status
Accepted

## Date
2026-09-14

## Context

このハーネスのルールファイルはどれもFat Controllerを禁止している——`.claude/rules/10-laravel.md`、`docs/ai-context/module-map.md`、`.claude/rules/50-review.md`、`.claude/commands/review.md`、`.claude/agents/tdd-implementer.md` のすべてがそう書いている。しかしいずれも「薄く保つ（Fat Controller禁止）」という抽象的なラベルとしてしか書かれておらず、LLMが自分の出力を照らし合わせて判定できる基準になっていなかった。`meta/adr/ADR-0003-auth-strategy.md` は認可について同じ失敗パターンをすでに特定しており、Policy/Gateの必須化と直接ロールチェックの禁止という構造的な解決を行っている。

実プロジェクトでの計測により、ラベルだけでは不十分であることが確認された。**すでにこのハーネスを利用している**Laravelプロジェクト（その `.claude/rules/10-laravel.md` は9行目に「直接 `DB::` を呼ばない」、41行目に「**Policy / Gate を必ず使う**（手動チェック禁止）」と明記している）の21個のControllerをスキャンしたところ、以下が見つかった。

- `DB::transaction(...)` がControllerで直接呼び出され、`User::create(...)` と `Employee::create(...)` をラップしていた——採用済みルールへの違反が3件
- Controller内に手書きのネストした認可判定（`isAdmin()` / `isSectionHead()` / `abort(403)`）が存在した。**しかもこのプロジェクトにはすでに12個のPolicyクラスが実装されていた**
- 21個中1個のControllerしかServiceクラスを参照していなかった
- 合計103件の指摘、加えて17・18分岐を抱えるControllerメソッドが存在した

ルールは存在し、仕組み（Policy）も存在していたにもかかわらず、違反は積み上がった。プローズ（文章によるルール）だけでは境界は守られない。

本ADRのきっかけは、MulmoClaude/MulmoTerminal風のDSL——スキーマ・リレーション・権限・不変条件を宣言し、構造によってintegrityを強制する——を採用する提案だった。その方向性自体は妥当だが、ドキュメントとルールを配布するリポジトリであってコード生成エンジンではない本プロジェクトには不釣り合いに大きい（「採用しなかった代替案」参照）。

## Decision

### 1. 境界を列挙型の契約として明文化する

**Domain Boundary** を Service/Action レイヤーおよび Policy レイヤーと定義し、`.claude/rules/10-laravel.md` にラベルではなく明示的なMAY / MUST NOTリストとして記載する。Controllerは `FormRequest` によるバリデーション、`authorize()` の呼び出し、Service/Actionの呼び出し（ちょうど1つ）、レスポンスの整形のみを行ってよい。`DB::` の呼び出し、Eloquentの書き込みメソッドの呼び出し、ロールのインラインチェック、複数エンティティにまたがる判断は行ってはならない。

この枠組みは意図的に「Controllerを正しく書く」ことではなく「Controllerが誤っていてもシステムが正しさを保つ」ことをゴールとしている。

「model層」ではなく「Domain Boundary」という語を使うのは、*model* という語がフレームワークによって意味が異なるためであり、また本テンプレートではEloquent Modelはスキーマとリレーションのみを保持し、実施（enforcement）はService/Actionが担うためである。これにより、新しい契約は既存の「Modelにビジネスロジックを書かない」というルールと矛盾せず整合する。

`.claude/agents/tdd-implementer.md`——実際に実装コードを書くエージェントであり、`10-laravel.md` がGreenフェーズに到達する実際の経路——はこの契約を直接名指しする。

### 2. 機械的に発見可能な半分を検知する

`.claude/hooks/domain-boundary-check.sh` を追加し、`/review` のStep 0で `review-score.sh` と並べて実行する。純粋なgit + awkでAI呼び出しなし、対象範囲のControllerに対して1パスで走査する。`db-access`、`eloquent-write`、`role-check` の指摘に加え、メソッド単位の分岐密度ヒューリスティックを報告する。指摘があればexit 1を返すため、プロジェクト側でCIやpre-commitフックのゲートに利用できる。`/review` はこの出力をレビュー材料として扱い、失敗として扱わない。

### 3. 行ではなくファイルを優先度付けする——priorityシグナル

行単位の指摘を並べただけのリストは「何かがおかしい」ことは伝えるが「どこから読むべきか」を伝えない。ブラウンフィールドのコードベースではこのリストは長くなる。そこでスクリプトは、ファイル単位で **書き込みが存在し、かつインラインのロールチェックが存在し、かつファイル内のどこにも `authorize()` / `Gate` 呼び出しがない** という組み合わせも報告する。これは、オブジェクトレベルの認可チェック漏れが隠れやすい形——ファイルが書き込みをすべて手書きのガードだけで守り、Policyがまったく関与していない——である。

このシグナルは事前に設計されたものではなく、検証の過程で導出されたものである。実プロジェクトで指摘されたControllerを1つ読んだところ、実際のIDORが見つかった。ネストしたルートが `{mentoringSession}` と `{sessionLog}` をそれぞれ独立に束縛しており（このプロジェクトは `scopeBindings()` を一切使っていない）、手書きのガードは実行者を*親*セッションに対してのみ確認しており、ログがそのセッションに属することは確認していなかった——そのため、あるセッションの正当なメンターが別セッションのログを編集・削除できてしまう。上記の組み合わせがこのファイルを特定し、同じコードベースで**21個のControllerにまたがる102件の行単位の指摘を1ファイルまで絞り込んだ**。それが実際に欠陥を含んでいたファイルである。

このスクリプトはバグそのものを見ることはできない——*存在しない*チェックはパターンにマッチしない。どのファイルを最初に読むべきかを示すだけであり、それがパターンマッチングで買える正直な限界である。

## Rationale

- 列挙型の契約は実行時コストもメンテナンスコストもかからず、すでに存在する経路を通じてコード生成エージェントに届く——そのため、次にControllerを生成する時点から即座に効果を発揮し、ユーザー側の新しいセットアップは不要である。
- 検知は決定的かつローカルであり、`meta/adr/ADR-0009-review-escalation-mechanism.md` の「ゼロコストで実行できるチェックはAI呼び出しに依存すべきではない」という考え方と一貫している。
- 計測コスト: 実プロジェクトの21個のControllerで0.59秒、300Controller・44,400行の合成ツリーに対する `--audit-all` で1.1秒、通常の差分スコープ実行で0.26秒。ファイルリストを1ファイルにつき1回の `grep` プロセスでフィルタしていた初期案は、同じ300Controllerに対してWindows/Git Bashで15.8秒かかった——リストは現在1パスでフィルタされており、この制約（ファイルごとのプロセス起動を避けること）がスクリプトの実装方針を決めている。

### 採用しなかった代替案

- **フルDSL＋パーサー/コンパイラ（MulmoClaude/MulmoTerminal的な形）**: アイデアとして最も強力で、違反を事後に検知するのではなく構造によって未然に防げる唯一の案。本リポジトリはドキュメントとルールを配布するものであり、コード生成ツールチェーンではないため、現時点では不採用とする。文法・パーサー・CI統合の構築と保守は別プロジェクトに相当する。ダウンストリームのプロジェクトがスキーマ/権限生成の機械的強制を必要とする場合に再検討する。
- **不変条件宣言ループ**（`data-model.md` に不変条件を宣言 → Redフェーズでのテストカバレッジを要求 → Gate 4で承認）: **却下ではなく保留（deferred）**とする。その価値——数ヶ月後に機能追加で失われがちなビジネスルールのセッションをまたいだ記憶——は本物だが、コストは変更のたびに発生する一方、恩恵はずっと後になって現れる。さらに構造的な穴もある。テストはある振る舞いが*存在する*ことは強制できても、それが*特定のレイヤーに存在する*ことは強制できない。HTTP経由のFeature Testは、チェックがControllerにあってもServiceにあっても通ってしまうためである。これを塞ぐにはService/Actionに対するUnit Testを追加で必須化する必要があり、`.claude/rules/30-testing.md` のFeature Test優先方針・CRUD網羅の抑制ルールと衝突する。プロジェクトが真にクロスエンティティな不変条件を蓄積した時点で再検討する。同じ分析を後で繰り返さないよう、ここに記録しておく。
- **常時読み込みの新規ルールファイル（`05-architecture.md`）**: 不採用。すべてのセッションの読み込み対象を増やしてしまい、`10-laravel.md` はすでに実装に到達する経路上にある。
- **`review-score.sh` へのマージ**: 不採用。そのスクリプトは「差分をスコアリングしてレビューの深さを決める」という単一の責務を持っており、パターンlintを混ぜると契約が曖昧になり、両者を独立にチューニングできなくなる。
- **Repositoryレイヤー**: 不採用。`.claude/rules/20-mysql.md` がEloquent Builderを直接使う方針にコミットしていることと矛盾する。

## Consequences

### メリット

- この禁止事項がAI・スクリプト・人間レビュアーのいずれによってもチェック可能になる。
- priorityシグナルにより、長く平坦な指摘リストが短い「まず読むべきリスト」に変わる。これがブラウンフィールドの既存コードベースでもこのチェックを実用的にしている。
- `--stats` はトレンド化可能な数値（指摘件数・ヒューリスティック警告・priorityファイル数）を返し、境界が守られているかを定量的に見る唯一の手段になる。
- 新しいコマンドの導入は不要——`/review` のStep 0はすでに存在する。

### デメリット・リスク（既知の限界）

`ADR-0008-tdd-e2e-harness-tooling.md` がこのハーネスのサブエージェント分離について「本質的な強制力ではない」と率直に開示しているのと同じ姿勢で、以下を明記する。

- **これは検知するだけで、防止はしない。** 違反コードが書かれること自体を止める仕組みはない。
- **典型的な違反はこの仕組みには見えない。** プレーンなPHPで書かれたクロスエンティティな判断——`if ($order->items->sum('qty') > $product->stock) { ... }`——には識別可能なトークンが存在しない。分岐密度ヒューリスティックはこのケースに対する粗い代理指標であって検出器ではない。クリーンな実行結果はクリーンなControllerの証拠にはならない。
- **「ちょうど1つのService/Action」はカウントルールであり**、パターンマッチングでは表現できない。
- **スコープの穴**: ロジックが基底Controller・trait・ルートクロージャに移されている場合、Controllerパスのglobの対象外になる。`merge-base` によるスコープ限定のため、`--audit-all` を意図的に実行しない限り既存のControllerは検査されない。
- **パスの前提**: デフォルトのglobは `app/Http/Controllers/` である。独自のパスを追加しないモジュラー構成やDDD構成は0ファイルとしてスキャンされ「クリーン」と報告される——スクリプト自身のコメントでも警告されている、誤った安心感である。
- **ブラウンフィールドへの導入は積み残しを可視化するのであって、ブロッカーにはならない**: 上記で計測した実プロジェクトはフルオーディットで103件の指摘を出した。日々の差分スコープの実行は小さいままである。
- **チューニングは前提**: 閾値・パスのglob・3つのルールグループはすべて環境変数であり、意図的にServiceレイヤーを持たない小規模プロジェクトはpersistenceグループを無効化できる。
- **`.claude/hooks/` は本リポジトリにおける命名慣習であり、Claude Codeに登録されたライフサイクルフックではない**——`.claude/settings.json` による配線は存在しない。ここに置かれたスクリプトは `/review` から明示的に呼び出される。
