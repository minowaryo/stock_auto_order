# ADR-0013: スキルとコマンドの使い分け、および単体エクスポートの慣行

## Status
Accepted

## Date
2026-09-28

## Context

本ハーネスが提供するAIエントリポイントは、当初すべて `.claude/commands/`（`/adr`、`/review`、`/tdd`、`/generate-mock`、`/generate-e2e-test`、`/commit`）に置かれてきた。Claude Codeは現在 `.claude/skills/<name>/SKILL.md` にも対応しており、呼び出し方自体は `/<name>` でどちらも同じである。実質的な違いは1点のみ：スキルはfrontmatterに `description` を持ち、状況が合致すればAIが自分の判断で発動できる。コマンドは人間が明示的にタイプした時のみ実行される。

以下の2つの問いが繰り返し議論されながら、明文化された答えがなかった。

1. 新しいエントリポイントを追加するとき、どちらに置くべきか？
2. 1つのエントリポイントを、このリポジトリの外の相手に渡すとき、コピーがオリジナルと乖離しないようにどう共有するか？

問い2には本ハーネス固有の事情がある。リポジトリ内バージョンはGate番号・`meta/adr/` のパス・`.claude/rules/` のファイルなど、テンプレート外では意味を持たない参照を含むため、共有版ではそれらを取り除く必要がある。また逆に、リポジトリ内バージョンでは書く必要のなかったこと——このエントリポイントがいつ適用されいつ適用されないか、なぜ存在するか——を書き足す必要がある。リポジトリ内では隣接するルールファイルがそれを担っているが、共有先の相手はそれを持たないためである。したがってエクスポート版は単なるコピーではなく、双方向に別物のファイルになる。

## Decision

**新しいエントリポイントの判断基準:**

- **「実行し忘れる」ことが失敗モードならスキルにする。** `.claude/skills/<name>/SKILL.md` に置き、`description` はそのスキルが発動すべき状況だけに絞って書く。
- **「タイミングを誤って実行する」ことが失敗モードならコマンドにする。** `.claude/commands/<name>.md` のまま `description` は付けず、実行は常に人間の明示的な行為として残す。

**既存の6つのコマンド（`/adr`・`/review`・`/tdd`・`/generate-mock`・`/generate-e2e-test`・`/commit`）は全て `.claude/commands/` に残す。** いずれも基準上「コマンド」側に該当し、移行すると `CLAUDE.md`・`README.md`・`.claude/rules/`・`docs/ai-context/common-commands.md` の相互参照を全て書き換える必要が生じる一方、機能的な利点はない。

この基準は、既に導入済みの5つのスキルにも一致している：`prepare-merge`（マージの機会を逃す/雑に済ませる失敗）、`systematic-debugging`・`verification-before-completion`（AI自身が思い出さないと発動しない自己規律）、`grill-me`（Gate 1前のインタビューを始め忘れる）、`regenerate-traceability`（トレーサビリティマトリクスが「気づかないうちに陳腐化する」——タイミングを誤って再生成することでは失敗しない）。

**単体エクスポートはビルド成果物であり、追跡対象ファイルではない。** リポジトリ外で共有するために抽出したエントリポイントは `dist/skills/<name>/SKILL.md` に書き出し、これは `.gitignore` 対象とする。リポジトリ内バージョンが唯一のソース・オブ・トゥルースであり、エクスポート版は共有したくなった時点でそこから再生成する。

## Rationale

この基準を「重要かどうか」ではなく「失敗モード」で組み立てているのは、重要性では判別できないためである——`/review` と `regenerate-traceability` はどちらも重要だが、必要な扱いは正反対である。`ADR-0009` はすでに「`/review` の実行自体は意図的に自動化しない」という決定（Option A）を下している：レビュー強度は自動で適応するが、レビューするかどうか自体の判断は人間に残す。`/review` に `description` を付けることは、この決定を静かに覆すことになる。同じ論理が `/tdd`（自動発動させるとGate 4の承認ポーズを飛ばしてしまう）、`/generate-mock`（Gate 1〜2の間でのみ有効）、`/commit`（コミットは常に人間の承認1回を経由する——`.claude/rules/70-git.md` §4）も保護している。

`/generate-e2e-test` は名指しする価値のある近い例である：これはすでに `/tdd` の手順6から該当時に自動実行されているため、`description` を付けるとトリガー経路が2つになり、調整されないまま重複するだけであり、欠けているものを補うことにはならない。

### 採用しなかった代替案

- **一貫性のために既存6コマンドを全てスキルへ移行する。** 得られる利点は一貫性のみであり、コストは6ファイルの相互参照の総ざらいと、`/review` や `/tdd` に `description` を付けることでゲートが静かに壊れるリスクである。Gateを浸食する一貫性には価値がない。
- **単体エクスポートをリポジトリで追跡する（例: `dist/` をコミットする）。** 同じ指示のコピーが2つコミットされると乖離が起き、しかもその乖離は不可視である——両者が食い違っても何も失敗しないため、誰かが古い方を共有するまで誰も気づかない。エクスポートを未追跡のままにしておけば、その場で編集して静かに再コミットすることができなくなる。
- **リポジトリ内ファイルをそのまま共有する。** 受け取った相手は、自分のプロジェクトには存在しないGate番号や `meta/adr/` のパスへのダングリング参照を抱えることになる。取り除く作業は省略できないため、エクスポート版は本当に別物のファイルとなる。

## Consequences

### メリット

- エントリポイントを追加するたびに「スキルかコマンドか」を再議論しなくてよくなる
- `ADR-0009` と `.claude/rules/00-global.md` が守っているGateが、エントリポイントが自律的な発動トリガーを獲得することで迂回されることがなくなる
- 1つのエントリポイントを、リポジトリ側に2つ目のコピーを増やすことなく共有できる

### デメリット・リスク

- `dist/` はソース側が変わると自動的には追随せず、静かに陳腐化する。これは許容する——エクスポートはコミットのたびの作業ではなく共有する瞬間の作業であり、再生成すべきタイミングは誰かがそのファイルを求めた瞬間である
- 境界事例では判断に人間の判断力が必要になる。「忘れる」「タイミングを誤る」の両方が失敗モードであるようなエントリポイントには機械的な答えがない——その場合はコマンドとして書き、ルールファイルからも言及することで、自律的な発動トリガーを持たせずにリマインドの仕組みだけを持たせる
