# ADR-0014: サードパーティ由来のスキル概念の自社導入（Trial）

## Status
Trial — 下記「ロールアウト追跡」を参照。しばらく使って問題が報告されなければAcceptedに昇格させる。
逆に特定の項目だけ摩擦が大きければ、その項目だけ個別にロールバックする。

## Date
2026-09-28

## Context

ユーザーから提供された「Superpowers」（Claude Codeプラグイン、`obra/superpowers`）と本ハーネス自身の
Gateベースのワークフローとの比較検討がきっかけとなった。検証の結果（GitHub Issue #1480、#1456、#2377）、
SuperpowersのSessionStartフックが毎セッション約1,300トークンを `<EXTREMELY_IMPORTANT>` タグで包んで
強制注入すること、およびそのTDDスキルがRed → 承認 → Green の境界を機械的に強制していないこと
（Issue #384、#2372）が確認された——いずれも本リポジトリ自身のCLAUDE.mdルールやGate 4の人間承認要件と
衝突するリスクがある（Superpowers自体を導入しないという判断の詳細は `ADR-0015` を参照）。

この検討の中で、何も導入せずに取り込む価値のある、本ハーネスに実際に欠けている4つのアイデアが
見つかった。

1. `docs/ai-context/known-pitfalls.md`（**既知**の問題のみをカバーする）を超えて、不明瞭なバグに
   対する調査規律を体現するスキルが存在しない。
2. 「テストが通った」ことの確認は、`.claude/rules/30-testing.md` のGreenフェーズ後の `run` スキル
   推奨という狭い形でしか行われておらず、あらゆる「完了」宣言を検証する一般的な習慣がない。
3. `.claude/rules/30-testing.md` はRed → Green → Refactorのサイクルは述べているが、個々のテストが
   「良い」テストなのか、それとも空虚（vacuous）なテストなのかについてはほとんど述べていない。
4. Gate 1前の `docs/product/requirements.md` のドラフト作成には構造化された手法がない——別の
   `mattpocock/skills` リポジトリの `grill-me`/`grilling` スキル（一問一答形式のインタビュー）が
   まさにこのギャップに対応していることが分かった。

## Decision

これら4つのアイデアを、インストールするプラグインとしてではなく、自社で書き直した
`.claude/skills/` エントリまたは既存ルールファイルへの編集として、**Trial** と明記した上で
一度にまとめて採用する:

1. 新規スキル `.claude/skills/systematic-debugging/SKILL.md`
2. 新規スキル `.claude/skills/verification-before-completion/SKILL.md`
3. `.claude/rules/30-testing.md` への新規「テストの質に関するヒューリスティクス」節の追加
4. 新規スキル `.claude/skills/grill-me/SKILL.md`（`mattpocock/skills` から翻案・出典明記）

分類: 項目1・2・4は「実行し忘れる」ことが失敗モードであり、「タイミングを誤って実行する」ことでは
ない自己発動するスキルである。項目3はルールファイルの編集であり、エントリポイントではない。

### ロールアウト追跡

| 項目 | 状態 | 備考 |
|---|---|---|
| `systematic-debugging` | Trial | 些細な修正を過度に手順化しないか注視する |
| `verification-before-completion` | Trial | 自己チェックのみのため最も摩擦が小さいと想定 |
| テストの質に関するヒューリスティクス（`30-testing.md`） | Trial | 平文の追記のみで新規エントリポイントではない |
| `grill-me` | Trial | 摩擦リスクが最も高い——AI自身の内部規律を厳しくするだけの他3項目と違い、人間との
インタラクションのパターン自体を変える唯一の項目である |

この表（および上記Statusの行）は、バッチをある程度使ってみて判断できるようになった時点で更新する。
いずれか1項目だけが本当に摩擦を生んでいる場合は、バッチ全体ではなくその項目だけをロールバックする。

## Rationale

自社で書き直すことで、Superpowersで検証済みのセッション注入・TDD非強制のリスク（`ADR-0015`）を
回避しつつ、4つの実在するギャップを埋める。4つとも小さく、テキストのみの追加である——新規依存関係も
プラグインマーケットプレイスもスクリプトも不要である。

### 採用しなかった代替案

- **Superpowersプラグインを導入し、都合の良い部分だけを取り出す。** 不採用——`ADR-0015` を参照。
  セッション注入とTDD非強制のリスクはプラグイン全体に及ぶものであり、欲しい部分だけを切り離せない。
- **4項目を1つずつ、間に観察期間を挟みながら段階導入する。** 検討したが、この規模の変更としては
  過剰なオーバーヘッドと判断した——4項目のうち3つ（`systematic-debugging`、
  `verification-before-completion`、テストの質の追記）はAI自身の内部規律を厳しくするだけで
  人間とのやり取りの仕方は変えない。有意に異なるリスクを持つのは `grill-me` だけであり、
  それは上記のロールアウト追跡表で個別に明示することとし、バッチ全体をそれに合わせて
  ゲートすることはしなかった。

## Consequences

### メリット

- 実在するギャップを埋める：一般的なデバッグ規律や、完了検証の一般化を担う既存スキルは
  存在しなかった。
- `grill-me` により、Gate 1の要件定義ドラフト作成に、無秩序な会話ではなく再現可能な手法が
  与えられる。
- 新規依存関係・インストール手順はゼロ——プレーンなマークダウンであり、本リポジトリ内で
  レビュー・保有される。

### デメリット・リスク

- `grill-me` は無差別に使うと要件定義作業が遅く・うるさく感じられる可能性がある——SKILL.md側で
  本当に曖昧な点にのみ絞るようスコープを限定している。
- `systematic-debugging` は些細な1行のtypo修正にまで「再現してから直す」を適用すると
  過度に儀式化する可能性がある——SKILL.md側でトリガーを「不明瞭・非自明なバグ」に限定している。
- 4項目とも「Trial」のままであるため、相互参照もTrialとして明記し、昇格するまではその旨を残す。
