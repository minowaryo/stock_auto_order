# ADR-0016: Gitワークフロー — 短命ブランチ、`--no-ff` マージによる記録、マージ前チェックの区分

## Status
Accepted — マージ前チェックの閾値と `prepare-merge` スキルは **Trial**（`meta/adr/ADR-0014` 参照）

## Date
2026-09-29

## Context

- 本テンプレートを使うチームの多くは1人開発で、1プロジェクトあたり2〜3人が一般的、
  まれに中規模（〜5〜8人）となる。主なホスティングはGitLabだが、GitHubでも動き続ける必要がある。
- 社内にはMerge/Pull Requestの文化がない。現時点でそれを導入するのは摩擦が大きすぎると判断したため、
  ブランチ・コミット・マージだけで使える記録を残す必要がある。
- 本ADR以前のテンプレートは、「小さなコミット」という表現が3箇所にありながらコミット単位を
  定義しておらず、ブランチ作成・`main` への直接コミット・pushのタイミング・マージ方法に関する
  ルールもなかった。また「AIは明示的な指示があった場合のみcommit/pushする」というルールは
  `GLOBAL_CLAUDE.md` とサブエージェントのファイルにしか書かれていなかった。force pushの禁止は
  `AGENTS.md` にしか存在しなかった。PRのプロセスが存在しないにもかかわらず、docsは「PR」について
  言及していた。
- Superpowersプラグイン（ADR-0015で全体としては却下）は一部の開発者環境にインストールされている。
  そのGitスキルはタスクごとのAI自動コミットと、AIが実行するローカルマージを規定しており、
  上記のルールと衝突する。

## Decision

ルールは `.claude/rules/70-git.md` に一度だけ記述し、他のすべてのファイルはそこを参照する。
手順は `/commit`（`.claude/commands/commit.md`）と `prepare-merge` スキル
（`.claude/skills/prepare-merge/SKILL.md`）に置く。要約:

1. **ブランチ** — GitHub Flow風の短命ブランチ（`<type>/<issue-no>-<slug>`、
   2営業日以内、最長5営業日）。`main` への直接コミットはdocs/誤字修正のみの変更に限る。
2. **コミット単位** — 一文で説明できる、すべてのコミットでGreen、振る舞いの変更 /
   リファクタ / 整形を分ける、テストはそのコードと一緒。`/tdd` では Red + Green で1コミット、
   Refactorは別コミット。マイグレーションは単独のコミット。
3. **メッセージ** — 既存の `[type]: [summary]` 形式を、Conventional Commitsの最小サブセットとして
   扱う（`feat/fix/refactor/style/test/docs/chore`、破壊的変更には `!`）。本（日本語版）テンプレートは
   日本語チーム向けのため、件名・本文は日本語または英語で書いてよい（英語版テンプレートは英語のみ）。
4. **権限** — AIは提案した分割案に対する人間の承認1回を得てからのみコミットする
   （`/commit`）。pushは明示的な指示があった場合のみ（`ask`）。force pushは拒否。マージは
   `prepare-merge` が準備し、明示的な指示があった場合のみ実行する。
5. **マージ** — `git merge --no-ff`。テストはマージ結果に対して1回実行する。マージコミットには
   短い「なぜ」と `Merge-Check:` / `Review:` / `Tests:` トレーラーを付ける。このコミットが
   MRの説明文の軽量な代替となる。
6. **マージ前チェック** — `review-score.sh` に `MERGE_CHECK=` 行を追加し、3つの区分を設ける:
   `light`（スコア < 10、機密パスなし: テストのみ）、`recommended`（10〜29: `/review` を推奨）、
   `required`（≥ 30 または機密パスあり: `/review` 必須）。ブランチごとにマージ時に1回だけ実行し、
   コミットごとには実行しない。
7. **worktree** は並行セッションの場合のみ。タスクごとのサブエージェントレビューループは行わない。
8. **優先順位** — 本ルールはプラグインのGitスキル（Superpowers）より優先する。

## Rationale

### MRプロセスではなく `--no-ff` マージコミットを採る理由

- `git log --first-parent main` が機能単位の一覧（MR一覧が提供するもの）として読め、
  `git revert -m 1 <merge>` で機能を1ステップで取り消せる。
- ブランチ上で整理されたコミットが変更されずに `main` に残るため、コミット単位のルールが
  マージ後も効き続ける。
- GitLabのMRのデフォルトのマージ方法は「Merge commit」であり、同じ形の履歴を生む——
  将来MRを導入しても、履歴については何も変わらない。

### この閾値にした理由（キャリブレーション、2026-09-29）

社内のLaravelプロジェクト4件の実際の履歴を読み取り専用で計測した（マージ以外のコミット714件、
マージ92件、作者×日370件。スキャフォールドのコミットは除外）:

- スコア10 ≈ 約3ファイルで変更100〜150行、スコア30 ≈ 6〜8ファイルで350〜450行。
  行の重み0.05は、観測された1ファイルあたりの行数の比率に沿っている。
- 外部の目安: Google eng-practices「Small CLs」（〜100行は通常妥当、〜1000行は通常大きすぎる）↔ 10、
  SmartBear/Ciscoのレビュー研究（200〜400 LOCを超えると欠陥検出率が落ちる）↔ 30。
- 10では、100行以下の非機密な変更の89〜98%が `light` に分類される。5では55〜76%しか拾えず
  （誤字程度の作業に負担がかかる）、15では〜150行まで達する。
- 30は、400行超の単位の92〜93%を捉え、誤検知はほぼない（`required` のマージのうち200行以下は
  0〜2%）。25ではノイズが増え、40では400行超の単位の23〜36%を通してしまう。
- 機密パスは単位の7〜11%に現れる（主にマイグレーション、次いでPolicy）。機密ルール単独で
  `required` に押し上げられるのは1〜2%にすぎないため、このルールのコストは小さい。
- コミットされたロックファイル・minify済みアセット・フォントが行数の水増しの主な原因だったため、
  スクリプトはそれらを除外するようにした（`public/js/` は除外しない。プレーンBladeのプロジェクトでは
  手書きされるため）。

### 不採用 / 見送りとした代替案

- **Squashマージ** — MRのボタンがあってこそ意味がある。整理されたコミットを捨ててしまう。
- **Rebase / fast-forwardマージ** — 機能単位のまとまりが失われる。機能の取り消しにN回のrevertが必要になる。
- **MR/PRプロセス（Ship / Show / Ask）** — 見送り: まだMR文化がなく、マージコミットがすでに
  なぜ / 検証内容 / リスクを記録している。非同期レビューを望む開発者が2人以上アクティブな
  プロジェクトが出てきたら再検討する。
- **GitLab CI** — 見送り: MRなしではpush後に通知することしかできない。runnerのセットアップ
  （セルフホストGitLab）とスタックごとの設定が必要。MRと合わせて導入する。
- **ブランチ保護** — MRと合わせて見送り（GitLab Freeは、デフォルトでデフォルトブランチを
  force pushから保護している）。
- **バージョン管理された警告のみのマージフック（`.githooks/`）** — 見送り: フックファイル2つ、
  `review-score.sh --target` オプション、`.gitattributes` のルールと実行ビット、セットアップ手順が
  必要になるが、AIを介したフローですでにカバーされている経路のためである。
  AIセッション外でのマージが日常的に起こるようになったら再検討する。
- **タスクごとのAI自動コミット（Superpowers）** — 明示的な指示のルールと衝突する。
- **タスクごとのサブエージェントレビューループ** — AIコストのため（ADR-0009に準じる）。
- **git-flow** — バージョン管理された複数リリースのソフトウェア向けである。
- **commitlint / husky / コミットscope** — リリースパイプラインがない状況ではオーバーヘッドになる。

## Consequences

- 過去のサンプルでは、`required` がマージの約46%をカバーすることになる——これは閾値ではなく、
  過去のブランチがどれだけ大きかったか（43%が400行超）を反映したものである。それを下げるのは
  短命ブランチとコミット単位のルールである。Trialのフィードバックをもとに閾値を再検討する
  （候補: `create_*` マイグレーションの重みを下げる、docsのみの差分の重みを下げる）。
- 人間が直接 `git merge` を実行した場合、区分の自動警告は出ない。それでもルールは適用される。
- `settings.json` のパーミッションルールはガードレールであってセキュリティ境界ではない。
- `GLOBAL_CLAUDE.md` と `.claude/agents/*` は、それぞれ独自の短いcommit/push禁止の記述を残す
  （それらの読み手は `70-git.md` を読み込まないため）。
