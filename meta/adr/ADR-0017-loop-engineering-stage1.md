## Date

## Context

設計メモ（EN版の `meta/design/loop_engineering_design_memo.txt`、日本語）は、このハーネスを「人間の
ゲートの内側でAIがコードを書く」形から「Loop Engineering」へ発展させることを提案している。Orchestrator
+ Coder + Reviewer が 実装 → 検証 → レビュー を自分たちで繰り返し、その範囲を決定的なゲート、ロックした
受け入れテスト、読み取り専用で証拠に基づくレビュアー、権限の段階、停止条件で区切る、という形である。

このメモを8回の調査・レッドチームと3回のツール採用検討で確認した（2026-10-01〜10-03）。この ADR を
動かした所見:

- **リスクは現実にある。** 仕様とテストが矛盾する課題では、最先端のモデルでも約半数の実行で不正をする。
  多くはテストの書き換えで、禁止しても起きる。テストを読み取り専用にするとこれは止まり、モデルに「矛盾を
  報告して止まる」という明示的な選択肢を与えると、あるモデルの不正は 54% から 9% に下がった
  （ImpossibleBench、arXiv 2510.20270）。
- **このハーネスは、まさにその点をプロンプトに頼っている。** `tdd-implementer` は `test-writer` と同じ
  ツールを持ち（`.claude/agents/*.md`）、「`tests/` を編集しない」は指示でしかない。Gate 4（Red の
  テストを人間が承認する）が唯一の防御で、実際には形式的になりがちである。
- **メモのアーキテクチャ全体は、まだ小さなチームには合わない。** planner / generator / evaluator 構成の
  ハーネスは単独エージェントの約22倍のコストがかかる（Anthropic「Harness design for long-running
  apps」）。ループを大規模に回しているチーム（Stripe、Spotify、Cognition）は、オーケストレーションを
  コードに置き、書き手を1人に保ち、合否を決定的なチェックで判定している。ネイティブWindowsには Claude
  Code の OS サンドボックスがないので、プロセス内のブロックはサブプロセス経由で回避できる。チェックが
  信頼できるのは、改ざんされた結果を後から拒否できる場合だけである。
- **中核を満たす既存ツールはない。** Probity（`ADR-0007`）は書き込んでいるエージェントを区別できず、
  `enforceTdd()` はサブエージェントにも Pest の構文にも対応しない。hookify もエージェントで条件分岐
  できない。`/goal` はトランスクリプトを読む小さなモデルが判定する。組み込みのループはどれも人間の
  ために一時停止できない。周辺の部品（Pest/PHPUnit の strict モード、各ツールの JSON/JUnit 出力、
  `--json-schema`、Stop フック、予算、worktree）はすでに使える。
- **Claude Code 2.1.278 で確認（2026-10-03）:** `.claude/settings.json` に登録した PreToolUse フックは、
  そのサブエージェントによる書き込みでは `"agent_type":"tdd-implementer"` を受け取り、メインセッションの
  書き込みでは `agent_type` を受け取らない。同じフックをサブエージェントの frontmatter で宣言した場合は、
  `claude -p` の下で実行され**なかった**。`tool_input.file_path` はWindowsの絶対パスで届く。

## Decision

### ゴール

AIが 実装 → 検証 → レビュー を繰り返してよい。ただしTDDの規律と人間の判断はそのまま保つ。人間が
持つもの: ユースケースの承認、重要なテスト（認可、バリデーション、回帰、ユーザーに見える挙動）の承認、
マージの判断。機械が確認するもの: テストが改ざんされていないこと、ゲートを通過したこと、同じ失敗の
繰り返しでループが止まること。**TDD そのもの（Red → Green → Refactor）はどの段階でも譲らない。**

### 原則

1. TDD は変わらない。変わるのは、その規律を誰が確認するかだけである。
2. 確認は機械に、判断は人間に。
3. 改ざんを不可能にするのではなく、無意味にする（検出して拒否する）。
4. 段階を進めるのは計測した結果があるときだけ（各段階に終了条件がある）。
5. 組み込み・既存のツールを先に使い、どれも満たさない小さな部分だけを作る。

### 段階

| 段階 | 範囲 | 終了条件 |
|---|---|---|
| 1 — この ADR | テンプレート内での機械によるTDDの規律（下記） | フックとそのテストが通る。ブロックした試みが記録される |
| 2 | 決定的な `gate.sh` + 証拠 JSON。証拠を読む読み取り専用レビュアー。実験は2部構成 — 2a で無人のチェック（仕込んだ矛盾、シャドーリプレイ、レビュアー用の仕込み）、2a の結果が有望な場合のみ 2b で実際の Laravel プロジェクトでの2週間の人間による A/B | テスト・仕様の弱体化の見逃しがゼロ。流出した欠陥が増えない |
| 3 | 上限付きの Green ループ（ゲートを実行する Stop フック）。構造化したレビュー結果。Gate 4 の `lite` / `standard` プロファイル | タスクあたりの人間の時間が 30% 以上減る。弱体化の見逃しがゼロ。コストが予算内 |
| 4 | JP版・社内版への移植。Codex との同等性。トレーサビリティの AC / Evidence 列 | 3つのリポジトリと Codex で同じ挙動 |
| 5（条件付き） | エージェントの外から実行する自律ループ（サンドボックス、予算付き）。必要な場合のみ別リポジトリ | 段階3が成功し、なお実際のギャップが残る場合のみ開始 |

#### 変更する側にも決定的なツールを（段階2〜3）

これは `docs/development/ai-workflow.md` の一般的な役割分担（「決定的なツールを先に」）をループに
当てはめたものである（改善の全体像はEN版の `meta/design/template-improvement-directions.md`）。段階1
までは、決定的なツールは結果を*判定する*だけである。大規模な移行の報告は、それらが変更を*作る*側にも
回るべきで、LLM はそれらにできない部分だけを担うべきだと示している: Google（arXiv 2504.09691 —
39件の移行で、変更箇所を自動で見つけた後にコード変更の 74.45% を LLM が生成、総時間は約50%減、すべての
変更を人間がレビュー）と Slack（Enzyme → React Testing Library: LLM のみで成功率 40〜60%、AST の
codemod のみで 45%、組み合わせで 80% — それでも移行時間の削減は 22% のみ）。ここでの適用:

1. **機械で直せる失敗は LLM に回さない。** ゲートが失敗したら、まず自動修正（`pint`、任意で Rector）を
   実行し、残った失敗だけを実装者に返す。ループの回数とコストが減り、「スタイル修正のついで」の変更も
   起きない。
2. **場所は機械が見つけ、変更は LLM がする。** 決定的な検出器（`domain-boundary-check.sh --audit-all`、
   Larastan、Rector の dry-run）が作業リストを作り、LLM が1件ずつ直し、ゲートが確認する。範囲と完了の
   両方が機械的に決まる。
3. **段階2の実験に移行型のタスクを含める。** 挙動を変えない作業（非推奨 API の置き換え、Larastan の
   レベル引き上げ、Domain Boundary の積み残し）は、報告されたどの事例でもループが元を取れる領域である。
   既存のテストが判定基準になり、すべてロックできる — 新しいテストがないので改ざんの余地が最も小さい。
   これはTDDの Refactor フェーズ（前も後も Green）なので、TDDの規律は変わらない。

Slack / Google の時間削減（22% / 約50%）は、人間がすべての変更をレビューし続けた上での数字であり、
レビューがボトルネックであり続けることを示している: 計測した結果があるときだけ進める。

段階2〜5は、それぞれ作業開始前に独自の ADR（またはこの ADR の追記）を持つ。Gate の定義
（`00-global.md` / `SETUP.md` / `AGENTS.md`）は段階3より前には変えない。

### 誰が何を変更できるか（段階1）

段階1の仕事は1つ: **実装者は、自分が到達を求められているゴールを動かせない。** ロックは Green の間の
`tdd-implementer` だけに適用され、他の全員はこれまでどおり作業する。

| 誰 | `tests/` | 仕様（`docs/product/`） | アプリケーションコード |
|---|---|---|---|
| 人間 | いつでも | いつでも（変更要求のフローを通して） | いつでも |
| メインセッション（人間と対話している） | 人間の指示で | 人間の承認を得てドラフト・修正（Gate 1〜2、変更要求） | 可（例: Refactor） |
| `test-writer`（Red） | 書く — それが役割 | 読むだけ | 不可 |
| **`tdd-implementer`（Green）** | **ロック** | **ロック** | 書く — それが役割 |

テストや仕様の正当な変更に特別なコマンドは要らない: 人間が判断する → Red からやり直す → Gate 4 で承認
する。承認時に新しいスナップショットが取られる（項目5）。*（2026-10-05 に簡素化: 以前のレビューで提案された
`/tdd relock` / `/tdd abandon` コマンド、ロックの有効期間、ロック対象パスの設定ファイルは、運用の負担が
大きすぎるとして取りやめた。ロックが実装者だけを縛るなら、どれも必要ない。）*

### 段階1の項目

1. **SPEC_CONFLICT** — 承認済みのテストと仕様が矛盾する、または両方を満たせない場合、`tdd-implementer`
   は回避策を取らずに止まって報告する。
2. **停止条件** — Green の試行は1サイクルあたり最大3回。同じ失敗が2回続いたら人間に上げる（`/tdd`）。
3. **テストロックのフック** — `.claude/settings.json` の PreToolUse フックが、`agent_type` が
   `tdd-implementer` のとき `tests/` 配下への `Write` / `Edit`（とそこに書き込む Bash コマンド）を拒否し、
   拒否を1件ずつ JSONL のログに追記する。照合の前にパス区切りを正規化する。メインセッションと
   `test-writer` には影響しない。
   実地で確認（2.1.278、`claude -p`）: 拒否は exit 2 + stderr でも、JSON の
   `permissionDecision: "deny"` でも効く。メインセッションの書き込みは通る。サブエージェントからの `Bash`
   呼び出しにも `agent_type` が付き、`file_path` だけを確認すると `echo x > tests/a.txt` が通ってしまった
   — そのためフックは Bash の `command` 文字列も調べる必要がある。bash の組み込み機能だけで書いている
   （`grep` / `sed` のサブプロセスなし）: Windows の Git Bash で1回あたり約83ms（`grep` / `sed` を使うと約500ms）で、
   すべてのツール呼び出しで実行される。
   仕組みは OS に依存しない（Claude Code のフック + bash スクリプト。Windows では Git Bash で、これは
   すでに前提条件）。最も弱いプラットフォーム — OS サンドボックスのないネイティブWindows — で成り立つ
   ように設計し、macOS / Linux / WSL2 ではサンドボックスで強化できる。
   同じフックは `tdd-implementer` に対して、git でインデックスや作業ツリーを変える Bash コマンド
   （`git add`、`commit`、`stash`、`checkout`、`restore`、`reset`、`rm`、`mv`、`apply`、`update-index`）と
   `git config` も拒否する。`tdd-implementer.md` から「`git add` は可」という許可を外す。実装者には
   ステージングも git の設定も必要ない。*（2026-10-03 追記。`git config` は 2026-10-05 に追加。）*
   ロック対象のパスは `tests/` **と `docs/product/`**（ユースケース、受け入れ基準、要件定義）である:
   仕様を編集できる実装者は、仕様を書き換えることで「完了」できてしまう（メモ §6、ゴールのハッキング）。
   また SPEC_CONFLICT の報告は `use-cases.md` からの原文引用と照合するので、仕様が動かない間しか機能
   しない。*（2026-10-03 追記。）*
   **タイムアウトしたフックは素通しになる**: 2026-10-03 に確認（2.1.278、Windows） — タイムアウトすると
   フックの拒否は捨てられてツール呼び出しが進み、stdout を開いたままの子プロセスはタイムアウトに関係なく
   その実行中ずっと呼び出しを止める。そのためロックのフックは速いままでなければならず（bash の組み込み
   機能のみ、外部コマンドなし）、子プロセスを実行中のまま残してはならない。*（2026-10-03 追記。）*
   フックは実装者に対して **サイクルの記録** もロックする: 拒否ログ（`logs/`、および Bash コマンド中の
   `audit.jsonl`）と承認スナップショット（パスに `claude-tdd` を含むもの。worktree の git ディレクトリも
   含む）。2026-10-07 に確認: それまでは実装者の `Edit .git/claude-tdd/approved/tests/…`、
   `Edit logs/audit.jsonl`、`echo x > logs/audit.jsonl` がすべて通り、実装者が自分の拒否記録を消したり、
   スナップショットのチェックが比較する基準を動かしたりできた。確認される側が書き換えられる証拠は証拠では
   ない。ルール名は `locked_evidence` で、専用のメッセージを返す。ゴールのロックと同じ限界がある:
   サブプロセスは書き込める。項目5が縮んだログを報告する。*（2026-10-07 追記。）*
4. **フックのテスト** — `meta/tests/`（テンプレート内部用。`review-score.test.sh` と同様）。
5. **Green の証拠（承認スナップショット）** — Gate 4 が承認されたら、`/tdd`（メインセッション）が
   `tests/` と `docs/product/` を `$(git rev-parse --git-path claude-tdd)/approved/`（`.git/` の中。
   コミットされない）にコピーする。Green の後、現在のファイルをそのコピーと比較する（`diff -r`）。変更・
   削除・追加があれば差分を人間に見せ、人間が判断するまでサイクルは進まない。これでフックから見えない
   書き込み（例: サブプロセス経由）を捕まえる。新しい Gate 4 の承認でコピーは置き換わる。
   素のコピーにする理由: 基準は、実装者が動かせるものに依存してはならない。`HEAD` は使えない（`lite` の
   Git プロファイルは Green の後にしかコミットしないので、新しい Red のファイルは未追跡）。実際の
   インデックスも使えない（改ざん後の `git add -A` — 2026-10-03 に再現）。一時インデックスを使った git の
   ツリーハッシュも使えない — **2026-10-05 に、clean フィルタ（`git config filter.x.clean …` +
   `.gitattributes`）で改ざんしたファイルが承認時と同じハッシュになることを再現した**。ファイルを直接
   比べる方法は git のフィルタを通らず、ハッシュではなく読める差分を人間に見せられる。*（2026-10-05 に
   書き直し。2026-10-03 のツリーハッシュ版を置き換える。）*
   `record` は `logs/audit.jsonl` のサイズも記録し、`verify` は承認後に書かれたすべての
   `agent_guard_denial` 行をそのまま表示する（1件もなければ、そう1行出す）。それまでは、ブロックされた
   試みが人間に届くのは実装者自身の報告に書かれていた場合だけで、モデルが自分のしたことを説明しても、
   それは実際にしたことの信頼できる証拠ではない（述べた推論が、実際に行動を決めたものと一致するとは
   限らない）。ログが外部の記録である。拒否は終了コードを変えない — ブロックされたので、ゴールは動いて
   いない — が、`/tdd` が人間に見せる。承認時より短いログは変更として報告する（exit 2）: 記録が書き
   換えられている。*（2026-10-07 追記。）*
6. **訂正の記録** — `ADR-0007`（Probity: サブエージェント / agent_type に非対応、Pest の構文を認識しない、
   依存関係が約834MB、自身の設定ファイルが保護されない）と `ADR-0015`（Laravel Boost に MCP のみの
   インストール方法ができた）に日付入りの更新メモを付ける。
7. **コマンドはモデルから呼び出せる** — Claude Code は `.claude/commands/*.md` を、ファイルに
   `disable-model-invocation: true` がない限り、モデルが自分で呼び出せるスキルとして扱う
   （code.claude.com/docs/en/skills）。これは `ADR-0009`（`/review` は常に人間が始める）、`/tdd` の
   Gate 4 での一時停止、`/commit` の背後にあるコミット承認のルールと矛盾する。また `ADR-0013` の前提
   「コマンドは入力されたときにしか実行されない」も崩す。テンプレートのすべてのコマンドに
   `disable-model-invocation: true` を付け（どれも `ADR-0013` の「間違ったタイミングでの実行が失敗の
   形」の側に入る）、`ADR-0013` に日付入りの訂正メモを付ける。テンプレートの `/review` は名前を変えない:
   名前を変えると、習慣で `/review` と入力した人間が組み込みの汎用レビューに送られ、review-score と
   Domain Boundary のチェックを飛ばしてしまう。2026-10-03 に確認（2.1.278、`claude -p`、3/3回）:
   プロジェクトの `/review` が組み込みの別名より優先され、素の「レビューして」という依頼でモデルが
   プロジェクトの `review` コマンドを自分で呼び出した（問題を確認）。この優先順位は**文書化されていない**
   （ドキュメントは `code-review` という名前のプロジェクトのスキルしか扱っていない）ので、Claude Code の
   アップグレードのたびに再確認するプラットフォームの事実として記録する。対話型の TUI では試していない。
   `.claude/settings.json` には `"skillOverrides": {"code-review": "user-invocable-only"}` も追加する
   （確認済み: モデルは組み込みのレビューを選ばなくなり、人間が `/code-review` と入力すれば実行される）。
   2026-10-03 に確認（2.1.278）: `.claude/commands/*.md` の `disable-model-invocation: true` はモデルからの
   呼び出しを止め（0/2）、コマンドの入力は引き続き効く。後のバージョンで変わった場合の代替:
   `"review": "user-invocable-only"` のような `skillOverrides` のエントリ。注意: Git Bash では
   `claude -p "/review"` が MSYS のパス変換で崩れる — PowerShell から試すこと。
   現在別のコマンドを起動している呼び出し元は、それをやめる必要がある。このフラグは、モデルが人間の代わりに
   起動することも止めるからである: `/tdd` のステップ6（「`/generate-e2e-test` を実行」）と
   `prepare-merge` のステップ1（「`/commit` のステップ1〜5を実行」）は「`.claude/commands/<name>.md` を
   読んでその手順に従う」に変える — フラグが止めるのは呼び出しで、ファイルを読むことではない。
   *（2026-10-03 追記。）*
8. **フックが導入先プロジェクトに届く** — `APPLY_TEMPLATE.md` の class C は現在、すでに
   `.claude/settings.json` を持つ導入先に `permissions` のエントリしかマージしない。`hooks` のエントリも
   マージするように広げる。そうしないと、既存コードベース導入パスでテストのロックが黙って消える。
9. **拒否ログ** — プロジェクトルートの `logs/audit.jsonl`（JSONL。拒否1件につき1行: 時刻、イベント、
   `session_id`、`agent_type`、ツール、正規化したパス — ファイルの内容は決して入れない）。git の管理外。
   `session_id` によって段階2で拒否とタスクを結び付けられる。パスは `GLOBAL_CLAUDE.md` のAI作業の監査ログの
   慣行（`logs/audit.jsonl`）に従う。各行はイベントの種類（例: `agent_guard_denial`）を持ち、ドキュメントで
   1行、これがAIエージェントの活動の記録であり、アプリケーション自身の `audit` ログチャネル
   （`storage/logs/audit.log`、`.claude/rules/40-security.md`）とは別物だと述べる。*（2026-10-03 追記。）*
10. **バージョンの確認** — 上記のプラットフォームの事実は PATH 上の CLI（2.1.278）で確認したが、同じ週の
   VS Code 拡張のセッションは 2.1.283〜2.1.284 で動いていた。フックに頼る前に、実際に使うバージョンで
   確認用のフィクスチャを再実行し、各プラットフォームの事実の横にバージョンを記録する。

段階1に意図的に**入れない**もの: 構造化したレビュー結果のスキーマ（まだ使う側がない）、あらゆる種類の
ハッシュ（項目5は素のコピーを使う）、ロック管理のコマンドやロックの有効期間、ロック対象パスの設定ファイル、
Gate 4 の変更、オーケストレーター、インストールするプラグイン。

## Rationale

TDD にとって最も重要な、プロンプトだけのルール — 「実装者はテストに触れない」 — を、黙って無視できない
チェックに変え、実装者に正当な出口（SPEC_CONFLICT）を与えて不正をする理由を減らすのが、実効性のある最も
安い変更である。どちらも現在の人間がゲートを持つフローで機能するので、Gate の定義は何も変える必要がなく、
どちらも後の段階が自らを正当化するために必要なデータ（記録された拒否）を生む。

### 採用しなかった代替案

- **メモのアーキテクチャ全体を今採用する**（4つのループ、14のスキーマ、Spec / Test / Permission の
  エージェント、コントロールプレーン）: 計測した基準値がないうちは、小さなチームにとってコストと故障の
  形が見合わない。
- **独自のオーケストレーターを今、別リポジトリで作る**: 組み込み（Stop フック、`--max-budget-usd`、
  `--json-schema`、Workflows）でほとんどを賄える。強制はどのみちプロジェクト自身の `.claude/` に置く
  必要があり、4つ目のリポジトリは移植のコストを増やす。
- **Probity を段階1の中核にする**（`ADR-0007`）: `tdd-implementer` と `test-writer` を区別できない。
  `enforceTdd()` はサブエージェントのフローを誤判定する。任意の補助レイヤーとして残す。
- **セッション全体の `permissions.deny` で `Edit(tests/**)` を拒否する**: `test-writer` もブロックして
  しまう。
- **サブエージェントの frontmatter にフックを置く**: テストでは `claude -p` の下で実行されなかった。
- **Gate 4 を今緩める**: どのデータも安全だと示す前に、20以上のファイルと3つのリポジトリにまたがって
  Gate の定義を変えることになる。段階3に先送り。
- **何もしない**: TDD の中核の保証 — ゴールは実装の前に固定される — がプロンプトに頼ったままになる。

## Consequences

### メリット
- 「`tests/` を編集しない」が実装者に対して強制され、監査の記録が残る。
- 拒否の件数によって、Gate 4 が実際に何かを守っていたかが初めてわかる。
- 人間のワークフローも Gate の定義も変わらない。

### デメリット・リスク
- テンプレートで初めて登録したライフサイクルフックである（`ADR-0011` は意図的に `/review` から呼ぶ
  スクリプトにした）。フックは Windows の Git Bash で動き続けなければならない。
- ネイティブWindowsでは、フックはサブプロセス経由で回避できる。Green 後のスナップショットのチェックが
  最後の砦であり、完全に自律したループ（段階5）にはエージェントの外から実行するチェックが必要になる。
- `disable-model-invocation: true` によって、素の言葉での依頼（「レビューして」「コミットして」）では
  コマンドが始まらなくなる。人間がコマンドを入力する — これが意図した挙動である。根底のルール
  （`docs/development/review-guidelines.md`、`docs/development/git-workflow.md`）は素の依頼にも適用される。
- Codex の利用者は段階4（Codex のフック / 権限プロファイル）までプロンプトのレベルの保護のままになる。
  スナップショットのチェックは両方に適用される。
- JP版には保留中の ADR 草案があり、再開時に次の空き番号を使う。
