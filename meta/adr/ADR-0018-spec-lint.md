# ADR-0018: 仕様ドキュメントの構造事前チェック（spec-lint）（Trial）

## Status
Trial — 実プロジェクトで使った後にAcceptedに昇格させるか、ロールバックする。

## Date
2026-10-05（実装 2026-10-03、`9406ae7`（EN）。日本語の見出しへの対応 `de664de`。JP への移植 `fc8c9cb`）

## Context

Gate 1〜3 は、AIがドラフトしたドキュメント（`requirements.md`、`use-cases.md`、モック）を人間が承認する
ゲートである。レビュー担当者が確認していた内容の一部は構造であり、これは機械でも確認できる: すべての
ユースケースに Actor・基本フロー・エラーケース・権限があるか、IDの形式が正しく一意か、各ユースケースが
実在する要件を指しているか、テンプレートの文言が残っていないか。

開発サイクル全体の調査（2026-10-03、EN `meta/design/template-improvement-directions.md`）で、次のことが
わかった:

- 仕様駆動開発ツールの整合性チェックの手順はLLMへのプロンプトである（spec-kit `/analyze`、Kiro の
  「Analyze Requirements」）。見つかった唯一の決定論的なバリデーター（OpenSpec）は見出しとキーワードしか
  チェックしない。
- LLMによる仕様レビューが見つけたのは、専門家が特定した問題の中央値47%で、11%は誤検知だった
  （arXiv 2609.03230）——決定論的なチェックの代わりにはならない。
- 単語リストによる要求の「臭い」の検出が高精度なのは4カテゴリ——主観的な表現、曖昧な副詞・形容詞、
  抜け穴、範囲の定まらない語——だけで、精度は0.70〜0.96（Femmer et al.、arXiv 1611.08847）。代名詞や
  否定のチェックはほとんどがノイズである。
- Loop Engineering の設計（`ADR-0017`）は、`SPEC_CONFLICT` のために、安定したユースケースIDと
  ユースケースの行をそのまま引用できることを前提にしている。それを保証するものはなかった。

## Decision

- `.claude/hooks/spec-lint.sh` を追加する: 読み取り専用、bash + awk、新しい依存関係なし、AIの呼び出しなし。
  次の内容をそれぞれ1行で報告する: 形式が正しくない、または重複した `UC-NNN` / `F-NNN` のID。Actor・
  基本フロー・エラーケース・権限のいずれかがない、または空のユースケース。存在しない関連要件と、
  どのユースケースからも参照されていない要件。残っているテンプレートの文言（承認記録とレビュー基準の
  セクションを除く）。モックファイル・ユースケースID・画面一覧の食い違い。そして警告としてのみ、高精度な
  4つの「臭い」カテゴリの単語（英語と日本語のリスト。スクリプトの先頭で編集できる）。
- `--requirements` は `requirements.md` だけをチェックする（Gate 1 の前）。`requirements.md` が参照先を
  示すだけの場合（既存コードベース導入パス）は、要件へのリンクのチェックを省略する。未解消の
  `[inferred]` マーカーは別に報告するので、同じ実行で Gate 0〜3 の一括承認もチェックできる。
- AIは Gate 1、Gate 2、または Gate 0〜3 の一括承認を求める前にこれを実行し、承認の依頼と一緒に指摘を
  示す（`CLAUDE.md`、`AGENTS.md`、`SETUP.md` Step 2 と 2B、`/onboard-existing-codebase`）。これは
  レビュー担当者に情報を与えるだけで、承認・却下・ブロックは決してしない。Gateの定義は変えない。
- 1つのファイルで英語版と日本語版の両方のテンプレートに対応する（見出しとラベルは両方の言語で、
  半角・全角どちらのコロンでも受け付ける）。そのため、他のフックスクリプトと同様に、兄弟リポジトリは
  これをバイト単位でそのままコピーする。
- `meta/tests/spec-lint.test.sh`（テンプレート内部用）でテストする。`meta/traceability-matrix.md` で
  追跡する。

## Rationale

ドキュメントのゲートを改善する最も安くて確実な方法は、レビューの機械的な半分を人間から取り上げ、
レビューの時間を、内容が正しく完全かどうか——スクリプトには判断できない部分——に使えるようにする
ことである。情報を与えるだけのチェックなら、Gateは人間の判断のままであり、誤検知で作業が止まることも
ない。

### 採用しなかった代替案
- **SDDフレームワークの analyze 手順（spec-kit、cc-sdd）を採用する**: そのチェックはLLMへのプロンプトで
  あり、フレームワークを採用すると Gate 0〜3 と重複する（`ADR-0015`）。
- **LLMによるレビューのみ**: 再現率が低く（47%）、結果が決定論的でない。スクリプトの後に助言として
  追加することはありうるが、スクリプトの代わりにはしない。
- **クリーンな実行結果をGateの条件にする**: 3つのリポジトリでGateの定義が変わり、誤検知で作業が
  止まる。指摘は示し、判断は人間が行う。
- **EARSの文型を必須にする**: 根拠は産業界の事例1件だけであり、ビジネス側の要件の書き方を変えることに
  なる。
- **広い単語リスト（代名詞、否定、「など」の類すべて）**: 研究では精度が低い。ノイズが多いと、人は出力を
  無視するようになる。

## Consequences

### メリット
- 構造上の抜けが、レビューの前に毎回、1回あたり約1秒で見つかる。
- ユースケースIDとセクション名が規則的に保たれ、Loop Engineering のチェックがそれを前提にできる。
- 3つのリポジトリすべてで同じファイルである。

### デメリット・リスク
- 要件そのものが丸ごと欠けていることは見えない——要件の問題として最もよく挙げられるものであり、それは
  レビュー担当者に残る。
- テンプレートの見出しを変更したプロジェクトは、スクリプト先頭のラベル変数を編集する必要がある。
  さもないと、セクションがないと報告される。
- 曖昧な語の警告は、分野によってはノイズになりうる。リストは編集できる。
