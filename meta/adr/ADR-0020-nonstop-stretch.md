# ADR-0020: 止めずに進める区間（Loop Engineering 段階3の再定義）（Trial）

## Status
Trial — EN版 ADR-0019（2026-10-12、2026-10-13・10-15 追記）を本プロジェクトに直接移植したもの。実プロジェクトでの試用後に Accepted にするか、ロールバックする。

## Date
2026-10-19（本プロジェクトへの移植）

## Context

ADR-0017 は段階3を、Green の**再試行ループ**として計画していた。段階2a（ADR-0019）とその後の分析では、
実際のサイクルの10回中9回で、実装者は1回の呼び出しで Green に到達していた。人の時間を使っていたのは、
「進めて」「コミットして」といった許可、人が起動しなければならないコマンド（`/review`、`/verify`）、
そして遅いタイミングでの判断だった。再試行ループはほとんど動かない。

メンテナーの目標（2026-10-08）: 人が承認したら、レビューを含めて**止まらずに**進み、人が判断すべきだと
機械的なチェックが示した箇所でだけ止まる——ブラックボックスにはしない。調整（2026-10-12）: 素早く開発できる
ことを優先し、一部の変更は最後のレビューまで素通りしてよいが、重大なセキュリティリスク・重大な機能バグ・
破壊的操作は決して見逃さない。新しく覚える設定は増やさず、サイクルあたりのトークンも増やさない。

## Decision

段階3を**止めずに進める区間**として定義し直す（設計: EN版の `meta/design/nonstop-goal.md`）。

1. **範囲** — 人が起動した `/tdd` の中の、Gate 4 承認から完了報告まで。仕様（Gate 0〜3）、テスト（Gate 4）、
   最後の報告は引き続き人が判断する。マージも人が行う。
2. **S7 — Green 後のリスクの高い変更で止まる**（EN版の `meta/design/s7-user-facing-stop.md`）:
   `tdd-snapshot.sh mark-green` / `verify-green` が、Green 後に行われた権限・破壊的操作・セキュリティ・
   secrets・外部への影響・依存関係・整合性の変更で止まり、それ以外のユーザー向けの変更は最後のレビュー用に
   一覧にする。決定的で、トークンは0。
3. **サイクルレビュー**（EN版の `meta/design/cycle-reviewer.md`）: `/tdd` が Green 後に実行する、指摘だけを
   返すサブエージェント（`cycle-reviewer`、Read / Grep / Glob）。小さな変更ではスキップする。判断が必要な指摘
   （仕様の矛盾、セキュリティ、ユーザー向けの変更、不審な指示、HIGH）で区間は止まる。DEFECT / DOMAIN_BOUNDARY
   の指摘は**1回だけ**修正し、全件テストと S7 を続けて実行する。
4. **利用者向けの新しい概念を増やさない** — スイッチも設定もない。自動で見つけられるものは自動で見つける
   （例: S7 が使う、プロジェクト独自のロール判定メソッド）。

**連続実行と上限（EN 2026-10-13、EN版の `meta/design/stretch-chaining-limits.md`）。**
`/tdd` は Gate 4 承認から1通の完了報告（ステップ8。判断が必要なものが先頭。`lite` ではコミットとマージの
計画も含む）まで、ステップの間で待たない。S5 と S9 は `agent-guard.sh` の機械的なチェックになった: Gate 4
承認1回あたり、3回目の `tdd-implementer` の起動と、60回を超える実装者の書き込み・コマンドを拒否する
（観測された最大値、起動2回・呼び出し34回のおよそ2倍）。時間とトークンは制限しない——フックからは見えない。

**ガードレールの回帰（EN 2026-10-15、EN版の `meta/design/guardrail-regression-suite.md`）。**
Claude Code のアップデート後にフックが一致しなくなると、何の兆候もなく素通りになる。常時・トークン0で、
`tdd-snapshot.sh verify` は、承認後に `agent-guard.sh` が実装者の呼び出しを1件も数えなかったときに警告する。
フックの配線とモデル上の挙動を確かめ直すスクリプトはテンプレート側（EN版）にあり、本プロジェクトには取り込まない。

### 本プロジェクトでの適用
- フック（`agent-guard.sh`・`tdd-snapshot.sh`）は EN版とバイト単位で同一。違うのは ADR 番号のコメントと
  メッセージだけである（EN 0016 → 本プロジェクト 0017、EN 0019 → 0020）。EN版の `meta/tests/` を本プロジェクトの
  フックに対して実行し、全件通ることを確認した（agent-guard 83、tdd-snapshot 45、fixture-literal-check 21）。
- フロントエンドは Livewire なので、`/tdd` のサイクルレビューを省略しない条件に `app/Livewire/` を加え、
  `cycle-reviewer` の判断基準に Livewire コンポーネントを加えた。スクリプトの `LISTED` の対象パスには
  `app/Livewire/` が入っていないが、`STOP` の判定は行の内容で行うので同じく効く。
- Codex ではフックが動かないため、S5/S9 の上限は働かない（`AGENTS.md`、`docs/development/codex-adapter.md`）。

## Rationale

- 許可待ちをなくすほうが、再試行よりも人の時間を減らす。
- 守らなければならないガードレールは機械的なチェックにする（S1〜S3、S7）。判断は人に残す。
- サブエージェントは何もインストールせず、スクリプトも増やさない。修正後のリスクの高い部分は、
  引き続きスクリプト（S7）が判断する。

### 採用しなかった代替案

- **上限付きの Green 再試行ループ（ADR-0017 段階3の当初案）** — ほとんど動かない。
- **段階2bの人による A/B** — 新しい目標が問わない問いに答えるもの。
- **ヘッドレス `claude -p` のレビュアースクリプト** — CLI が PATH に必要で、スクリプトとテストが1つずつ増える。

## Consequences

### Benefits
- 人に聞くのは Gate 4、停止条件にかかったとき、最後に1回だけになる。各ステップの後ではない。
- 実運用で守られなかった唯一のルール（承認なしのユーザー向け挙動変更）が、最も重要なケースで機械に裏付けられる。

### Drawbacks / Risks
- パターンベースの S7 は、よく使われる語を使わずに書かれた権限の変更を見逃すことがある。レビュアーと最後の
  レビューで補うが、保証はない。
- サイクルレビューの振り分けは、書かれたルールに従ってメインセッションが行う。試用中は、捨てられた指摘や
  振り分けを誤った指摘に注意する。
- レビューしたサイクルあたり約 $0.3、1〜2分。
