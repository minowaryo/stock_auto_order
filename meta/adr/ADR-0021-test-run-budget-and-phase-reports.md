# ADR-0021: `/tdd` とマージのテスト実行バジェットと、各フェーズ終了時の結果報告（Trial）

## Status
Trial — EN版 ADR-0020 を本プロジェクトに直接移植したもの。実プロジェクトでの試用後に Accepted にするか、ロールバックする。

## Date
2026-10-19（本プロジェクトへの移植。EN版は 2026-10-13、実プロジェクト `ihs-tech-uplift` で計測・採用されたもの）

## Context

ある実プロジェクト（Laravel + MySQL、テスト466件）で、小さな UC 変更の `/tdd` 1サイクルに約50分かかり、
その大半はコードを書く時間ではなくテストの待ち時間だった。

- 全件（5分46秒）が4回実行された: `tdd-implementer`、同じツリーに対するメインセッション、マージ結果
  （`main` が動いていなかったのでブランチ先端と同一）、計測用の1回。うち2回は結果が分かっているものの繰り返しだった。
- サブエージェントも、変わっていないテストファイルを何度も再実行した。
- 待ち時間はトークンを使わないが、実行のたびに出力がコンテキストに読み戻される。テスト1件ごとに1行の出力が膨らませていた。
- 466件中16件が、317テスト秒のうち約222秒を使っていた（実データファイルをテストごとに取り込み直す12件、
  `setUp` で `Schema::create` を実行してテストごとに全件の再マイグレーションを起こす1件など）。
- サイクルは、何が起きたかの1通の報告なしに終わっていた。

## Decision

1. **テスト実行バジェット**（`.claude/rules/30-testing.md`、`/tdd`、TDDの両サブエージェント）:
   - Red: `test-writer` は自分が作成・編集したテストファイルだけを実行する。メインセッションは Gate 4 の根拠として
     それらを1回実行する。Red で全件を実行する者はいない。
   - Green: `tdd-implementer` は対象テストファイルだけを実行し、全件は実行しない。メインセッションが `/tdd`
     ステップ4で全件を1回実行する——サイクルの正式な実行。そこでの失敗は実装者に戻し、試行回数に数える。
   - Green 後に全件を再実行するのは、コードが変わったとき（サイクルレビューの修正、Refactor）だけ。
   - 反復中の広めの確認では `--exclude-group slow` を使ってよい。正式な実行には含める。
   - AI による実行は `--compact` を使い、サマリー行と失敗ブロックだけを読む。
2. **マージ結果のテスト**（`docs/development/git-workflow.md` §5、`prepare-merge`）: 次の両方を満たす場合は省略する——
   ブランチを切ってからベースが動いていない（`git merge-base --is-ancestor <base> <branch>`。`--no-ff` のマージ結果の
   ツリーはブランチ先端と同じ）、かつこのセッションで、コミット済みのツリーそのものに対して全件が通っている。
   その場合 `Tests:` トレーラーにそう書く。それ以外、または迷ったら実行する。
3. **`slow` グループ**: 実データ相当の準備に数秒かかるテストには `#[Group('slow')]`（Pest: `->group('slow')`）を
   付ける。まず速くする（重い準備はテストごとに1回。MySQL では `setUp` で DDL を実行せず、一時テーブルを使う）。
4. **フェーズ報告**（会話の中だけ。ファイルには残さない）: `/tdd`・`/commit`・`prepare-merge` は、バグが見つかった
   かどうかに関係なく、途中で止まった場合も、必ず結果報告で終える。`/tdd` ではステップ8の完了報告（ADR-0020）で、
   その「チェック」項目に実行したテストを加える。`/commit` と `prepare-merge` はステップ8に固定の表を持つ。

## Rationale

待ち時間の大半は、同じツリーの繰り返し実行と、重い準備をやり直す少数のテストから来ていた。各ツリーを、その結果を
使う場所で1回だけ実行すれば、確認する範囲を下げずに繰り返しをなくせる: 全件は引き続き1サイクルに1回、その後に
コードが変わればもう1回、テスト済みのツリーと異なるマージ結果に対しても実行される。

### 採用しなかった代替案

- **`php artisan schema:dump`**: 計測したマイグレーションのコストは1回あたり約5〜7秒で効果が小さく、ダンプの読み込みには
  テストを実行するすべての環境で `mysql` クライアントが PATH に必要。
- **`php artisan test --parallel`**: `brianium/paratest`（新しい依存。独自の ADR が必要）とプロセスごとのテスト DB が必要。
- **フェーズ報告をファイルに保存する**: `git log`（マージのトレーラー）と `PLAN.md` と重複し、再利用されにくい。
- **マージ結果を常にテストする**: ベースが動いていなければ、マージ結果のツリーはテスト済みのブランチ先端とバイト単位で同一である。

## Consequences

### Benefits
- 実プロジェクトでの計測（遅いテストの整理後）: 466件 / 317テスト秒（実時間5分17秒〜5分46秒）→ 460件 / 151テスト秒（2分30秒〜2分50秒）。
- 見込み（未計測）: 同じ規模のサイクルが約50分 → 25〜30分。主に、全件実行が1サイクル3回から1回になることによる。
- 各サイクルが、読める1通の報告で終わる。

### Drawbacks / Risks
- 正式な全件実行が1サイクルに1回なので、不安定なテストは偶然の再実行に救われず、1回で表に出る。
- マージ時のテスト省略は、テストしたツリーがコミット済みのツリーと同じだとセッションが知っていることに依存する。迷ったらマージ結果をテストする。
- 本プロジェクトでは Sail コンテナと testing DB を並行セッションと共有している。全件実行が減ることで、他セッションとの衝突（`docs/ai-context/known-pitfalls.md`）の機会も減る。
